Topic 01

Local Versus Shared State

The most important question in state management: where should this value live?

1.1 What is state?

State is information an application remembers and uses to determine what appears on the screen.

For example, a student management dashboard may remember:

  • The currently selected tab.
  • The text in a search box.
  • The active filter.
  • The selected student.
  • The user's favorite courses.
  • The current shopping cart.
  • The currently signed-in user's profile information.

You have already learned about useState. State management extends that knowledge by helping you decide where the state should live and how multiple components should access and update it.

1.2 What is local state?

Local state is state managed by a component for its own needs.

For example, a search input might need to remember the text currently being typed.

SearchBox.jsxJSX
import { useState } from "react";

function SearchBox() {
  const [search, setSearch] = useState("");

  return (
    <div className="space-y-3">
      <input
        value={search}
        onChange={event => setSearch(event.target.value)}
        placeholder="Search students"
        className="rounded-lg border p-3"
      />

      <p>You are searching for: {search}</p>
    </div>
  );
}

export default SearchBox;

Here, search is local state.

The component manages it because the value is only needed for this small interface.

Why use local state?

Local state is appropriate for:

  • Opening and closing a dropdown.
  • Showing a modal.
  • Managing a controlled input.
  • Keeping track of which accordion section is open.
  • Temporarily selecting a tab.
  • Displaying the current step in a wizard.

You do not need Redux or Context for every small interface value.

1.3 What is shared state?

Shared state is information that multiple components need to access or update.

Imagine an online shopping interface:

  • Navbar displays the shopping cart count.
  • ProductList displays available products.
  • ProductCard allows items to be added to the cart.
  • CartPage displays the selected items.
  • CheckoutPage uses the cart information to prepare the checkout.

If these components need the same cart information, the application needs a way to share that state consistently.

◆ Analogy: A Family Budget

Imagine a family where several people contribute to the same household budget.

Each person may perform different tasks, but they need an accurate view of the shared amount.

Shared state works similarly: several components work with a common source of information.

1.4 Sharing state by lifting it up

For a small application, the solution may simply be to move the state into the closest common parent.

App.jsxJSX
import { useState } from "react";

function CartButton({ count }) {
  return <button>Cart ({count})</button>;
}

function ProductCard({ onAdd }) {
  return (
    <button onClick={onAdd}>
      Add Product
    </button>
  );
}

function App() {
  const [cartCount, setCartCount] = useState(0);

  return (
    <div className="space-y-4">
      <CartButton count={cartCount} />

      <ProductCard
        onAdd={() => setCartCount(count => count + 1)}
      />
    </div>
  );
}

export default App;

The parent owns the state. It passes the current value down through props and supplies the update function to the child.

This is a good solution for small component trees.

1.5 When does local state become shared state?

Suppose your application starts with one product card. Its selection might remain local.

Later, multiple product cards, a navigation bar, a cart page, and a checkout summary need access to the same cart data.

At that point, you need a state-sharing strategy that keeps the data consistent.

Common options include:

  • Lifting state into a common parent.
  • Context combined with useState or useReducer.
  • Redux Toolkit.
  • A lightweight external store.
  • A dedicated server-state library when the data comes from an API.
◆ Remember

Local state belongs to a component's own needs. Shared state is information that multiple components need to coordinate around. Start with the simplest approach that fits the application.

Topic 02

Prop Drilling and When It Matters

A design concern, not a React error.

2.1 What is prop drilling?

Prop drilling occurs when a value must be passed through multiple intermediate components just to reach a deeply nested component that actually needs it.

Imagine your application has this structure:

App └── Dashboard └── Sidebar └── UserMenu └── UserAvatar

Suppose UserAvatar needs the current user's information.

You might pass that information from App to Dashboard, then Sidebar, then UserMenu, before it reaches UserAvatar.

If the intermediate components do not use the data themselves, passing it through every level can become inconvenient.

◆ Analogy: Passing a Message Through a Chain

Imagine that a manager needs to send a message to one employee.

The message passes through several people who do not need to read it themselves.

That process works, but the chain can become unnecessary overhead.

Prop drilling is similar.

2.2 Example of prop drilling

App.jsxJSX
function UserAvatar({ user }) {
  return (
    <div className="rounded-lg bg-white p-4">
      <h2>{user.name}</h2>
      <p>{user.email}</p>
    </div>
  );
}

function UserMenu({ user }) {
  return <UserAvatar user={user} />;
}

function Sidebar({ user }) {
  return <UserMenu user={user} />;
}

function Dashboard({ user }) {
  return <Sidebar user={user} />;
}

function App() {
  const user = {
    name: "Rahul",
    email: "rahul@example.com"
  };

  return <Dashboard user={user} />;
}

export default App;

The information passes through several components even though only UserAvatar displays it.

2.3 Is prop drilling always bad?

No.

Passing props is a fundamental React pattern. It clearly shows which components receive and use which information.

Prop drilling becomes a concern when:

  • Many intermediate components only forward a value.
  • The same information is used by many distant components.
  • Updating the component hierarchy requires changing numerous prop declarations.
  • The application becomes harder to maintain because shared information is threaded through unrelated components.

If the hierarchy is shallow, or if intermediate components genuinely need the value, props are often the best choice.

2.4 Solution 1: Keep using props

For a shallow structure, simply pass the required value.

JSXJSX
function StudentCard({ student }) {
  return <h2>{student.name}</h2>;
}

function StudentList({ student }) {
  return <StudentCard student={student} />;
}

This is easy to understand and does not require extra architecture.

2.5 Solution 2: Use composition

Sometimes you can restructure the components so that an intermediate layout receives ready-made children instead of repeatedly forwarding data.

JSXJSX
function Layout({ children }) {
  return (
    <div className="rounded-xl bg-white p-6 shadow-sm">
      {children}
    </div>
  );
}

function StudentProfile({ student }) {
  return (
    <Layout>
      <h2 className="font-bold">{student.name}</h2>
      <p>{student.email}</p>
    </Layout>
  );
}

The layout does not need to know anything about students.

2.6 Solution 3: Use Context

Context allows a parent to provide a value to descendants without every intermediate component manually forwarding it through props.

That is particularly useful for values like a shared theme, current user information, or application preferences.

You will implement Context in the next topic.

◆ Remember

Prop drilling is a design concern, not a React error. Use props by default, and introduce Context or a store when the shared-state requirements justify it.

Reference: React — Passing Data Deeply with Context.

Topic 03

Context API Patterns

Distributing values through the component tree.

3.1 What is the Context API?

Context is a React feature that allows a parent to provide information to descendant components without manually passing the value through each intermediate component.

Context is commonly useful for:

  • Theme preferences.
  • Current user information.
  • Application settings.
  • Locale and language preferences.
  • Shared interface configuration.

Context distributes a value. The value can itself contain state and functions, but Context does not automatically provide state management or persistence.

◆ Analogy: A Shared Noticeboard

Imagine an office noticeboard that displays a common company announcement.

Any employee in that office can read the announcement without asking every person between them and the noticeboard.

Context provides a similar way of making information available to a section of the component tree.

3.2 Step 1: Create a Context

Create src/context/ThemeContext.jsx:

src/context/ThemeContext.jsxJSX
import { createContext } from "react";

const ThemeContext = createContext("light");

export default ThemeContext;

createContext("light") creates a context with a default value of "light".

That default is used when a component reads the context without a matching provider above it.

It is not a shared state variable that can be changed automatically.

3.3 Step 2: Provide the value

Create src/App.jsx:

src/App.jsxJSX
import { useState } from "react";
import ThemeContext from "./context/ThemeContext.jsx";
import ThemeLabel from "./components/ThemeLabel.jsx";

function App() {
  const [theme, setTheme] = useState("light");

  function toggleTheme() {
    setTheme(current =>
      current === "light" ? "dark" : "light"
    );
  }

  return (
    <ThemeContext.Provider value={theme}>
      <main className={theme === "dark" ? "bg-slate-900 p-6 text-white" : "bg-slate-100 p-6 text-slate-900"}>
        <button
          onClick={toggleTheme}
          className="rounded-lg bg-blue-600 px-4 py-2 text-white"
        >
          Switch Theme
        </button>

        <ThemeLabel />
      </main>
    </ThemeContext.Provider>
  );
}

export default App;

The provider makes the current theme available to its descendants.

When theme changes, React updates the provided value.

3.4 Step 3: Read the context

Create src/components/ThemeLabel.jsx:

src/components/ThemeLabel.jsxJSX
import { useContext } from "react";
import ThemeContext from "../context/ThemeContext.jsx";

function ThemeLabel() {
  const theme = useContext(ThemeContext);

  return (
    <p className="mt-4 font-semibold">
      Current theme: {theme}
    </p>
  );
}

export default ThemeLabel;

useContext(ThemeContext) reads the value from the nearest matching provider above the component.

You do not need to pass theme through every intermediate component.

3.5 Context with a custom Hook

You can simplify context access with a custom Hook.

ThemeContext.jsxJSX
import { createContext, useContext } from "react";

const ThemeContext = createContext(null);

export function useTheme() {
  const context = useContext(ThemeContext);

  if (context === null) {
    throw new Error("useTheme must be used inside ThemeProvider");
  }

  return context;
}

export default ThemeContext;

Now any descendant can use:

usageJSX
const theme = useTheme();

The custom Hook makes the pattern easier to reuse and gives a clearer error if the component is placed outside its provider.

3.6 Separate contexts by responsibility

Avoid combining unrelated global values into one enormous Context unnecessarily.

For example, a larger application might have:

Contexts
AuthContext
ThemeContext
LanguageContext

This makes responsibilities easier to understand.

However, do not create a context for every small local value. A component-local modal state usually does not require a global provider.

3.7 Avoid unnecessary context rerenders

Components that read a context value are updated when the provider supplies a different value.

If the provider creates a new object on every render, consumers may receive a changed reference even when the meaningful contents are unchanged.

For example:

providerJSX
<PreferencesContext.Provider value={{ theme, language }}>
  {children}
</PreferencesContext.Provider>

For a performance-sensitive component, consider whether the provider's value needs to be memoized, whether the Context should be split into separate responsibilities, or whether a selector-based state-management solution would be more suitable.

Do not add memoization automatically to every context. Start with a clear state design and optimize when needed.

◆ Remember

Context is useful for making shared values available to distant descendants. Pair it with state when the value needs to change, and avoid turning it into a home for every value in the application.

Official reference: React — useContext.

Topic 04

useReducer with Context

Centralized update logic without adopting Redux.

4.1 Why combine Context with useReducer?

Context can distribute a shared value, and useReducer can organize state updates through actions and a reducer function.

Together, they can provide a predictable pattern for shared state without introducing Redux.

This can work well for moderately complex state within a particular application section.

For example, a shopping cart might support actions such as:

  • Add item.
  • Remove item.
  • Change quantity.
  • Clear cart.

Rather than placing all the update functions in a large parent component, you can centralize the update logic in a reducer.

4.2 What is a reducer?

A reducer is a function that receives the current state and an action, then returns the next state.

reducerJavaScript
function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return state + 1;

    case "decrement":
      return state - 1;

    default:
      return state;
  }
}

The action describes what happened. The reducer calculates the resulting state.

4.3 Create a shared cart Context

Create src/context/CartContext.jsx:

src/context/CartContext.jsxJSX
import {
  createContext,
  useContext,
  useReducer
} from "react";

const CartStateContext = createContext(null);
const CartDispatchContext = createContext(null);

const initialState = {
  items: []
};

function cartReducer(state, action) {
  switch (action.type) {
    case "cart/add": {
      const existing = state.items.find(
        item => item.id === action.item.id
      );

      if (existing) {
        return {
          ...state,
          items: state.items.map(item =>
            item.id === action.item.id
              ? { ...item, quantity: item.quantity + 1 }
              : item
          )
        };
      }

      return {
        ...state,
        items: [...state.items, { ...action.item, quantity: 1 }]
      };
    }

    case "cart/remove":
      return {
        ...state,
        items: state.items.filter(
          item => item.id !== action.id
        )
      };

    case "cart/clear":
      return initialState;

    default:
      return state;
  }
}

export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(
    cartReducer,
    initialState
  );

  return (
    <CartStateContext.Provider value={state}>
      <CartDispatchContext.Provider value={dispatch}>
        {children}
      </CartDispatchContext.Provider>
    </CartStateContext.Provider>
  );
}

export function useCartState() {
  const context = useContext(CartStateContext);

  if (context === null) {
    throw new Error("useCartState must be used inside CartProvider");
  }

  return context;
}

export function useCartDispatch() {
  const context = useContext(CartDispatchContext);

  if (context === null) {
    throw new Error("useCartDispatch must be used inside CartProvider");
  }

  return context;
}

Explanation

Initial state

initial stateJSX
const initialState = {
  items: []
};

The cart initially contains no items.

Reducer

The reducer handles add, remove, and clear actions. Each action returns the new state, using immutable update patterns.

Provider

CartProvider creates the shared reducer state and distributes the state and dispatch function.

Custom Hooks

useCartState() and useCartDispatch() provide access to the appropriate context values.

Separating state and dispatch into two contexts can be useful when some components only need to dispatch actions. It does not guarantee that every state-reading component will avoid updates; consumers of the state context can still update when its value changes.

4.4 Use the shared cart state

Create src/components/CartSummary.jsx:

src/components/CartSummary.jsxJSX
import { useCartState } from "../context/CartContext.jsx";

function CartSummary() {
  const { items } = useCartState();

  const totalQuantity = items.reduce(
    (total, item) => total + item.quantity,
    0
  );

  return (
    <p className="rounded-lg bg-white p-4 shadow-sm">
      Cart items: {totalQuantity}
    </p>
  );
}

export default CartSummary;

This component reads the cart data without needing props from every intermediate component.

4.5 Dispatch an action from another component

ProductCard.jsxJSX
import { useCartDispatch } from "../context/CartContext.jsx";

function ProductCard({ product }) {
  const dispatch = useCartDispatch();

  function handleAdd() {
    dispatch({
      type: "cart/add",
      item: product
    });
  }

  return (
    <article className="rounded-xl bg-white p-5 shadow-sm">
      <h2 className="font-semibold">{product.name}</h2>

      <button
        onClick={handleAdd}
        className="mt-3 rounded-lg bg-blue-600 px-4 py-2 text-white"
      >
        Add to Cart
      </button>
    </article>
  );
}

export default ProductCard;

The product card dispatches an action. The reducer calculates the next state, and components that use the updated state can render again.

4.6 When is Context plus useReducer enough?

This pattern can be useful for:

  • A multi-step form.
  • A small shopping cart.
  • A wizard with multiple related transitions.
  • Shared settings with structured updates.
  • A feature where several components need the same state.

For a large application with many features, advanced debugging requirements, or complex asynchronous workflows, Redux Toolkit may provide a more maintainable architecture.

◆ Remember

Context distributes shared state; useReducer organizes how that state changes. Together they offer a built-in alternative for moderately complex shared-state needs.

Official reference: React — Scaling Up with Reducer and Context.

Topic 05

Redux Toolkit Fundamentals

The recommended modern way to write Redux logic.

5.1 What is Redux?

Redux is a state-management library designed to manage application state through a centralized store and predictable update patterns.

It is often used when multiple parts of an application need access to shared state and when the update logic becomes complicated.

5.2 What is Redux Toolkit?

Redux Toolkit, commonly abbreviated RTK, is the recommended modern way to write Redux logic.

It provides tools such as:

  • configureStore
  • createSlice
  • createAsyncThunk
  • RTK Query
  • Utilities for managing structured state

Redux Toolkit reduces boilerplate and includes useful defaults for common Redux patterns.

Documentation: Redux Toolkit — Usage Guide.

◆ Analogy: A Central Office Database

Imagine a company where multiple departments need access to the same official records.

Rather than maintaining disconnected copies of the records, the company keeps an organized central system.

Applications with shared global state can follow a similar approach.

The store holds the shared state, actions describe what happened, and reducers calculate how the state changes.

5.3 The Redux data flow

5.4 When should you use Redux Toolkit?

Redux Toolkit is particularly useful when:

  • Many components require the same state.
  • State is updated by many different actions.
  • State transitions are complex.
  • Several developers work on different features.
  • You need Redux DevTools for debugging and inspection.
  • You want a structured place for global client-state logic.

Redux is not mandatory for every React project.

5.5 Install Redux Toolkit and React Redux

In your Vite project:

terminalBash
npm install @reduxjs/toolkit react-redux

These packages provide Redux Toolkit and its official React integration.

◆ Remember

Redux Toolkit helps you manage complex shared client state predictably. Begin with a real requirement for shared state instead of adding Redux to every small application.

Topic 06

Store, Slices, Reducers and Actions

The four building blocks that make Redux tick.

6.1 What is the Redux store?

The store holds the application's Redux state and provides the mechanism for dispatching actions.

A store might contain:

store shapeJavaScript
{
  cart: {
    items: []
  },
  preferences: {
    theme: "light"
  }
}

Here, cart and preferences are separate top-level state sections.

6.2 What is a slice?

A slice represents one feature or section of your Redux state.

For example:

  • cartSlice
  • preferencesSlice
  • favoritesSlice
  • usersSlice

A slice defines an initial state and reducer functions for that part of the store.

6.3 What is a reducer?

A reducer determines how state changes in response to an action.

For a cart slice, the reducer might add a product, remove a product, or clear the cart.

6.4 What is an action?

An action describes what happened.

For example:

actionJavaScript
{
  type: "cart/addItem",
  payload: {
    id: 1,
    name: "React Course",
    price: 100
  }
}

An action contains a type and may contain a payload carrying data.

Redux Toolkit automatically generates action creators for the reducer functions declared in createSlice.

6.5 Create a cart slice

Create src/features/cart/cartSlice.js:

src/features/cart/cartSlice.jsJavaScript
import { createSlice } from "@reduxjs/toolkit";

const initialState = {
  items: []
};

const cartSlice = createSlice({
  name: "cart",

  initialState,

  reducers: {
    addItem(state, action) {
      const product = action.payload;

      const existing = state.items.find(
        item => item.id === product.id
      );

      if (existing) {
        existing.quantity += 1;
      } else {
        state.items.push({
          ...product,
          quantity: 1
        });
      }
    },

    removeItem(state, action) {
      state.items = state.items.filter(
        item => item.id !== action.payload
      );
    },

    clearCart(state) {
      state.items = [];
    }
  }
});

export const { addItem, removeItem, clearCart } =
  cartSlice.actions;

export default cartSlice.reducer;

Explanation

Slice name

nameJavaScript
name: "cart"

The slice name contributes to the generated action type strings.

Initial state

initial stateJavaScript
const initialState = {
  items: []
};

The cart starts empty.

Reducers

reducerJavaScript
addItem(state, action) {
  // Add product
}

The reducer receives the current draft state and the action.

Generated actions

actionsJavaScript
export const { addItem, removeItem, clearCart } =
  cartSlice.actions;

Redux Toolkit creates the action creators corresponding to these reducer names.

Exported reducer

reducer exportJavaScript
export default cartSlice.reducer;

This reducer is passed into the Redux store configuration.

6.6 Why does the reducer appear to mutate state?

In ordinary React state, you should not mutate existing objects or arrays.

However, Redux Toolkit's createSlice uses Immer internally. Immer allows you to write update logic in a mutation-like style while producing the necessary immutable state updates.

For example:

pushJavaScript
state.items.push(product);

is acceptable inside a createSlice reducer because Immer tracks the changes.

Do not take this pattern out of the reducer and use it to mutate arbitrary Redux state directly.

6.7 Configure the Redux store

Create src/app/store.js:

src/app/store.jsJavaScript
import { configureStore } from "@reduxjs/toolkit";
import cartReducer from "../features/cart/cartSlice.js";

export const store = configureStore({
  reducer: {
    cart: cartReducer
  }
});

The state has the following structure:

store shapeJavaScript
{
  cart: {
    items: []
  }
}

The cart key is determined by the key you used in the reducer object.

6.8 Provide the store to React

Open src/main.jsx:

src/main.jsxJSX
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { Provider } from "react-redux";
import { store } from "./app/store.js";
import App from "./App.jsx";
import "./index.css";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <Provider store={store}>
      <App />
    </Provider>
  </StrictMode>
);

Provider makes the Redux store accessible to descendant React components.

6.9 A professional folder structure for Redux

A practical feature-oriented structure looks like this:

src/ ├── app/ │ └── store.js ├── features/ │ ├── cart/ │ │ ├── cartSlice.js │ │ └── CartSummary.jsx │ └── preferences/ │ └── preferencesSlice.js ├── components/ ├── pages/ ├── services/ ├── hooks/ └── main.jsx

As your application grows, related actions, reducers, components, and services can be grouped by feature.

◆ Remember

The store holds the global state. A slice organizes state and reducers for a feature. Actions describe events, and reducers calculate how the state should change.

Topic 07

Selectors and useSelector

Reading and deriving state with precision.

7.1 What is a selector?

A selector is a function that reads or derives information from the Redux state.

For example:

selectorJavaScript
const selectCartItems = state => state.cart.items;

The selector receives the root state and returns a specific part of it.

7.2 Why are selectors useful?

Imagine that several components need the same information.

One component may need the cart items, another may need the item count, and another may need the total price.

Selectors let you centralize the logic for reading and deriving those values.

They also make components easier to understand.

7.3 What is useSelector?

useSelector is a React Redux Hook that lets a component read the result of a selector.

CartCount.jsxJSX
import { useSelector } from "react-redux";

function CartCount() {
  const items = useSelector(state => state.cart.items);

  const total = items.reduce(
    (sum, item) => sum + item.quantity,
    0
  );

  return <p>Cart items: {total}</p>;
}

The component subscribes to the selected part of the store.

When the selector result changes according to React Redux's comparison behavior, the component can render again.

7.4 Create reusable selectors

Create src/features/cart/cartSelectors.js:

src/features/cart/cartSelectors.jsJavaScript
export const selectCartItems = state => state.cart.items;

export const selectCartQuantity = state =>
  state.cart.items.reduce(
    (sum, item) => sum + item.quantity,
    0
  );

export const selectCartTotal = state =>
  state.cart.items.reduce(
    (sum, item) => sum + item.price * item.quantity,
    0
  );

Now components can select precisely the information they need.

CartTotal.jsxJSX
import { useSelector } from "react-redux";
import { selectCartTotal } from "./cartSelectors.js";

function CartTotal() {
  const total = useSelector(selectCartTotal);

  return (
    <p className="text-lg font-bold">
      Total: ₹{total}
    </p>
  );
}

This avoids repeating the total-price calculation in multiple components.

7.5 What is a memoized selector?

A memoized selector can cache the result of an expensive calculation when its input values have not changed.

Redux Toolkit re-exports createSelector from Reselect.

For example:

memoized selectorJavaScript
import { createSelector } from "@reduxjs/toolkit";

const selectItems = state => state.cart.items;

export const selectCartSummary = createSelector(
  [selectItems],
  items => ({
    quantity: items.reduce(
      (sum, item) => sum + item.quantity,
      0
    ),

    total: items.reduce(
      (sum, item) => sum + item.price * item.quantity,
      0
    )
  })
);

The selector calculates the summary from the items array and can reuse the previous result when its input remains unchanged.

This is helpful when calculations are expensive or when a stable derived result matters. You do not need memoization for every simple selector.

7.6 Avoid unnecessarily selecting the entire store

For example:

✕ Don'tJSX
const wholeState = useSelector(state => state);

This may cause the component to render on many unrelated state changes.

Prefer selecting the specific section or derived value needed:

✓ DoJSX
const items = useSelector(state => state.cart.items);
◆ Remember

Use selectors to read and derive data from Redux state. Use useSelector inside React components to access the result.

Official reference: React Redux — Hooks API.

Topic 08

useDispatch and Async Workflows

Dispatching actions and managing asynchronous logic.

8.1 What is useDispatch?

useDispatch is a React Redux Hook that returns the store's dispatch function.

You use it to dispatch actions from components.

Example:

AddToCartButton.jsxJSX
import { useDispatch } from "react-redux";
import { addItem } from "./features/cart/cartSlice.js";

function AddToCartButton({ product }) {
  const dispatch = useDispatch();

  return (
    <button
      onClick={() => dispatch(addItem(product))}
      className="rounded-lg bg-blue-600 px-4 py-2 text-white"
    >
      Add to Cart
    </button>
  );
}

When the user clicks the button, the action is dispatched. The cart reducer calculates the new state, and relevant components can update.

8.2 What is asynchronous Redux logic?

Some workflows involve operations that take time, such as a server request.

For example:

  • Fetch a list of students.
  • Submit a form.
  • Verify a login request.
  • Save changes to a profile.

The Redux store processes state updates synchronously. The asynchronous work must happen outside the reducer, and the result can then be used to update the store.

8.3 What is createAsyncThunk?

Redux Toolkit provides createAsyncThunk for asynchronous workflows that need pending, fulfilled, and rejected actions.

It creates lifecycle actions around a Promise-returning payload creator.

This is useful when you want to implement custom asynchronous logic in Redux.

For straightforward server-state fetching and caching, RTK Query is usually the recommended option within Redux Toolkit. We will cover it in Topic 9.

8.4 Create an asynchronous thunk

Create src/features/users/usersSlice.js:

src/features/users/usersSlice.jsJavaScript
import {
  createAsyncThunk,
  createSlice
} from "@reduxjs/toolkit";

export const fetchUsers = createAsyncThunk(
  "users/fetchUsers",

  async (_, { rejectWithValue, signal }) => {
    try {
      const response = await fetch(
        "https://jsonplaceholder.typicode.com/users",
        { signal }
      );

      if (!response.ok) {
        return rejectWithValue("Failed to fetch users");
      }

      return await response.json();
    } catch (error) {
      if (error.name === "AbortError") {
        throw error;
      }

      return rejectWithValue(
        error.message || "Unexpected request error"
      );
    }
  }
);

const usersSlice = createSlice({
  name: "users",

  initialState: {
    items: [],
    status: "idle",
    error: null
  },

  reducers: {},

  extraReducers: builder => {
    builder
      .addCase(fetchUsers.pending, state => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.items = action.payload;
      })
      .addCase(fetchUsers.rejected, (state, action) => {
        if (action.meta.aborted) {
          state.status = "idle";
          return;
        }

        state.status = "failed";

        state.error =
          action.payload || action.error.message || "Request failed";
      });
  }
});

export default usersSlice.reducer;

Explanation

createAsyncThunk creates a thunk called fetchUsers and lifecycle actions for it.

The payload creator requests users and returns the parsed data.

The reducer processes the following outcomes:

  • pending: request started.
  • fulfilled: request succeeded.
  • rejected: request failed or was rejected.

extraReducers lets the slice respond to actions generated elsewhere, including asynchronous thunk lifecycle actions.

8.5 Add the slice to the store

store.jsJavaScript
import { configureStore } from "@reduxjs/toolkit";
import cartReducer from "../features/cart/cartSlice.js";
import usersReducer from "../features/users/usersSlice.js";

export const store = configureStore({
  reducer: {
    cart: cartReducer,
    users: usersReducer
  }
});

The store now contains both cart state and user-request state.

8.6 Dispatch the thunk from a component

UsersPage.jsxJSX
import { useEffect } from "react";
import { useDispatch, useSelector } from "react-redux";
import { fetchUsers } from "./features/users/usersSlice.js";

function UsersPage() {
  const dispatch = useDispatch();

  const {
    items: users,
    status,
    error
  } = useSelector(state => state.users);

  useEffect(() => {
    const request = dispatch(fetchUsers());

    return () => {
      request.abort();
    };
  }, [dispatch]);

  if (status === "loading") {
    return <p>Loading users...</p>;
  }

  if (status === "failed") {
    return <p role="alert">{error}</p>;
  }

  if (users.length === 0) {
    return <p>No users found.</p>;
  }

  return (
    <ul className="space-y-2">
      {users.map(user => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}

This is a demonstration of a custom Redux asynchronous workflow.

For a complete production implementation, account for request deduplication and possible overlapping requests so that an obsolete response cannot overwrite the latest result. RTK Query already handles many common server-state concerns and is generally the better default for standard data fetching.

◆ Remember

useDispatch lets React components dispatch Redux actions. createAsyncThunk is useful for custom asynchronous workflows that require explicit lifecycle state in Redux.

Official reference: Redux Toolkit — createAsyncThunk.

Topic 09

RTK Query or TanStack Query for Server State

Choosing the right tool for data that lives on the server.

9.1 What is server state?

Server state is information that belongs to a backend or external service and is fetched by the frontend.

Examples include:

  • Students loaded from a database.
  • Course records.
  • User profiles.
  • Product catalogs.
  • Attendance records.
  • Notifications.

Server state has different requirements from ordinary component state because it can become stale, requests can fail, multiple components may need the same data, and the server can change independently of the current page.

9.2 What is RTK Query?

RTK Query is a data-fetching and caching tool included in Redux Toolkit.

It provides:

  • Query hooks.
  • Mutation hooks.
  • Request lifecycle management.
  • Shared caching.
  • Cache invalidation.
  • Refetching.
  • Loading and error states.

It is particularly convenient when your application already uses Redux Toolkit.

9.3 Install Redux Toolkit

terminalBash
npm install @reduxjs/toolkit react-redux

RTK Query is included in Redux Toolkit; it is not a separate package that you need to install.

9.4 Create an API slice

Create src/features/users/usersApi.js:

src/features/users/usersApi.jsJavaScript
import {
  createApi,
  fetchBaseQuery
} from "@reduxjs/toolkit/query/react";

export const usersApi = createApi({
  reducerPath: "usersApi",

  baseQuery: fetchBaseQuery({
    baseUrl: "https://jsonplaceholder.typicode.com"
  }),

  tagTypes: ["Users"],

  endpoints: builder => ({
    getUsers: builder.query({
      query: () => "/users",
      providesTags: ["Users"]
    }),

    getUserById: builder.query({
      query: id => `/users/${id}`,
      providesTags: (result, error, id) => [
        { type: "Users", id }
      ]
    })
  })
});

export const {
  useGetUsersQuery,
  useGetUserByIdQuery
} = usersApi;

Explanation

createApi defines an API slice.

fetchBaseQuery is a lightweight request helper.

getUsers defines a query for the user list.

providesTags associates cached query data with a tag.

RTK Query generates React Hooks for the endpoints, which means you do not need to manually write the same loading and error state logic for each request.

9.7 What is TanStack Query?

TanStack Query is another library for fetching, caching, synchronizing, and updating server-state data.

It is independent of Redux and can be used with React's built-in state, Context, Redux Toolkit, or other state-management approaches.

  • QueryClientProvider
  • useQuery
  • useMutation
  • useInfiniteQuery
  • Query invalidation

Topic 10

Choosing Between Context, Redux and Other Stores

The decision-making skill that ties the previous topics together.

10.1 Why are there multiple options?

Different kinds of state have different needs.

For example, a search input only needs a short-lived local value, while a shopping cart may be shared across an entire application, and a list of students may be owned by the server.

Using one tool for every kind of state can introduce unnecessary complexity.

10.2 Compare the options

SituationGood starting choice
One component has a selected tabuseState
One component manages several related transitionsuseReducer
Multiple distant components share a small number of valuesContext
Complex global client state with many actionsRedux Toolkit
Frequently changing shared state where a small external store is preferredA library such as Zustand
API queries, caching and refetchingRTK Query or TanStack Query
Form inputs used only by one formLocal state or a form library, depending on complexity
Values that can be derived from other stateCalculate them instead of storing duplicate state

10.3 Context vs. Redux Toolkit

Use Context when:

  • You need to distribute values through a component tree.
  • The shared state and update logic are relatively straightforward.
  • A custom provider provides enough structure.

Use Redux Toolkit when:

  • Many application features share state.
  • State updates involve numerous actions or complicated transitions.
  • You need centralized debugging and predictable update patterns.
  • The application benefits from feature slices and selectors.

Context does not automatically cache data or provide Redux-style action history and reducer tooling.

Redux Toolkit introduces more concepts, so it may be unnecessary for a small application.

10.4 Redux Toolkit vs. server-state libraries

Redux is often useful for client-side application state, such as:

  • Cart items.
  • UI preferences.
  • Active selections.
  • Multi-step workflows.

RTK Query and TanStack Query specialize in server data, such as:

  • Records fetched from a backend.
  • Loading and error states.
  • Cached query results.
  • Refetching and invalidation.

If you use RTK Query, the API cache is already integrated with Redux Toolkit. You generally should not duplicate all its server data into ordinary Redux slices without a clear reason.

10.5 What about Zustand?

Zustand is a lightweight external state-management library.

It can be useful when you want a simpler shared store with direct selectors, without adopting the full Redux Toolkit pattern.

However, adding Zustand simply because Redux or Context exists is unnecessary. Choose it when its usage model fits your application.

10.6 A useful rule

Ask yourself:

  1. Is this value needed only in the current component?
  2. Is it shared by a few related components?
  3. Is it required throughout many features?
  4. Does it come from the backend?
  5. Does it need to survive a page refresh?
  6. Does the update logic justify additional architecture?

Your answers will help you choose the right tool without overengineering.

◆ Remember

There is no single best state-management tool for every React application. Choose the simplest approach that meets the requirements, and use specialized server-state tools for API data.

Topic 11

Persisting Selected State Safely

Remembering what matters — without creating security risks.

11.1 What is persistence?

Persistence means retaining selected information beyond the current component's lifetime or browser session.

Normally, React component state is reset when the page reloads.

For example, an application may want to remember:

  • The user's selected theme.
  • Whether the sidebar is collapsed.
  • A non-sensitive draft preference.
  • A shopping cart, if the product requirements call for it.

Persistence can use browser storage or a backend.

◆ Analogy: A Notebook vs. Temporary Memory

Imagine writing a preference on a sticky note and throwing it away at the end of the day.

The next time you return, you must choose the same preference again.

Saving the preference to a notebook helps you retain it.

Browser storage provides a simple way to remember selected values across reloads.

11.2 What is localStorage?

localStorage is a browser API that stores string values for a given origin across browser sessions.

Example:

localStorageJavaScript
localStorage.setItem("theme", "dark");

const theme = localStorage.getItem("theme");

console.log(theme);

To remove the value:

removeJavaScript
localStorage.removeItem("theme");

It stores strings, so objects must be serialized using JSON.stringify() and parsed using JSON.parse().

11.3 Persist a theme with React state

ThemeSettings.jsxJSX
import { useEffect, useState } from "react";

function ThemeSettings() {
  const [theme, setTheme] = useState(() => {
    try {
      const savedTheme = localStorage.getItem("theme");

      return savedTheme === "dark" ? "dark" : "light";
    } catch {
      return "light";
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem("theme", theme);
    } catch {
      // Storage may be unavailable or blocked.
    }
  }, [theme]);

  return (
    <main className={theme === "dark" ? "min-h-screen bg-slate-900 p-6 text-white" : "min-h-screen bg-slate-100 p-6 text-slate-900"}>
      <h1 className="text-2xl font-bold">Theme Settings</h1>

      <p className="mt-3">Current theme: {theme}</p>

      <button
        onClick={() => setTheme(current => current === "dark" ? "light" : "dark")}
        className="mt-5 rounded-lg bg-blue-600 px-4 py-2 text-white"
      >
        Switch Theme
      </button>
    </main>
  );
}

export default ThemeSettings;

Explanation

Initialize the state from storage

lazy initJSX
const [theme, setTheme] = useState(() => {
  // Read the stored preference.
});

The lazy initializer reads the value when the component initializes, rather than on every render.

Write changes to storage

saveJSX
useEffect(() => {
  localStorage.setItem("theme", theme);
}, [theme]);

When the theme changes, the Effect saves the new preference.

Handle storage errors

Storage may be unavailable because of browser settings or the environment. The example catches storage failures rather than crashing the application.

This pattern is intended for client-rendered browser applications such as Vite. Server-rendered applications need to account for the fact that localStorage is not available on the server.

11.4 Persist selected Redux state

For Redux applications, persist only the sections that genuinely need to survive reloads.

For example, you might persist:

persisted shapeJavaScript
{
  preferences: {
    theme: "dark",
    sidebarCollapsed: false
  }
}

But you might choose not to persist:

  • Temporary modal state.
  • Loading flags.
  • Transient error messages.
  • Temporary API results that should come from the server.
  • Sensitive authentication information.

A simple approach for a small project is to load only a validated preferences object when creating the store and save only that slice on state changes.

loadPreferencesJavaScript
function loadPreferences() {
  const defaults = {
    theme: "light",
    sidebarCollapsed: false
  };

  try {
    const raw = localStorage.getItem("app-preferences");

    if (!raw) return defaults;

    const parsed = JSON.parse(raw);

    return {
      theme: parsed.theme === "dark" ? "dark" : "light",
      sidebarCollapsed: parsed.sidebarCollapsed === true
    };
  } catch {
    return defaults;
  }
}

This code validates the permitted fields rather than accepting an arbitrary stored object as the application's complete state.

When configuring a Redux store, the preferences object can be provided as the initial state for the preferences slice. The state can then be serialized back to storage after changes.

For larger projects, a persistence library may help manage rehydration, selection of persisted slices, version migrations, and storage configuration.

11.5 What should never be persisted casually?

Do not blindly persist every Redux state value.

Be especially cautious with:

  • Passwords.
  • Authentication tokens.
  • Private API credentials.
  • Sensitive personal information.
  • Authorization information treated as the source of truth.

localStorage is accessible to JavaScript running on the same origin. If a successful cross-site scripting attack executes malicious JavaScript in your application, that code may be able to read stored values.

For authentication sessions, a backend-managed session using an appropriately configured HttpOnly, Secure, and SameSite cookie is often a safer starting point than storing sensitive tokens in localStorage. The correct strategy depends on your authentication architecture.

▲ Important

Persisted client state must never be treated as proof that a user is authorized to access protected backend resources. Authorization must be enforced by the server.

◆ Remember

Persist only the state the product genuinely needs to remember. Validate values loaded from storage, handle storage errors, and keep sensitive credentials out of ordinary browser storage.

import { useDispatch, useSelector } from "react-redux";
import { toggleFavorite } from "../features/favorites/favoritesSlice.js";

function UserCard({ user }) {
  const dispatch = useDispatch();

  const isFavorite = useSelector(state =>
    state.favorites.ids.includes(user.id)
  );

  return (
    <article className="rounded-2xl border border-slate-200 bg-white p-5 shadow-sm transition duration-200 hover:-translate-y-1 hover:shadow-md">
      <div className="flex items-start gap-4">
        <div className="flex size-12 shrink-0 items-center justify-center rounded-full bg-blue-100 font-bold text-blue-700">
          {user.name.charAt(0).toUpperCase()}
        </div>

        <div className="min-w-0">
          <h2 className="font-semibold text-slate-900">
            {user.name}
          </h2>

          <p className="break-words text-sm text-slate-500">
            {user.email}
          </p>
        </div>
      </div>

      <p className="mt-4 text-sm text-slate-600">
        {user.company.name}
      </p>

      <button
        onClick={() => dispatch(toggleFavorite(user.id))}
        aria-pressed={isFavorite}
        className={
          "mt-5 rounded-lg px-4 py-2 text-sm font-semibold transition " +
          (isFavorite
            ? "bg-amber-100 text-amber-800"
            : "bg-blue-600 text-white hover:bg-blue-700")
        }
      >
        {isFavorite ? "Remove Favorite" : "Add Favorite"}
      </button>
    </article>
  );
}

export default UserCard;

What does the component do?

useDispatch() obtains the dispatch function.

useSelector() reads whether the current user is in the favorites array.

Clicking the button dispatches toggleFavorite(user.id).

Redux processes the action, updates the favorite state, and causes the relevant component to render the updated state.

import { useMemo, useState } from "react";
import { useDispatch, useSelector } from "react-redux";
import { useGetUsersQuery } from "./features/users/usersApi.js";
import { toggleTheme } from "./features/preferences/preferencesSlice.js";
import {
  clearFavorites
} from "./features/favorites/favoritesSlice.js";
import {
  selectFavoriteCount
} from "./features/favorites/favoritesSelectors.js";
import UserCard from "./components/UserCard.jsx";

function App() {
  const dispatch = useDispatch();

  const theme = useSelector(state => state.preferences.theme);
  const favoriteCount = useSelector(selectFavoriteCount);

  const [search, setSearch] = useState("");

  const {
    data: users = [],
    isLoading,
    isFetching,
    isError,
    error,
    refetch
  } = useGetUsersQuery();

  const filteredUsers = useMemo(() => {
    return users.filter(user =>
      `${user.name} ${user.email} ${user.company.name}`
        .toLowerCase()
        .includes(search.trim().toLowerCase())
    );
  }, [users, search]);

  return (
    <main
      className={
        theme === "dark"
          ? "min-h-screen bg-slate-900 p-4 text-white sm:p-8"
          : "min-h-screen bg-slate-50 p-4 text-slate-900 sm:p-8"
      }
    >
      <div className="mx-auto max-w-7xl">
        <header className="mb-8 flex flex-col gap-4 sm:flex-row sm:items-center sm:justify-between">
          <div>
            <p className="text-sm font-semibold uppercase tracking-wide text-blue-600">
              Phase 7 Project
            </p>

            <h1 className="mt-2 text-3xl font-bold sm:text-4xl">
              State Management Dashboard
            </h1>

            <p className="mt-2 text-sm opacity-70">
              Shared state, server data, selectors and persistence.
            </p>
          </div>

          <div className="flex flex-wrap gap-2">
            <button
              onClick={() => dispatch(toggleTheme())}
              className="rounded-lg border border-slate-300 px-4 py-2"
            >
              Switch Theme
            </button>

            <button
              onClick={() => refetch()}
              disabled={isFetching}
              className="rounded-lg bg-blue-600 px-4 py-2 text-white disabled:opacity-50"
            >
              {isFetching ? "Refreshing..." : "Refresh"}
            </button>
          </div>
        </header>

        <section className="mb-6 grid gap-4 sm:grid-cols-3">
          <article className="rounded-xl border border-slate-200 bg-white p-5 text-slate-900">
            <p className="text-sm text-slate-500">Total Users</p>
            <p className="mt-2 text-3xl font-bold">{users.length}</p>
          </article>

          <article className="rounded-xl border border-slate-200 bg-white p-5 text-slate-900">
            <p className="text-sm text-slate-500">Favorites</p>
            <p className="mt-2 text-3xl font-bold">{favoriteCount}</p>
          </article>

          <article className="rounded-xl border border-slate-200 bg-white p-5 text-slate-900">
            <p className="text-sm text-slate-500">Current Theme</p>
            <p className="mt-2 text-3xl font-bold capitalize">{theme}</p>
          </article>
        </section>

        <section className="mb-6 rounded-xl border border-slate-200 bg-white p-4">
          <label
            htmlFor="search"
            className="mb-2 block text-sm font-medium text-slate-700"
          >
            Search users
          </label>

          <div className="flex flex-col gap-3 sm:flex-row">
            <input
              id="search"
              value={search}
              onChange={event => setSearch(event.target.value)}
              placeholder="Search by name, email or company"
              className="min-w-0 flex-1 rounded-lg border border-slate-300 p-3 text-slate-900 outline-none focus:border-blue-500 focus:ring-2 focus:ring-blue-100"
            />

            <button
              onClick={() => dispatch(clearFavorites())}
              className="rounded-lg border border-slate-300 px-4 py-3 text-slate-700 hover:bg-slate-50"
            >
              Clear Favorites
            </button>
          </div>
        </section>

        {isLoading && (
          <div className="grid gap-4 sm:grid-cols-2 lg:grid-cols-3">
            {[1, 2, 3].map(item => (
              <div
                key={item}
                className="animate-pulse rounded-xl bg-white p-6"
              >
                <div className="mb-4 h-5 w-1/2 rounded bg-slate-200" />
                <div className="h-4 w-full rounded bg-slate-100" />
              </div>
            ))}
          </div>
        )}

        {isError && (
          <div
            role="alert"
            className="rounded-xl border border-red-200 bg-red-50 p-6 text-red-700"
          >
            <p>Unable to load users.</p>
            <p className="mt-1 text-sm">{error?.message}</p>
            <button
              onClick={() => refetch()}
              className="mt-4 rounded-lg bg-red-600 px-4 py-2 text-white"
            >
              Try Again
            </button>
          </div>
        )}

        {!isLoading && !isError && (
          <>
            {isFetching && (
              <p className="mb-4 text-sm text-blue-600">
                Updating user data...
              </p>
            )}

            {filteredUsers.length === 0 ? (
              <div className="rounded-xl border border-dashed border-slate-300 p-12 text-center">
                <h2 className="text-xl font-semibold">
                  No matching users
                </h2>
                <p className="mt-2 opacity-70">
                  Try another search term.
                </p>
              </div>
            ) : (
              <section className="grid gap-4 sm:grid-cols-2 lg:grid-cols-3">
                {filteredUsers.map(user => (
                  <UserCard key={user.id} user={user} />
                ))}
              </section>
            )}
          </>
        )}
      </div>
    </main>
  );
}

export default App;

Reference

Common Beginner Mistakes

Eight pitfalls every state-management developer runs into — and how to fix them.

1. Putting every value in Redux

A simple input or modal state does not need global storage unless other parts of the application genuinely need it.

2. Using Context for everything

Context is useful for sharing values, but a large stateful application may benefit from a more structured state-management approach.

3. Mutating React state outside Redux reducers

Within createSlice reducers, mutation-like syntax is handled by Immer. Outside those reducers, continue to treat state as immutable.

4. Confusing selectors with reducers

A selector reads or derives information. A reducer calculates how the state changes in response to an action.

5. Using useDispatch to perform every API request manually

For ordinary server-state requests, RTK Query or TanStack Query can provide caching and request lifecycle management without requiring a separate Redux reducer for each request state.

6. Duplicating API results into Redux without a reason

When RTK Query already owns the API cache, copying every response into another slice creates redundant state and synchronization work.

7. Saving sensitive information in localStorage

Browser storage can be accessed by JavaScript on the same origin. Do not persist passwords, private service credentials, or authentication secrets casually.

8. Treating frontend route or state as authorization

Hiding an admin button or protecting a page in React does not secure the API. The backend must enforce authorization.

Quick Revision Notes

One-line definitions for every term in this module.

Local state

Data needed by one component.

Shared state

Data required by multiple components.

Prop drilling

Passing data through multiple intermediate components that do not use it themselves.

Context API

Provides values to descendants without manually forwarding props through every level.

useReducer with Context

A built-in way to organize complex shared state transitions.

Redux Toolkit

The recommended modern way to write Redux logic.

Store

Central container for Redux application state.

Slice

A defined section of the Redux state and its update logic.

Reducer

Function that calculates the next state.

Action

Description of something that happened.

Selector

Function that reads or derives data from state.

useSelector

Hook for selecting state from the Redux store.

useDispatch

Hook that returns the Redux dispatch function.

createAsyncThunk

Tool for managing custom asynchronous workflows in Redux.

RTK Query

Redux Toolkit's built-in solution for fetching, caching, and updating server data.

TanStack Query

Independent library for managing server-state requests and caching.

Persistence

Saving selected information so it survives a page reload or session transition.

Safe persistence

Persist only necessary, validated, non-sensitive values and never treat browser storage as a trusted authorization source.
