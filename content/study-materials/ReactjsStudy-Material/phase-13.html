Imagine you have built a Full Stack Training LMS with student accounts, administrator access, course materials, attendance records, and enrollment payments.

The application looks good and all its React components work. But before real students use it, you must answer important questions:

  • Can a student open an administrator-only API endpoint?
  • Are session credentials protected?
  • Can malicious text execute as JavaScript?
  • Are private backend credentials exposed in the frontend build?
  • Does the application handle API failures safely?
  • Does refreshing a nested route produce a 404?

▲ Important principle

A React application runs in the user's browser, so users can inspect its JavaScript and manipulate its state. Anything enforced only by frontend code can be bypassed. Sensitive access control must be enforced by a trusted server or service.

AUTH
Topic 1

Authentication Versus Authorization

Who you are is not the same as what you may do.

1.1 What is authentication?

Authentication verifies who a user is.

For example, when a student signs in to your LMS, the authentication system verifies the user's credentials or identity-provider response and establishes an authenticated session.

Typical authentication features include:

  • Sign-in
  • Sign-out
  • Password reset
  • Multi-factor authentication
  • Session expiration
  • Identity-provider integration

Imagine a student enters their email and password. The backend verifies the credentials and establishes the user's authenticated session.

1.2 What is authorization?

Authorization determines what an authenticated user is allowed to do.

For example, a student might be permitted to read released course materials but not to release books to other students.

An administrator might be allowed to publish books, manage enrollment, and update course access.

QuestionAuthenticationAuthorization
What does it determine?Who is the user?What may the user do?
ExampleStudent signs inStudent can read an assigned book
Another exampleAdministrator signs inAdministrator can release a book
Typical enforcementIdentity provider and session verificationBackend permission and resource checks

The two systems work together, but they solve different problems. An authenticated user is not automatically authorized to access every feature or record. See the OWASP Authorization Cheat Sheet.

Analogy · Front desk vs. the key rack
Authentication checks your ID at the desk. Authorization decides which rooms your key opens. A guest whose face matches the booking (authentication) still cannot enter every room (authorization). Every protected door must have its own lock.

1.3 A frontend permission check

Imagine that only administrators should see a button for releasing a book.

BookActions.tsxTSX
interface User {
  id: string;
  name: string;
  role: "student" | "admin";
}

interface BookActionsProps {
  user: User;
  bookId: string;
}

function BookActions({ user, bookId }: BookActionsProps) {
  function releaseBook() {
    // Call the backend release endpoint here.
    console.log("Request release for:", bookId);
  }

  return (
    <div>
      {user.role === "admin" && (
        <button
          type="button"
          onClick={releaseBook}
          className="rounded-lg bg-indigo-600 px-4 py-2 text-white"
        >
          Release Book
        </button>
      )}
    </div>
  );
}

Student sees:

(nothing — action hidden)

Hiding the button improves the UI, but the backend must still reject unauthorized release requests.

This improves the user interface because students do not see an action they cannot use.

However, it is not security enforcement. A student could manipulate frontend state, modify JavaScript, or call the backend endpoint independently.

The backend must verify that the authenticated account has administrator permissions.

1.4 Enforce permissions on the backend

The following Express-style example illustrates the backend responsibility:

server.tsTS
app.post(
  "/api/admin/books/:bookId/release",
  requireAuthenticatedUser,
  requireAdmin,
  async (req, res) => {
    const { bookId } = req.params;

    await releaseBook(bookId);

    res.status(200).json({
      success: true,
    });
  }
);

Here, requireAuthenticatedUser, requireAdmin, and releaseBook represent server-side functionality you must implement using your authentication system, authorization model, and data layer.

The backend must verify the user's permission on each protected request. It should also check whether the user is allowed to access the specific resource being requested.

For example, even if a student is authenticated, they should not be able to download another student's private documents merely by changing a student ID in the URL.

1.5 Real-life LMS example

Consider three roles:

  • Student: Reads books released to that student.
  • Trainer: Manages permitted course materials.
  • Administrator: Manages student accounts and book-release permissions.

Create a permission model that describes actions, not just the visible navigation:

permissions.tsTS
type Role = "student" | "trainer" | "admin";

type Permission =
  | "book:read"
  | "book:release"
  | "student:manage"
  | "attendance:manage";

const rolePermissions: Record<Role, Permission[]> = {
  student: ["book:read"],
  trainer: ["book:read", "attendance:manage"],
  admin: [
    "book:read",
    "book:release",
    "student:manage",
    "attendance:manage",
  ],
};

This is useful for expressing a frontend permission model, but do not treat the frontend object as the authoritative access-control system. The backend must enforce the corresponding rules independently.

Topic 2

Safe Token and Session Handling

Where credentials live determines how easily they can be stolen.

2.1 What is a session?

A session allows the application to recognize a user across multiple requests without requiring them to sign in again for every interaction.

Real-life example: after signing in to the LMS, a student opens their course page, checks attendance, and reads course material. The application must recognize the authenticated user during these requests.

Common mechanisms include:

  • Server-managed sessions identified by cookies
  • Access tokens used with an authentication system
  • OAuth 2.0 and OpenID Connect flows
  • A Backend-for-Frontend (BFF) that manages credentials on behalf of the browser

The correct design depends on the authentication architecture.

Analogy · Keys you never hand out
A session cookie is a key the browser keeps but the page cannot copy. With HttpOnly, JavaScript never sees the value — so even an XSS attacker cannot read it out of document.cookie.

2.2 Why token storage matters

A common mistake is storing access tokens or refresh tokens in localStorage because it is easy to access from React.

✕ AvoidTS
// Avoid storing authentication credentials this way.
localStorage.setItem("accessToken", token);

JavaScript executing within the same origin can read localStorage. If a cross-site scripting vulnerability allows an attacker to execute injected JavaScript, tokens stored there may be exposed.

OWASP advises against storing session identifiers, access tokens, refresh tokens, and other credentials in browser storage accessible to JavaScript. See the OWASP Session Management Cheat Sheet.

2.3 A common web-application pattern: secure session cookies

For a browser application backed by your own server, an HTTP-only session cookie is often a strong starting point.

A production session cookie might have attributes such as:

Set-CookieHTTP
Set-Cookie: __Host-session=<RANDOM_OPAQUE_SESSION_ID>; Path=/; Secure; HttpOnly; SameSite=Lax
◆ Corrected example

The previous example was largely valid; this version uses a clearer placeholder and a lowercase cookie-name suffix. The __Host- prefix requirements are satisfied.

Analogy · The sealed envelope
A session cookie is a sealed envelope with a wax stamp. HttpOnly keeps JavaScript from opening it. Secure ensures it only travels over an encrypted channel. The __Host- prefix binds it to a single origin so no subdomain can quietly read it.

The placeholder is not a real session credential. Your backend should generate and validate session identifiers using a secure implementation.

Understand the attributes:

AttributePurpose
SecureSends the cookie over HTTPS connections only
HttpOnlyPrevents JavaScript from reading the cookie
SameSite=LaxLimits many cross-site cookie-sending scenarios
Path=/Makes the cookie available across the site's paths
__Host- prefixRequires important host-only cookie restrictions, including Secure, Path=/, and no Domain attribute

The exact SameSite setting depends on the application's cross-site requirements. A cross-site cookie may require SameSite=None; Secure and stronger CSRF protections. These flags are not substitutes for server-side authorization or all XSS/CSRF defenses.

What each attribute does

  • __Host-session: Restricts the cookie to the host that sets it.
  • <RANDOM_OPAQUE_SESSION_ID>: A placeholder for a securely generated session identifier—not a literal value to copy.
  • Path=/: Makes the cookie available across paths on that host.
  • Secure: Sends the cookie only over HTTPS, except for browser localhost exceptions.
  • HttpOnly: Prevents JavaScript from reading the cookie.
  • SameSite=Lax: Provides some protection against cross-site request forgery (CSRF).
▲ Important

Do not include a Domain attribute with a __Host- cookie. The prefix requires Secure, Path=/, and no Domain attribute. See MDN documentation.

For additional protection, SameSite=Strict may be appropriate if your authentication and navigation flows support it. Whichever policy you choose, enforce session expiration and invalidate the server-side session on logout; cookie attributes alone are not sufficient. See OWASP session management guidance.

2.4 What happens after a user signs in?

A typical session-based flow looks like this:

  1. The user submits sign-in credentials over HTTPS.
  2. The server verifies the credentials.
  3. The server creates a session.
  4. The server sends a session cookie using appropriate security attributes.
  5. The browser attaches the cookie to eligible requests.
  6. The server verifies the session and checks the user's permissions.
  7. The server invalidates the session during logout or other required termination events.

React does not need to read an HTTP-only session cookie.

For example, the frontend can request the user's current session:

session.tsTS
interface SessionUser {
  id: string;
  name: string;
  role: "student" | "trainer" | "admin";
}

async function getCurrentUser(): Promise<SessionUser | null> {
  const response = await fetch("/api/session", {
    credentials: "same-origin",
  });

  if (response.status === 401) {
    return null;
  }

  if (!response.ok) {
    throw new Error("Could not check the current session.");
  }

  // Validate the response before trusting it in production.
  return response.json() as Promise<SessionUser>;
}

This code illustrates the frontend flow. In production, validate the returned JSON at runtime instead of blindly trusting the type assertion.

The session endpoint must return only appropriate user information and must verify the session on the server.

2.5 What if the application uses OAuth or access tokens?

Token-based authentication is also common, especially with identity providers and APIs.

The important considerations are:

  • Use a supported authentication flow.
  • Protect access and refresh tokens appropriately.
  • Validate tokens on the server or resource API.
  • Use TLS.
  • Handle expiration and revocation appropriately.
  • Do not assume a decoded token is automatically authentic.
  • Do not expose confidential client secrets in browser code.

A BFF pattern can keep long-lived credentials on the server while the browser interacts with the application through a session cookie.

The safest approach is the one that correctly fits your identity provider, application type, backend architecture, and threat model.

2.6 CSRF still matters

HTTP-only cookies help protect the cookie from being read by JavaScript, but the browser can still attach the cookie to requests.

For cookie-authenticated applications, evaluate cross-site request forgery (CSRF) risk.

Depending on the architecture, safeguards may include:

  • Appropriate SameSite cookie policy
  • Anti-CSRF tokens
  • Origin or Referer validation
  • Correct use of HTTP methods
  • Backend validation on every state-changing endpoint

SameSite is useful defense in depth, but it is not a universal replacement for a proper CSRF defense. See the OWASP CSRF Prevention Cheat Sheet.

XSS Risks and dangerouslySetInnerHTML

When text becomes code, every input becomes a potential attack surface.

3.1 What is XSS?

Cross-site scripting (XSS) is a vulnerability in which attacker-controlled content is interpreted as executable or otherwise dangerous browser content.

Real-life example: your LMS allows trainers to create course descriptions. If a student can submit a description containing malicious HTML and the application inserts it into a page unsafely, that content may execute in another user's browser.

Depending on the vulnerability, an attacker might manipulate the page, impersonate actions in the user's session, or access data available to page scripts.

Analogy · The uninvited guest
XSS is a guest who smuggles a script into your living room. React normally locks the door — it treats text as text. But when you call dangerouslySetInnerHTML, you are handing out keys. Sanitize every guest before letting them in.

3.2 React normally escapes text

This is the normal and safer way to display user-provided text:

StudentComment.tsxTSX
function StudentComment({ comment }: { comment: string }) {
  return <p>{comment}</p>;
}
StudentComment — HTML in the string Output

Hello <script>alert("XSS")</script> world

React displays the tags as text, not as executable markup.

React treats the string as text rather than parsing it as HTML.

For example, a string containing HTML-like tags is displayed as text in the paragraph rather than automatically becoming executable markup.

This protection applies to ordinary text rendering. It does not mean every way of passing data to the DOM is safe.

3.3 What is dangerouslySetInnerHTML?

React provides dangerouslySetInnerHTML for cases where the application intentionally inserts an HTML string.

CourseDescription.tsxTSX
function CourseDescription({ html }: { html: string }) {
  return (
    <div dangerouslySetInnerHTML={{ __html: html }} />
  );
}

The problem is that untrusted HTML may contain malicious elements, event handlers, or other dangerous content.

Do not pass arbitrary user-generated HTML into this property.

React's official documentation warns that untrusted input passed to dangerouslySetInnerHTML can introduce XSS vulnerabilities: React common DOM components.

3.4 Sanitize HTML before inserting it

Sometimes you genuinely need formatted content, such as a rich-text course description.

One option is to use a maintained HTML sanitization library.

Install DOMPurify:

terminalBash
npm install dompurify

For a browser-based React application:

CourseDescription.tsxTSX
import DOMPurify from "dompurify";

function CourseDescription({ html }: { html: string }) {
  const sanitizedHtml = DOMPurify.sanitize(html);

  return (
    <article
      className="prose max-w-none"
      dangerouslySetInnerHTML={{
        __html: sanitizedHtml,
      }}
    />
  );
}
CourseDescription — sanitized Output

React Fundamentals

Learn components, props, state, and hooks with practical projects.

Duration: 8 weeks · Level: Beginner

Script and event-handler attributes removed — safe markup preserved.

DOMPurify removes many dangerous constructs according to its sanitization rules. Its default configuration is a useful starting point for typical HTML sanitization, but you should configure it to match the allowed content you need and keep it updated.

If you do not need rich HTML, rendering the content as ordinary text is simpler and safer.

Also validate URL schemes and use safe handling for links, embedded content, and external resources. HTML sanitization is one defense, not a guarantee that every related issue has been solved.

3.5 Other sources of XSS risk

Review these areas:

  • Rich-text editors
  • Markdown-to-HTML conversion
  • HTML imported from other systems
  • Direct use of DOM APIs
  • Third-party widgets
  • User-controlled URLs
  • Unsafe template processing

Avoid treating a value as trusted merely because it comes from your database. Stored user input can still be malicious.

Useful references:

  • OWASP Cross Site Scripting Prevention
  • React DOM security guidance

Secure API Integration

A consistent client, correct methods, and errors that never leak internals.

4.1 Why is API security important?

A frontend communicates with the backend through requests and responses. Those requests may retrieve student records, upload files, modify permissions, or create accounts.

The frontend is not a trusted enforcement boundary. A user can modify the browser code or call an API independently.

Therefore, security-critical checks must occur on the server, and the frontend should handle the response safely.

See the OWASP REST Security Cheat Sheet.

Analogy · The labelled patch panel
A secure API is a well-labelled patch panel. Every cable is labelled with what it carries and who may unplug it. The frontend requests a specific port; the backend verifies the request, performs the operation, and responds with only what is allowed.

4.2 Create a central API helper

A central helper makes it easier to implement consistent error handling.

client.tsTS
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL;

export async function apiGet<T>(path: string): Promise<T> {
  const response = await fetch(`${API_BASE_URL}${path}`, {
    credentials: "include",
    headers: {
      Accept: "application/json",
    },
  });

  if (response.status === 401) {
    throw new Error("Please sign in to continue.");
  }

  if (!response.ok) {
    throw new Error("The request could not be completed.");
  }

  return response.json() as Promise<T>;
}

This example assumes that the application uses a browser cookie session and a configured API URL.

The T type is a compile-time expectation, not runtime validation. The response should be validated before the application trusts it, especially when the payload contains important business data.

The helper also needs architectural adjustments if your API uses a different base URL, authorization flow, CSRF mechanism, or response format.

4.3 Use the appropriate HTTP method

Use HTTP methods according to the API's intended operations.

MethodCommon use
GETRetrieve data
POSTCreate a resource or execute an operation
PUTReplace a resource
PATCHUpdate part of a resource
DELETEDelete a resource

The backend must still validate the request body, enforce permissions, and ensure that the operation is allowed.

Do not assume that a hidden frontend button or disabled input protects an endpoint.

4.4 Example: Send an update request

updateStudent.tsTS
interface UpdateStudentInput {
  name: string;
  courseId: string;
}

export async function updateStudent(
  studentId: string,
  input: UpdateStudentInput
): Promise<void> {
  const response = await fetch(
    `${API_BASE_URL}/students/${encodeURIComponent(studentId)}`,
    {
      method: "PATCH",
      credentials: "include",
      headers: {
        "Content-Type": "application/json",
        Accept: "application/json",
      },
      body: JSON.stringify(input),
    }
  );

  if (!response.ok) {
    throw new Error("Unable to update the student.");
  }
}

This example shows request construction, but the server must still verify the session, resource permissions, business rules, and input validity.

If a cookie-based cross-site setup requires CSRF tokens, include the correctly issued token according to the backend's expected mechanism. Do not invent a client-generated value and assume that it provides CSRF protection.

4.5 Avoid exposing sensitive information in responses

The backend should return only data appropriate for the requesting user.

For example, a public course list generally should not include private student records, password hashes, internal administrative notes, or unnecessary authentication metadata.

The frontend should not depend on hiding sensitive fields after they have already been sent to the browser.

4.6 Handle errors without leaking internals

Avoid returning raw stack traces or database errors to users.

A frontend can show a safe, general message while logging a diagnostic event for developers:

handler.tsxTSX
try {
  await updateStudent(studentId, input);
  setMessage("Student updated successfully.");
} catch {
  setMessage("Unable to update the student. Please try again.");
}
Update result — safe messages Output

✓ Success — Student updated successfully.

✕ Error — Unable to update the student. Please try again.

Stack traces, SQL errors, and internal details are never shown to the user.

Your monitoring system can capture relevant diagnostic information, with sensitive data removed.

CORS Fundamentals

A browser gate — not a security boundary on the server.

5.1 What is CORS?

CORS stands for Cross-Origin Resource Sharing.

A browser uses the same-origin policy to restrict certain cross-origin requests. CORS is a mechanism through which a server indicates which origins may access its responses through browser APIs such as fetch().

An origin consists of the scheme, hostname, and port.

For example:

  • http://localhost:5173
  • http://localhost:3000

These are different origins because their ports differ.

Imagine your React frontend runs on one origin while the backend API runs on another. The browser may block JavaScript from reading the API response unless the backend's CORS policy permits the frontend origin.

Reference: MDN CORS.

Analogy · The guest list at the door
CORS is a guest list enforced by the browser. The browser checks whether the origin is allowed to read the response. The bouncer (browser) only enforces the list — the venue (server) must still verify who you are and what you may do.

5.2 What does a CORS error mean?

Suppose the frontend executes:

fetchTSX
fetch("https://api.example.com/students");

If the API doesn't return the required CORS headers for the frontend's origin, the browser may refuse to expose the response to JavaScript.

This does not automatically mean that the API server itself is unreachable or that authentication is incorrect. Inspect the browser's Console and Network panels to diagnose the actual problem.

5.3 Configure CORS on the backend

For an Express backend, the cors middleware is commonly used.

Install it in the backend project:

terminalBash
npm install cors
npm install -D @types/cors

Example configuration:

server.tsTS
import cors from "cors";

app.use(
  cors({
    origin: ["https://lms.example.com"],
    credentials: true,
  })
);

This example permits the specified frontend origin and enables credentialed CORS handling.

The frontend origin must match the deployed application's actual origin. Keep the allowlist as narrow as your requirements allow.

When cookie credentials are included in cross-origin requests, the server must use an explicitly allowed origin rather than *, and the response must have the appropriate credentials header. The browser's cookie policy and the application's session and CSRF design must also be correct.

5.4 Send credentials only when appropriate

For a cross-origin cookie-based session, the frontend may need:

fetchTSX
fetch("https://api.example.com/students", {
  credentials: "include",
});

This tells the browser to include eligible credentials in the request.

For a same-origin cookie-based request, credentials: "same-origin" is commonly sufficient and is the default fetch credentials mode.

The correct setting depends on where the API lives and how authentication is configured.

5.5 CORS is not authorization

This is one of the most important concepts in this phase.

CORS does not prove that the person making a request has permission to access the data. It is primarily a browser mechanism controlling whether frontend scripts can read cross-origin responses.

An attacker can use non-browser clients to call an API directly. Therefore, your API still needs proper authentication, authorization, request validation, and other security controls.

Environment Configuration

Public configuration is not the same as a private secret.

6.1 What is environment configuration?

Applications commonly need different settings for development, staging, and production.

Examples include:

  • API base URL
  • Public application title
  • Public feature flags
  • Analytics configuration
  • Backend service endpoints

Different environments should use appropriate configuration instead of changing source code manually before every deployment.

6.2 Configure Vite environment variables

Vite exposes frontend variables through import.meta.env.

Example .env.development:

.env.developmentENV
VITE_API_BASE_URL=http://localhost:3000/api
VITE_APP_TITLE=Training LMS Development

Example .env.production:

.env.productionENV
VITE_API_BASE_URL=https://api.example.com/api
VITE_APP_TITLE=Training LMS

Usage in React:

env.tsTSX
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL;
const appTitle = import.meta.env.VITE_APP_TITLE;

Vite embeds VITE_-prefixed values into the client-side build. They are not secrets. Anyone who can access the deployed application can inspect those values.

See Vite environment variables and modes.

Analogy · The labelled keyring
Environment configuration is a labelled keyring. The development key opens the development door; the production key opens the production door. A key that opens every door is not a key — it's a secret. Public configuration is a key label. Private credentials belong on the server.

6.3 Never put backend secrets in frontend variables

Do not put these in a frontend-exposed environment variable:

  • Database passwords
  • Private API credentials
  • Secret signing keys
  • Private OAuth client secrets
  • Long-lived service tokens
  • Credentials that grant privileged backend access

For example, this is unsafe:

✕ UnsafeENV
VITE_DATABASE_PASSWORD=some-secret

The prefix tells Vite to expose the value to the client-side bundle.

Instead, keep private values in backend environment variables or a proper secret-management system.

6.4 An environment variable is not a secret simply because it is in .env

A .env file is a configuration file; it does not provide encryption or security by itself.

Keep private environment files out of version control, use a safe .gitignore, and commit only a template such as .env.example.

Example .env.example:

.env.exampleENV
VITE_API_BASE_URL=
VITE_APP_TITLE=Training LMS

This template contains placeholders rather than real credentials.

Vite's environment variables are loaded during startup or build. Restart the development server after changing environment files.

6.5 Type the frontend environment

You can declare expected public environment variables in a vite-env.d.ts file:

vite-env.d.tsTS
interface ImportMetaEnv {
  readonly VITE_API_BASE_URL: string;
  readonly VITE_APP_TITLE: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}

This provides editor support and documents the expected configuration. It does not validate that the values are present or correct at runtime, so important configuration should also be validated during startup or build as appropriate.

Two environments — same code, different configuration Output

VITE_APP_TITLE=Training LMS

Both files are committed as .env.example with empty values. Real values stay out of version control.

Topic 7

Frontend Error Reporting and Logging

Collect enough information to fix the bug — and none to betray the user.

7.1 Why does production logging matter?

A development console can help you debug a local problem, but a deployed application has users and devices you cannot directly inspect.

Imagine that the LMS reports that a course page went blank for some students. A production error-reporting system can help you identify the failing component, application release, browser environment, and stack trace.

Error monitoring is not only about collecting errors. It is about collecting enough information to investigate them safely.

Analogy · The flight recorder
An aircraft's black box records what mattered, not everything. Error monitoring should capture the flight path — release, route, error type, correlation ID — without recording the passengers' private conversations.

7.2 Use Error Boundaries for rendering failures

React Error Boundaries can catch certain errors thrown by descendant components during rendering and display a fallback.

For example:

ErrorBoundary.tsxTSX
import { Component, type ReactNode } from "react";

interface ErrorBoundaryState {
  hasError: boolean;
}

interface ErrorBoundaryProps {
  children: ReactNode;
}

class ErrorBoundary extends Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  state: ErrorBoundaryState = {
    hasError: false,
  };

  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true };
  }

  componentDidCatch(error: Error) {
    // Send a sanitized diagnostic event to your monitoring service.
    console.error("Dashboard section failed", error);
  }

  render() {
    if (this.state.hasError) {
      return (
        <div role="alert" className="rounded-xl border p-5">
          This section could not be displayed. Try again later.
        </div>
      );
    }

    return this.props.children;
  }
}

Use it around a part of the application:

Dashboard.tsxTSX
<ErrorBoundary>
  <AnalyticsDashboard />
</ErrorBoundary>
ErrorBoundary — fallback UI Output
⚠ This section could not be displayed.
Try again later.

Rest of the dashboard stays usable — only the failing panel was replaced.

The fallback keeps the user-facing experience more controlled when a descendant's rendering fails.

However, Error Boundaries do not catch every asynchronous or event-handler failure. Handle network requests, click handlers, timers, and other asynchronous operations appropriately in their own code.

7.3 Log useful information, not sensitive information

Useful information can include:

  • Error type and sanitized message
  • Application version
  • Route or feature name
  • Browser category
  • Release or build identifier
  • A correlation ID, where available

Avoid logging:

  • Passwords
  • Session cookies
  • Access tokens
  • Full payment credentials
  • Unnecessary student personal information
  • Sensitive request bodies
  • Entire server responses that may contain private data

Treat diagnostic events as potentially sensitive data. Apply access controls, retention policies, redaction, and sampling as appropriate.

7.4 Add a production error-reporting service

A service such as Sentry can collect frontend errors, provide stack traces, associate events with releases, and support source-map integration.

Follow the current official setup guide for your chosen monitoring provider.

For example, the core idea is to initialize an SDK once with appropriate configuration and report errors through its supported APIs. Do not add real credentials or expose private ingestion configuration beyond what your provider intentionally allows in a frontend SDK.

Source maps can help translate a minified production stack trace into useful original source locations. Treat source-map publication and access as part of your production security design.

Reference: Sentry React documentation.

7.5 Test the monitoring design

Build an intentional error path in development and verify that:

  1. A safe fallback appears.
  2. The error is recorded by the expected monitoring system.
  3. The event includes the correct release information.
  4. No sensitive values appear in the recorded payload.
  5. A user-facing message does not expose internal stack traces.

Build and Deployment Workflows

Reproducible builds, verified checks, reversible releases.

8.1 What happens during a production build?

A typical React production build transforms the project's source code into deployable assets.

In a Vite project, the command is usually:

terminalBash
npm run build

The output is generally placed in the dist directory.

The deployed files may include HTML, JavaScript chunks, CSS, fonts, and images.

The production deployment should use a reproducible build process and a controlled source of configuration.

Analogy · The shipment
A release is a shipment, not a handoff. Every package is inspected before it leaves (lint, tests, type check, build). If something is wrong, the whole shipment is held — not just the one item.

8.2 Separate development from production

Development mode supports fast iteration and debugging.

Production mode generally provides optimized assets and should be configured for a real deployment environment.

Before shipping the application, run the checks that your project supports:

terminalBash
npm ci
npm run lint
npm run test:run
npx tsc -b
npm run build

These commands assume your project has corresponding scripts and a Vite TypeScript setup. If one is missing, configure it rather than assuming it has already run.

npm ci installs from the lockfile and is appropriate for reproducible CI installations.

The test, lint, type-check, and build stages catch different classes of errors. A build alone does not necessarily mean that all tests have run.

8.3 Treat deployment configuration as part of the application

Before deployment, verify:

  • Production API URLs are correct.
  • No private credentials are embedded in the frontend.
  • API access is appropriately configured.
  • The hosting platform serves the built dist directory.
  • Browser routes work after direct navigation and page refresh.
  • HTTPS is enabled.
  • Error monitoring is configured and tested.
  • The previous release can be restored if a deployment fails.

8.4 Keep deploy credentials out of source code

Automated deployment commonly requires an access token or hosting credential.

Keep that credential in the platform's protected secret store or an approved identity-based deployment mechanism. Limit its scope and permissions to what the deployment process requires.

Do not commit credentials to Git or put them in frontend-exposed configuration.

Topic 9

Hosting and Routing Fallback Configuration

Clicking works. Refreshing gives a 404. The router is fine — the host isn't.

9.1 Why can a React route work after clicking but fail on refresh?

A typical React application uses client-side routing.

Imagine the user navigates to:

https://lms.example.com/students/STU-101

The React router recognizes the path and renders the student profile.

But if the user refreshes the page, the browser makes a request directly to the hosting server for /students/STU-101.

If the host searches for a physical file at that path and cannot find one, it may return 404 Not Found.

This is a hosting-routing problem, not necessarily a React component bug.

Analogy · The signpost at the door
The host needs to know every route leads to the same front door. Without an SPA fallback, refreshing a deep link asks for a file that doesn't exist — and the host returns a 404 instead of index.html.

9.2 What is an SPA fallback?

A single-page application (SPA) commonly serves the same HTML entry point for application routes.

When a request comes in for a route such as /students/STU-101, the host can return index.html, allowing the React router to handle the URL.

However, the fallback must be configured carefully. It should not turn missing JavaScript files or API requests into an HTML page.

9.3 Hosting rule: route fallback versus missing assets

A conceptual rule might be:

Routing rule
Application document routes → index.html
Existing JavaScript/CSS/images → corresponding assets
Missing JavaScript/CSS/images → real 404
API requests → backend/API handling

The exact syntax depends on your hosting platform. Some hosts have explicit SPA options; others require redirects or rewrite rules.

For Vite, the production output normally needs to be hosted from dist, and the deployment configuration must account for the application being a single-page app. See Vite static deployment.

9.4 What about nested paths?

Imagine your LMS uses the following routes:

Routes
/
 /login
 /dashboard
 /students
 /students/STU-101
 /courses/react
 /admin/books

Test each route by entering its URL directly into the address bar, not only by clicking the internal navigation links.

Also check that assets load correctly from nested routes.

If your application is hosted below a path such as /training/, you may need to configure Vite's base option and the router's base path appropriately.

9.5 A deployment debugging workflow

If refreshing a route produces a 404:

  1. Check whether the main document request returned 404.
  2. Confirm the built files were deployed to the correct directory.
  3. Review the hosting platform's rewrite or fallback rules.
  4. Confirm application routes return the frontend entry point.
  5. Verify that missing assets still return an error rather than index.html.
  6. Inspect the console and network requests for incorrect asset URLs.

Topic 10

CI Checks and Automated Tests

Every pull request passes the same gate before it can ship.

10.1 What is CI?

Continuous Integration (CI) is the practice of automatically checking changes as they are submitted to a project.

Imagine that several developers contribute to your LMS. One developer modifies the enrollment form, another changes the course list, and another updates the API client.

Without shared automated checks, a change might accidentally break the production build or an important workflow.

CI can run:

  • Lint checks
  • Type checking
  • Unit and component tests
  • Production builds
  • Additional security and integration checks
Analogy · The quality gate
CI is a quality gate on the assembly line. Every pull request is inspected — lint, tests, types, build — before it can merge. A failed check stops the line; nothing ships unverified.

10.2 Create a GitHub Actions workflow

For a repository hosted on GitHub, create .github/workflows/ci.yml:

.github/workflows/ci.ymlYAML
name: React CI

on:
  pull_request:
  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-latest

    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run lint
        run: npm run lint

      - name: Run tests
        run: npm run test:run

      - name: Check TypeScript
        run: npx tsc -b

      - name: Build for production
        run: npm run build

This is an illustrative workflow. Use current, approved action versions in your organization and confirm that Node.js 22 is supported by your project's dependency stack.

The workflow also assumes that the project provides lint, test:run, and TypeScript build scripts or compatible commands.

Official reference: GitHub Actions — Building and testing Node.js.

10.3 What does the workflow do?

  1. It checks out the source code.
  2. It installs Node.js.
  3. It installs dependencies from the lockfile.
  4. It runs linting.
  5. It runs the automated test suite.
  6. It checks TypeScript.
  7. It produces a production build.

When one of the required commands fails, the job fails. That gives the team an early warning before the change proceeds through the release process.

CI checks — pull request #482 Output

✓ passedInstall dependencies (npm ci)
✓ passedLint
✓ passedTests
✓ passedTypeScript
✓ passedBuild

A failed step would block merge and notify the author.

10.4 Add security checks carefully

A production workflow may also include:

  • Dependency vulnerability review
  • Secret scanning
  • Static analysis
  • License review
  • End-to-end tests
  • Deployment validation

A command such as npm audit can help identify known dependency advisories, but every finding requires investigation. Do not blindly apply all automated fixes to a production project without reviewing compatibility and breaking changes.

For production deployments, keep credentials in the CI platform's secret store and grant the job only the permissions it requires.

Topic 11

Production Debugging and Monitoring

See what real users experience — from the frontend to the release.

11.1 Why is production monitoring different from development debugging?

In development, you can directly inspect the application and reproduce a problem.

In production, a failure might happen on a user's phone, on an unusual browser version, under poor network conditions, or only with a specific sequence of actions.

Monitoring helps you understand what happened without accessing the user's computer directly.

It can include:

  • Frontend JavaScript errors
  • Backend errors
  • Failed HTTP requests
  • Response times
  • Application version and release information
  • Availability and health checks
  • Security-relevant events
  • Web Vitals and user experience metrics
Analogy · The control room
Operations watches the whole system at once. Monitoring connects the user's error to the release that caused it, the request that failed, and the backend metric that spiked — without ever opening the user's laptop.

11.2 Use a consistent release identifier

Suppose users report that the enrollment form stopped working immediately after a deployment.

Knowing the application release helps you correlate the error with the deployed code.

A release identifier might be based on a commit SHA or build number. Attach it to frontend error reports and correlate it with backend deployments when your monitoring system supports that integration.

Do not store private information in the release identifier.

11.3 Understand production source maps

Production JavaScript is often minified and transformed by the build process.

As a result, a stack trace may point to a compacted file and a confusing line number.

Source maps allow monitoring tools to relate generated code back to original source files. This can make production debugging substantially easier.

Source maps themselves need careful handling. They can reveal original source structure and may expose embedded source content, depending on the build configuration.

Choose whether to publish or privately upload source maps according to your application's security requirements, and restrict access to the monitoring system.

Reference: Sentry source maps and React monitoring.

11.4 Monitor frontend and backend errors together

A React application may display “Unable to load students,” but the cause could be:

  • A frontend exception
  • A network failure
  • An unavailable backend
  • A permission failure
  • Invalid data
  • An API contract change

The frontend monitoring event alone may not explain the root cause.

Correlate frontend and backend events using suitable request or correlation IDs, where available. Avoid using private personal information as a correlation identifier.

11.5 Safe production logging

A log message should give developers useful diagnostic information without exposing sensitive information.

Good examples might include:

  • Request failed with status code 500.
  • Feature: student-directory.
  • Release: deployment-2026-10-18.
  • Correlation ID: a non-sensitive request identifier.

Avoid recording:

  • Passwords
  • Session IDs
  • Access or refresh tokens
  • Full authorization headers
  • Unnecessary personally identifiable information
  • Sensitive request bodies

A monitoring platform should have appropriate permissions, retention limits, and redaction settings.

11.6 Establish practical alerting

For an LMS, alerts could focus on:

  • A spike in server errors
  • Increased failure rates for enrollment
  • Authentication service unavailability
  • Excessive response times
  • A rise in client-side errors after a release
  • A decline in availability

Avoid creating alerts for every individual error. Set thresholds around issues that affect users or important business workflows.

Monitoring dashboard — release correlation Output

ℹ Correlation
