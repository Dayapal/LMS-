Section 01

React Developer Tools

See what React actually rendered — component by component.

1.1 What is React Developer Tools?

React Developer Tools is a browser extension for inspecting applications built with React.

It adds two especially useful panels to your browser's developer tools:

  • Components: Inspect the React component tree and examine props, state, and context.
  • Profiler: Record rendering activity and investigate performance issues.

Official documentation: React Developer Tools.

1.2 Real-life example: A student profile shows the wrong name

Suppose you select a student from the list, but the profile panel still displays another student's name.

You could add console.log() statements throughout your application, but that may take a while.

Instead, inspect the component directly.

Analogy · 01
The detective's lens — before adding logs everywhere, look directly at the evidence. React Developer Tools is the magnifying glass for your component tree.

Steps

  1. Install the React Developer Tools browser extension for your browser.
  2. Open your LMS in development mode.
  3. Open browser developer tools.
  4. Open the Components panel.
  5. Find the student profile component in the tree.
  6. Inspect the props and state that it receives.

Imagine the component looks like this:

StudentProfile.tsxTSX
interface Student {
  id: string;
  name: string;
}

interface StudentProfileProps {
  student: Student | null;
}

function StudentProfile({ student }: StudentProfileProps) {
  if (!student) {
    return <p>Select a student</p>;
  }

  return <h2>{student.name}</h2>;
}

The component itself expects a student object or null.

If Developer Tools shows the wrong object being passed in, the bug may be in the parent component or in the selection logic rather than in the profile display.

That is a key debugging lesson: trace incorrect data back to where it originates.

1.3 Inspect props and state

Suppose the application has this counter:

StudentCounter.tsxTSX
import { useState } from "react";

function StudentCounter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((value) => value + 1)}>
      Students enrolled: {count}
    </button>
  );
}

Use the Components panel to inspect the component and its state.

Click the button and observe what changes. This can help you understand whether the application is receiving and updating state as expected.

Don't use the DevTools display as a substitute for application logic. It is an inspection aid, not the source of truth for your app.

1.4 What is the Profiler?

The React Profiler records rendering activity so you can investigate components that take time to render or render more frequently than expected.

Imagine a dashboard with 500 student rows. Whenever you select one row, the entire list seems to become slow.

A systematic approach is:

  1. Open the Profiler panel.
  2. Start recording.
  3. Select a student or apply a filter.
  4. Stop the recording.
  5. Inspect the commits and components involved.
  6. Identify expensive rendering work before deciding whether to optimize it.

You might discover that every row recalculates an expensive value or that a parent recreates props on each render.

You can then consider optimizations such as simpler calculations, more localized state, or memoization where it provides a measurable benefit.

Do not assume every render is a problem. Small components often render quickly, and optimization should be based on evidence.

When should you use React Developer Tools?

Use it when:

  • The wrong props or state seem to be reaching a component.
  • A component does not display the updated state you expect.
  • You want to understand the React component tree.
  • You need to investigate rendering performance.
  • You want to understand which part of the UI is responsible for an issue.

Section 02

Browser Debugging and Network Inspection

Console, breakpoints, and the truth about what the network returned.

React Developer Tools helps you investigate React-specific behavior. Browser DevTools gives you additional tools for diagnosing JavaScript, DOM, styling, and network problems.

2.1 The Console panel

Imagine your student dashboard shows a blank screen.

Open Chrome DevTools and select Console.

You might see an error such as:

Console
TypeError: Cannot read properties of undefined (reading 'name')

This suggests the code attempted to access .name on a value that was undefined.

For example:

StudentName.tsxTSX
function StudentName({ student }: { student: Student }) {
  return <h2>{student.name}</h2>;
}

This component expects a valid student object. If the parent passes data that does not satisfy that expectation, the render may fail.

If the student is legitimately optional, model that correctly:

StudentName.tsxTSX
function StudentName({
  student,
}: {
  student: Student | null;
}) {
  if (!student) {
    return <p>No student selected</p>;
  }

  return <h2>{student.name}</h2>;
}

Notice that this fixes the underlying state requirement rather than simply hiding the error.

Analogy · 02
The network is a physical system — requests travel through wires, servers, and gates. When something is stuck on “Loading…”, the Network panel lets you follow the wire.

2.2 Use console.log() intelligently

For quick debugging:

loggingTSX
function selectStudent(studentId: string) {
  console.log("Selected student:", studentId);
  setSelectedStudentId(studentId);
}

You can also inspect objects:

log objectTSX
console.log({
  selectedStudentId,
  filteredStudents,
});

Useful console methods include:

console methodsJS
console.log("General information");
console.warn("Unexpected condition");
console.error("Request failed");
console.table(students);

Use logging temporarily and remove noisy debugging statements before merging production code.

For problems that occur only under certain conditions, a breakpoint is often more effective.

2.3 Breakpoints and step-by-step debugging

A breakpoint pauses JavaScript execution so you can inspect values at the point where something happens.

Real-life example: clicking Enroll Student sends the wrong course ID to the backend.

You can:

  1. Open the Sources panel.
  2. Find the event-handler code.
  3. Click a line number to set a breakpoint.
  4. Submit the enrollment form.
  5. Inspect the values of studentId and courseId.
  6. Step through the function to understand where the wrong value is introduced.

This is especially useful when a problem is difficult to reproduce through logs alone.

2.4 The Network panel

Imagine the course list remains stuck on “Loading courses...”.

The Network panel helps answer questions such as:

  • Did the browser send the request?
  • Which URL was requested?
  • What HTTP status was returned?
  • What data did the server return?
  • Did the request take too long?
  • Was the request blocked or cancelled?

Open DevTools, select Network, and reload the page while recording is enabled.

Click the request of interest and inspect its Headers, Payload, Response, and Timing information.

Official guide: Inspect network activity in Chrome DevTools.

2.5 Understanding common API problems

Suppose your code calls:

fetchTSX
const response = await fetch("/api/students");
const students = await response.json();

A request can fail in several different ways.

ObservationPossible problem
No request appearsThe code path may not run, or the URL may never be requested
404The requested endpoint was not found
401 or 403Authentication or authorization may be required
500The server reported an internal error
CORS errorThe browser rejected the cross-origin request under its CORS rules
Response is not valid JSONThe frontend may be calling the wrong endpoint or receiving an unexpected response
Request is very slowThe network, server, or request processing may be slow

These are diagnostic clues, not definitive explanations. Inspect the response and application logic before deciding what caused the issue.

Also remember that fetch() does not automatically reject its Promise just because the server returns an HTTP error status such as 404. Check response.ok.

getStudents.tsTS
async function getStudents(): Promise<Student[]> {
  const response = await fetch("/api/students");

  if (!response.ok) {
    throw new Error(
      `Could not load students: ${response.status}`
    );
  }

  return response.json() as Promise<Student[]>;
}

This snippet illustrates HTTP error handling, but the type assertion does not validate the real response body. Validate untrusted server data before treating it as Student[].

2.6 A practical debugging workflow

When a bug appears, ask these questions in order:

  1. Reproduce: What exact steps cause the bug?
  2. Observe: Is there an error in the Console, Elements, React Components, or Network panel?
  3. Locate: Which component, event handler, or request is involved?
  4. Inspect: Which values are incorrect?
  5. Fix: Correct the underlying logic.
  6. Verify: Repeat the original steps and test nearby behavior.
  7. Prevent regression: Add a test for the bug.

This workflow is more reliable than making random changes until the problem disappears.

Section 03

React Testing Library

Test the page the user sees — not the state the user can't.

3.1 What is React Testing Library?

React Testing Library helps you test React components through their rendered DOM.

Its guiding principle is that tests should resemble how users interact with the application.

For instance, instead of checking whether a component's internal state variable equals "Aarav", test whether the rendered page displays the student's name after the user selects that student.

Official documentation: React Testing Library.

3.2 Install the testing packages

In an existing React + TypeScript + Vite project, install these development dependencies:

terminalBash
npm install -D vitest jsdom @testing-library/react @testing-library/dom @testing-library/user-event @testing-library/jest-dom

The packages serve different roles:

  • vitest runs the tests.
  • jsdom provides a simulated browser DOM for component tests.
  • @testing-library/react renders and queries React components.
  • @testing-library/user-event simulates user interactions.
  • @testing-library/jest-dom adds readable DOM assertions such as toBeInTheDocument().

3.3 Understand the basic structure of a test

A test commonly follows the Arrange, Act, Assert pattern.

  • Arrange: Set up the component and inputs.
  • Act: Perform a user action.
  • Assert: Check the expected result.

Imagine you want to verify that clicking the counter button adds one student.

Create Counter.tsx:

Counter.tsxTSX
import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <section>
      <p>Enrolled students: {count}</p>

      <button
        type="button"
        onClick={() => setCount((value) => value + 1)}
      >
        Add student
      </button>
    </section>
  );
}

Now write Counter.test.tsx:

Counter.test.tsxTSX
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, it } from "vitest";
import Counter from "./Counter";

it("increments the student count when clicked", async () => {
  const user = userEvent.setup();

  render(<Counter />);

  expect(
    screen.getByText("Enrolled students: 0")
  ).toBeInTheDocument();

  await user.click(
    screen.getByRole("button", { name: /add student/i })
  );

  expect(
    screen.getByText("Enrolled students: 1")
  ).toBeInTheDocument();
});

Understand the test

renderTSX
render(<Counter />);

This renders the component into the test DOM.

queryTSX
screen.getByRole("button", { name: /add student/i });

This finds the button the way an assistive technology user would identify it: through its role and accessible name.

clickTSX
await user.click(...);

This simulates clicking the button.

assertTSX
expect(...).toBeInTheDocument();

This verifies the visible result.

The test does not inspect the component's state directly. It verifies its behavior from the user's perspective.

Analogy · 03
The quality-control checklist — a test suite is a checklist for behavior. You check what a user can see and do, not the private machinery behind it.

3.4 Learn the main query methods

Testing Library offers several ways to locate elements.

QueryWhen to use it
getByRoleAn element should already be present
getByLabelTextFind a form field through its label
getByTextFind visible text when a role query is not suitable
queryByRoleCheck that something is absent
findByRoleWait for an element to appear asynchronously
getByTestIdUse as a fallback when suitable user-facing queries are impractical

The recommended preference is usually a semantic query such as getByRole or getByLabelText. These queries often help uncover missing labels and accessibility problems.

For asynchronous UI:

findByRoleTSX
expect(
  await screen.findByRole("heading", {
    name: /student dashboard/i,
  })
).toBeInTheDocument();

findByRole waits for the element to appear within the configured timeout.

To verify that a dialog is absent:

queryByRoleTSX
expect(
  screen.queryByRole("dialog")
).not.toBeInTheDocument();

Do not use getByRole when your intention is to check absence, because getByRole throws when it cannot find the element.

3.5 What should you test?

For a student card, useful tests include:

  • The student's name is visible.
  • The course name is visible.
  • Clicking the card triggers the appropriate interaction.
  • A disabled action cannot be activated normally.
  • Missing optional information is displayed appropriately.

Avoid testing implementation details that users cannot observe unless there is a specific reason.

Testing Library guidance: About queries.

Vitest and Test Configuration

The runner, the environment, and the setup that makes tests reliable.

4.1 What is Vitest?

Vitest is a testing framework designed to work with Vite. It supplies a test runner, assertions, mocking utilities, and related testing features.

For a Vite-based React application, Vitest is a natural starting point for unit and component tests.

Official documentation: Vitest getting started.

4.2 Configure Vitest for React

A normal React + TypeScript Vite application already has a vite.config.ts file.

Update it to include the Vitest configuration:

vite.config.tsTS
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],

  test: {
    environment: "jsdom",
    setupFiles: "./src/test/setup.ts",
    clearMocks: true,
  },
});

If your existing configuration contains other plugins or settings, keep them and add the relevant test options.

Why jsdom?

By default, Vitest runs tests in a Node.js environment. React component tests often need browser-like APIs such as document, window, and DOM elements. jsdom simulates many of those APIs.

It is not a full browser, so browser-specific behavior should also be tested in a real browser when necessary.

Reference: Vitest test environment.

4.3 Configure test setup

Create src/test/setup.ts:

src/test/setup.tsTS
import "@testing-library/jest-dom/vitest";

import { cleanup } from "@testing-library/react";
import { afterEach, vi } from "vitest";

afterEach(() => {
  cleanup();
  vi.unstubAllGlobals();
});

This setup:

  • Enables DOM assertions from jest-dom for Vitest.
  • Cleans up rendered React components between tests.
  • Restores stubbed global objects, such as a mock fetch.

Importing @testing-library/jest-dom/vitest is important when using Vitest rather than assuming the standard Jest entry point is appropriate.

4.4 Add scripts to package.json

Preserve your existing Vite scripts and add these:

package.jsonJSON
{
  "scripts": {
    "test": "vitest",
    "test:run": "vitest run"
  }
}

Run the tests in watch mode:

terminalBash
npm run test

Run the suite once:

terminalBash
npm run test:run

Watch mode is useful during development because tests can rerun as you change your code.

Also check that your Node.js and Vite versions are compatible with the version of Vitest you install. Current setup requirements can change as these tools evolve.

4.5 What is a test file?

Vitest normally discovers files using conventional names such as:

Test files
Counter.test.tsx
StudentForm.test.tsx
StudentDirectory.test.tsx

A useful folder arrangement is:

src/ ├── components/ │ ├── Counter.tsx │ ├── Counter.test.tsx │ ├── StudentForm.tsx │ └── StudentForm.test.tsx ├── test/ │ └── setup.ts └── App.tsx

You can also keep tests in a dedicated tests or __tests__ directory if that better suits the project.

4.6 Unit tests versus component tests

A unit test typically tests a small function or piece of logic.

formatStudentName.tsTS
export function formatStudentName(name: string): string {
  return name.trim().replace(/\s+/g, " ");
}

Test it:

formatStudentName.test.tsTS
import { expect, it } from "vitest";
import { formatStudentName } from "./formatStudentName";

it("removes extra spaces from a name", () => {
  expect(formatStudentName("  Aarav   Patel ")).toBe(
    "Aarav Patel"
  );
});

A component test renders React UI and checks how it behaves.

The counter and form tests in this phase are examples of component tests.

Both matter: unit tests are useful for business logic, while component tests verify that the logic works correctly with the rendered interface.

Testing Rendering and User Interactions

What the user sees first — and what happens after they act.

Imagine a trainer dashboard containing a button to toggle whether a course is visible to students.

The test should verify both the initial appearance and the outcome of the interaction.

5.1 Create the component

CourseVisibility.tsx:

CourseVisibility.tsxTSX
import { useState } from "react";

export default function CourseVisibility() {
  const [visible, setVisible] = useState(false);

  return (
    <section>
      <p>
        Course availability: {visible ? "Published" : "Draft"}
      </p>

      <button
        type="button"
        aria-pressed={visible}
        onClick={() => setVisible((value) => !value)}
      >
        {visible ? "Unpublish Course" : "Publish Course"}
      </button>
    </section>
  );
}

The component exposes the toggle state through readable text and aria-pressed.

5.2 Write the test

CourseVisibility.test.tsx:

CourseVisibility.test.tsxTSX
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, it } from "vitest";

import CourseVisibility from "./CourseVisibility";

it("publishes and unpublishes a course", async () => {
  const user = userEvent.setup();

  render();

  const button = screen.getByRole("button", {
    name: /publish course/i,
  });

  expect(button).toHaveAttribute("aria-pressed", "false");
  expect(screen.getByText(/availability: draft/i))
    .toBeInTheDocument();

  await user.click(button);

  expect(screen.getByRole("button", {
    name: /unpublish course/i,
  })).toHaveAttribute("aria-pressed", "true");

  expect(screen.getByText(/availability: published/i))
    .toBeInTheDocument();
});

The test verifies behavior rather than checking that useState was called or that the state variable has a particular internal value.

5.3 Why use user-event?

user-event models browser interactions at a higher level than manually dispatching a single DOM event.

For example, entering text can involve focus, keyboard events, and input changes. Using user-event helps tests exercise these interactions through the user-facing interface.

Prefer:

user-eventTSX
const user = userEvent.setup();

await user.click(
  screen.getByRole("button", { name: /publish course/i })
);

over directly calling an internal handler.

5.4 Test a component's initial state

Suppose a modal should be closed initially. You can verify that:

modalTSX
expect(screen.queryByRole("dialog")).not.toBeInTheDocument();

Then click its opener and check that the dialog appears.

For a dropdown, you might test that options only appear after the user opens the menu.

For pagination, verify that clicking Next changes the visible records.

For a navigation component, verify that its links and accessible names are correct.

Practical rule

Write tests based on meaningful behavior, not on the number of component renders. Rendering counts can change when implementation details change, even if the user-facing behavior remains correct.

6.2 Test validation

StudentForm.test.tsx:

StudentForm.test.tsxTSX
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, it, vi } from "vitest";

import StudentForm from "./StudentForm";

it("shows a validation error for an empty name", async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();

  render();

  await user.click(
    screen.getByRole("button", { name: /add student/i })
  );

  expect(screen.getByRole("alert"))
    .toHaveTextContent("Enter a student name.");

  expect(onSubmit).not.toHaveBeenCalled();
});

The test confirms two important behaviors:

  1. The user sees a validation message.
  2. The invalid data is not submitted.

6.3 Test successful submission

Add another test:

success testTSX
it("submits the student's trimmed name and selected course", async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();

  render();

  await user.type(
    screen.getByRole("textbox", { name: /student name/i }),
    "  Aarav Patel  "
  );

  await user.selectOptions(
    screen.getByRole("combobox", { name: /course/i }),
    "Full Stack"
  );

  await user.click(
    screen.getByRole("button", { name: /add student/i })
  );

  expect(onSubmit).toHaveBeenCalledWith({
    name: "Aarav Patel",
    course: "Full Stack",
  });
});

This verifies the real result of the user's interaction, including whitespace trimming.

6.4 What else should you test in a form?

For a professional LMS or workshop platform, useful cases include:

  • Required fields
  • Invalid email addresses
  • Minimum and maximum lengths
  • Invalid course selections
  • Submitting with Enter
  • Clear error messages
  • Disabled submission while a request is pending
  • Success messages
  • API errors
  • Duplicate submissions
  • Keyboard navigation and visible focus

Not every validation case requires a separate test if cases can be grouped clearly, but the key rules of a form should be explicitly verified.

▲ Important

Frontend validation improves user experience. The backend must still validate the submitted data and enforce authorization.

Mocking API Calls

A controlled substitute for the network — so tests are predictable.

7.1 What is mocking?

Mocking means replacing a dependency with a controlled substitute during a test.

Imagine your dashboard retrieves hundreds of students from an API. You don't want every component test to depend on an internet connection, a running backend, or production data.

You can mock the API response and provide known data.

This gives you predictable tests for success, empty responses, delays, and failures.

7.2 Create a student API service

studentsApi.ts:

studentsApi.tsTS
export interface Student {
  id: string;
  name: string;
  course: string;
}

function isRecord(
  value: unknown
): value is Record {
  return (
    typeof value === "object" &&
    value !== null &&
    !Array.isArray(value)
  );
}

function isStudent(value: unknown): value is Student {
  return (
    isRecord(value) &&
    typeof value.id === "string" &&
    typeof value.name === "string" &&
    typeof value.course === "string"
  );
}

export async function fetchStudents(): Promise {
  const response = await fetch("/api/students");

  if (!response.ok) {
    throw new Error("Could not load students.");
  }

  const payload: unknown = await response.json();

  if (!Array.isArray(payload) || !payload.every(isStudent)) {
    throw new Error("The server returned invalid student data.");
  }

  return payload;
}

The function verifies the HTTP status and checks that the received value matches the expected student structure.

In a real project, the validator should reflect the actual API contract, including any nested objects and business constraints.

7.3 Mock a fetch response

Imagine you want to verify that the API service can return a list of students.

A mocked response can be created like this:

studentsApi.test.tsTSX
import { expect, it, vi } from "vitest";
import { fetchStudents } from "./studentsApi";

it("returns students from the API", async () => {
  const students = [
    {
      id: "STU-101",
      name: "Aarav Patel",
      course: "React",
    },
  ];

  const mockFetch = vi.fn().mockResolvedValue({
    ok: true,
    json: async () => students,
  });

  vi.stubGlobal("fetch", mockFetch);

  await expect(fetchStudents()).resolves.toEqual(students);
  expect(mockFetch).toHaveBeenCalledWith("/api/students");
});

This test does not contact the actual backend. It replaces fetch with a function that returns a predetermined response.

The object is a lightweight test double for the subset of the Fetch API used by this service. More complex code that uses additional Response behavior may require a fuller mock.

Because fetch is a global, restore the stub after the test with vi.unstubAllGlobals() or the test cleanup mechanism configured for your project.

7.4 Test API failures

failure testTSX
it("throws when the server returns an unsuccessful status", async () => {
  vi.stubGlobal(
    "fetch",
    vi.fn().mockResolvedValue({
      ok: false,
      status: 500,
      json: async () => ({}),
    })
  );

  await expect(fetchStudents()).rejects.toThrow(
    "Could not load students."
  );
});

This verifies how the service handles an HTTP failure.

It is different from a network failure, in which the fetch Promise rejects. You should test both when both cases matter.

7.5 When should you mock API requests?

Mocks are useful when testing:

  • An API service's handling of responses
  • A component's rendering after a known API result
  • Loading indicators
  • Error messages
  • Empty responses
  • Unusual or invalid data
  • Slow requests
  • Rare failure conditions

Do not mock away the actual behavior you want to test. If your goal is to verify that the frontend and backend are correctly integrated, you will also need integration or end-to-end tests that exercise more of the real system.

8.3 Test the loading state

A loading test needs to keep the request pending long enough for you to inspect that state.

loading testTSX
import { act, render, screen } from "@testing-library/react";

it("shows a loading message while the request is pending", async () => {
  let resolveResponse!: (value: {
    ok: boolean;
    json: () => Promise;
  }) => void;

  const pendingResponse = new Promise<{
    ok: boolean;
    json: () => Promise;
  }>((resolve) => {
    resolveResponse = resolve;
  });

  vi.stubGlobal("fetch", vi.fn(() => pendingResponse));

  render();

  expect(screen.getByRole("status"))
    .toHaveTextContent("Loading students...");

  await act(async () => {
    resolveResponse({
      ok: true,
      json: async () => [],
    });
  });

  expect(await screen.findByText("No students found."))
    .toBeInTheDocument();
});

This snippet uses a simplified response object shaped around the behavior required by this component. If your service directly uses additional Response methods, adapt the test double accordingly.

The test checks the intermediate loading state and then verifies the result after resolving the request.

8.4 Test the error state

error testTSX
it("displays an error when the server fails", async () => {
  vi.stubGlobal(
    "fetch",
    vi.fn().mockResolvedValue({
      ok: false,
      status: 500,
      json: async () => ({}),
    })
  );

  render();

  expect(await screen.findByRole("alert"))
    .toHaveTextContent("Could not load students.");
});

Here, the API service throws an error because the HTTP response is unsuccessful. The directory catches it and renders an alert.

8.5 What else should you test?

For a reliable API-driven UI, consider:

  • A successful request
  • An empty result
  • A non-success HTTP status
  • A network failure
  • Malformed response data
  • A delayed response
  • A component unmounting before a request completes
  • A retry action, if the interface supports retries

Testing all these conditions is especially valuable when users rely on the data for enrollment, billing, attendance, or administration.

◆ Remember

A component that works when the API succeeds is not necessarily a robust component.

Testing Custom Hooks

Testing behavior that lives between components — with control over time.

Custom Hooks allow you to reuse behavior across React components.

Examples include:

  • useDebouncedValue
  • useLocalStorage
  • useOnlineStatus
  • useWindowSize
  • useStudentSearch

Testing the Hook independently can be useful when its behavior is complex or shared across multiple components.

9.1 Create a realistic Hook: useDebouncedValue

Imagine a student search box that queries a large student database. You don't want the search logic to run immediately for every keystroke; instead, you may want to wait until the user has stopped typing for a short time.

Create useDebouncedValue.ts:

useDebouncedValue.tsTS
import { useEffect, useState } from "react";

export function useDebouncedValue(
  value: T,
  delayMs = 300
): T {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timerId = window.setTimeout(() => {
      setDebouncedValue(value);
    }, delayMs);

    return () => {
      window.clearTimeout(timerId);
    };
  }, [value, delayMs]);

  return debouncedValue;
}

The Hook returns the latest value after the delay has passed without a newer value resetting the timer.

It is useful for debouncing a value, but it does not itself perform an API request or cache the results.

9.2 Test the Hook with renderHook

React Testing Library provides renderHook for rendering a Hook inside an appropriate test component.

Create useDebouncedValue.test.ts:

useDebouncedValue.test.tsTSX
import { act, renderHook } from "@testing-library/react";
import { afterEach, expect, it, vi } from "vitest";

import { useDebouncedValue } from "./useDebouncedValue";

afterEach(() => {
  vi.useRealTimers();
});

it("updates only after the delay has passed", () => {
  vi.useFakeTimers();

  const { result, rerender } = renderHook(
    ({ value }) => useDebouncedValue(value, 300),
    {
      initialProps: { value: "aar" },
    }
  );

  expect(result.current).toBe("aar");

  rerender({ value: "aara" });

  expect(result.current).toBe("aar");

  act(() => {
    vi.advanceTimersByTime(300);
  });

  expect(result.current).toBe("aara");
});

How the test works

Step 1: Fake timers allow the test to control the passage of time.

Step 2: renderHook initializes the Hook with "aar".

Step 3: rerender provides "aara" as the new input value.

Step 4: Before 300 milliseconds have passed, the Hook still returns the earlier debounced value.

Step 5: Advancing the fake timer allows the pending timeout callback to run. act() makes sure React processes the resulting update before the assertion.

9.3 Test timer cleanup

The cleanup function is just as important as the value update.

If the value changes several times, previous timers should be cancelled so that only the latest value is returned after the delay.

You can extend the test by updating the input several times and verifying that advancing the clock by less than the full delay does not reveal an earlier, intermediate value.

9.4 Should you test every custom Hook independently?

Not necessarily.

A tiny Hook may be adequately tested through a component that uses it. A shared or complicated Hook often benefits from its own focused tests.

Choose the test style that makes the behavior easiest to understand and maintain.

End-to-End Testing with Playwright or Cypress

The whole workflow, in a real browser, with real clicks.

Unit and component tests are helpful, but they do not verify the entire application in the same way a real user experiences it.

End-to-end (E2E) tests run through important workflows in a real browser and check that multiple parts of the system work together.

Imagine a user opening your institute LMS, navigating to the enrollment page, adding a student, and verifying the student's entry in the list.

An E2E test can check that flow across the rendered application.

Analogy · 04
The theatre of the browser — an E2E test is a full performance: real props, real stage, real audience. Playwright and Cypress put your application on stage in a real browser.

10.1 What is Playwright?

Playwright is an end-to-end testing framework with browser automation, assertions, browser isolation, and other testing capabilities.

It supports Chromium, Firefox, and WebKit. Its web-first assertions can retry until the expected UI condition is met or the timeout is reached.

Official documentation:

  • Playwright introduction
  • Playwright assertions

10.2 Install Playwright

From your application project directory:

terminalBash
npm init playwright@latest

Follow the prompts to configure end-to-end testing and install the desired browser dependencies.

The setup may create a playwright.config.ts file and an example test directory.

10.3 Configure the development server

For a Vite application, an illustrative playwright.config.ts is:

playwright.config.tsTS
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",

  use: {
    baseURL: "http://127.0.0.1:5173",
    trace: "on-first-retry",
  },

  projects: [
    {
      name: "chromium",
      use: { ...devices["Desktop Chrome"] },
    },
  ],

  webServer: {
    command: "npm run dev -- --host 127.0.0.1",
    url: "http://127.0.0.1:5173",
    reuseExistingServer: !process.env.CI,
  },
});

This configuration launches the Vite development server when needed and points Playwright at the local application.

Adapt it if your app runs on a different port or if your tests need a separate backend process.

10.4 Write an E2E test for student enrollment

Imagine your real application has a page with a student enrollment form. The form provides a textbox labeled Student name, a course selector, and an Add Student button.

Create e2e/student-enrollment.spec.ts:

e2e/student-enrollment.spec.tsTS
import { test, expect } from "@playwright/test";

test("an administrator can add a student", async ({ page }) => {
  await page.goto("/");

  await page.getByLabel("Student name").fill("Aarav Patel");

  await page.getByLabel("Course").selectOption("React");

  await page.getByRole("button", {
    name: /add student/i,

  await expect(
    page.getByText("Aarav Patel")
  ).toBeVisible();

  await expect(
    page.getByText("React", { exact: true })
  ).toBeVisible();
});

This is an example of the intended test flow. It assumes your application has matching labels and behavior.

fillTS

Finds the field through its accessible label and enters text.

selectOptionTS

Unlike a component test, this exercise includes the actual browser and the running application.

10.5 Mock network requests in Playwright

Playwright can intercept network traffic. This is useful when an E2E test needs a deterministic API response rather than depending on a separate backend service.

mock networkTS
import { test, expect } from "@playwright/test";

test("shows students returned by the API", async ({ page }) => {
  await page.route("**/api/students", async (route) => {
    await route.fulfill({
      status: 200,
      contentType: "application/json",
      body: JSON.stringify([
        {
          id: "STU-101",
          name: "Aarav Patel",
          course: "React",
        },
      ]),
    });
  });

  await page.goto("/");

  await expect(
    page.getByText("Aarav Patel")
  ).toBeVisible();
});

The test intercepts requests to /api/students and returns the specified JSON data.

This is still an end-to-end test of the frontend workflow in a real browser, but the backend response is mocked. For full-stack integration testing, include separate tests against a real test backend where appropriate.

Network documentation: Playwright network mocking.

10.6 What about Cypress?

Cypress is an alternative browser-testing tool.

It supports end-to-end tests and component testing. Cypress Component Testing mounts components directly in a real browser and provides tools for inspecting and interacting with them.

Official documentation: Cypress React Component Testing.

A component test might look like this:

CypressTSX
import { StudentForm } from "./StudentForm";

it("renders the student form", () => {
  cy.mount();

  cy.get("input").should("be.visible");
});

This assumes the StudentForm component exports a named StudentForm function. In your project, adapt the import to the actual export.

Cypress commands such as cy.mount() are configured through Cypress's component testing setup; this snippet is not a Vitest test.

10.7 Playwright or Cypress: which should you choose?

Both are capable tools. You do not need to adopt both at the beginning.

Choose a primary tool based on your application's requirements, your team's experience, integration support, and the workflows you need to automate.

For this learning phase, the main E2E examples use Playwright.

Use it to automate critical workflows such as login, enrollment, search, editing records, and submitting forms. Use React Testing Library and Vitest for faster feedback on individual components.

Section 11

Accessibility Checks and Regression Testing

Making sure real people can use the app — and that today's fix stays fixed.

Testing is not complete merely because a component renders without an error.

A page can appear correct while missing form labels, using inaccessible controls, or breaking an important workflow after a code change.

This topic combines accessibility testing with regression testing.

Analogy · 05
The keyboard-only path — many users never touch a mouse. Accessibility tests verify that the same workflow works with only a keyboard and an accessible name.

11.1 What is accessibility testing?

Accessibility testing checks whether people with different abilities can use an application, including people who rely on keyboards or assistive technology.

For an LMS, you should investigate questions such as:

  • Can the user navigate the interface without a mouse?
  • Are inputs associated with labels?
  • Do buttons have understandable names?
  • Are validation errors announced appropriately?
  • Can the user see keyboard focus?
  • Do dialogs manage focus correctly?
  • Is text readable against its background?

React Testing Library helps by encouraging queries that use accessible roles and labels. It does not guarantee that a full page is accessible, so automated checks and manual testing remain important.

11.2 Prefer accessible queries in tests

For example, this form has a correctly associated label:

labelTSX
<label htmlFor="email">Email address</label>
<input id="email" type="email" />

A test can find it through the label:

getByRoleTSX
screen.getByRole("textbox", {
  name: /email address/i,
});

A properly labeled button can be located through its role and accessible name.

button queryTSX
screen.getByRole("button", {
  name: /save student/i,
});

These queries can uncover a missing accessible name. If you cannot locate an element in the way a user or assistive technology would, the underlying markup may need improvement.

11.3 Automated accessibility checks with Playwright

You can add an accessibility scanner to your browser tests.

Install the Playwright integration for axe-core:

terminalBash
npm install -D @axe-core/playwright

Create an accessibility test:

accessibility.spec.tsTS
import AxeBuilder from "@axe-core/playwright";
import { test, expect } from "@playwright/test";

test("student dashboard has no detected accessibility violations", async ({ page }) => {
  await page.goto("/");

  const results = await new AxeBuilder({ page }).analyze();

  expect(results.violations).toEqual([]);
});

This runs a set of automated accessibility rules against the loaded page.

Automated tools can detect many issues, but they do not prove that a page is fully accessible. Manual keyboard checks, focus testing, and assistive-technology testing remain important.

11.4 What is regression testing?

Regression testing verifies that previously working behavior still works after code changes.

Real-life example: you update the styling and validation logic for the enrollment form. The form now looks better, but accidentally stops submitting selected courses.

A regression test catches the problem.

Your test suite might include:

  • The student list renders.
  • Searching finds the correct student.
  • Enrollment rejects an empty name.
  • Enrollment submits the correct data.
  • API errors display a helpful message.
  • Course visibility can be toggled.
  • The dashboard loads at common viewport widths.

The purpose is not to prove that every possible input works. It is to protect important behavior from accidental changes.

11.5 Regression tests for a critical workflow

Suppose your dashboard filters students by course.

A simple component test may verify that selecting React displays only React students.

filter testTSX
it("filters the student list by course", async () => {
  const user = userEvent.setup();

  render(
    <StudentDirectoryWithFilter
      students={[
        { id: "1", name: "Aarav", course: "React" },
        { id: "2", name: "Diya", course: "Data Analytics" },
      ]}
    />
  );

  await user.selectOptions(
    screen.getByRole("combobox", { name: /course/i }),
    "React"
  );

  expect(screen.getByText("Aarav")).toBeInTheDocument();
  expect(screen.queryByText("Diya")).not.toBeInTheDocument();
});

This example assumes StudentDirectoryWithFilter accepts a students prop and includes a course selector labeled "Course". Adjust the test to the actual component contract in your project.

Once added, it can help catch future changes that accidentally break filtering.

11.6 Visual regression testing

Visual regression tests compare screenshots to check for unintended changes in appearance.

For example, after changing Tailwind styles, a dashboard card may become too narrow or a button may overflow on mobile.

Playwright can compare screenshots against approved baseline images:

screenshot assertionTS
await expect(page).toHaveScreenshot("student-dashboard.png");

This is an illustrative assertion for a configured Playwright screenshot test. You must generate and review the baseline first.

Visual tests work best when the test environment is stable. Dynamic dates, animations, random content, and network timing can produce screenshot differences unrelated to a genuine defect.

Visual regression tests complement functional tests; they do not replace them.

Common testing mistakes to avoid

Fourteen pitfalls that make tests fragile, slow, or misleading.

  1. Testing a component's internal state instead of its observable behavior.
  2. Using arbitrary CSS selectors when an accessible role or label is available.
  3. Testing only the successful API response.
  4. Using fixed delays such as setTimeout in tests when a proper async query or controlled promise would be more reliable.
  5. Forgetting to restore mocks and clean up rendered components.
  6. Using real production data or an unreliable external API in every component test.
  7. Believing a mocked frontend request proves the backend works correctly.
  8. Assuming TypeScript types guarantee that server data is valid.
  9. Using getByRole for an element that should not exist.
  10. Writing E2E tests for every tiny implementation detail instead of focusing on important user journeys.
  11. Ignoring keyboard navigation and accessible labels.
  12. Relying on screenshot tests alone to catch functional problems.
  13. Skipping tests after fixing a production bug.
  14. Trying to achieve a high test coverage percentage without checking whether important behavior is actually tested.
