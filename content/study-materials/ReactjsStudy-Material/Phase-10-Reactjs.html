Section 08

Typing API Responses

The type system is a promise. The network is the wild. Only one of them can be trusted.

Typing API data is particularly important because a React component often receives information from a backend service.

Imagine your CRM fetches student records from an Express API. The frontend expects the response to contain a student's id, name, and course.

TypeScript can describe the expected structure. However, a TypeScript type does not validate the JSON returned by the server at runtime.

This distinction is critical.

▲ Trust boundary

API responses are runtime data. TypeScript can prove what your code does. It cannot prove what the server sent. That is why validation belongs at the boundary where the data enters your application[reference:6].

8.1 Define an API data type

Create types/student.ts:

types/student.tsTS
export interface Student {
  id: string;
  name: string;
  email: string;
  course: string;
}

Then define the state:

stateTSX
const [students, setStudents] = useState<Student[]>([]);

This tells TypeScript what the frontend expects to manage.

But it does not prove that an API response actually contains valid Student objects.

8.2 A simple API request with typed data

fetchStudents.tsTS
async function fetchStudents(): Promise<Student[]> {
  const response = await fetch("/api/students");

  if (!response.ok) {
    throw new Error("Failed to fetch students");
  }

  return (await response.json()) as Student[];
}

This demonstrates the function signature and the success check. However, the as Student[] assertion only tells TypeScript to trust the programmer. It does not inspect the actual response.

If the backend sends malformed data, this function can still return data that does not match Student[] at runtime.

For production-quality code, consider validating untrusted API data.

8.3 Safely validating unknown API data

Start with a type guard:

type guardsTS
interface Student {
  id: string;
  name: string;
  email: string;
  course: string;
}

function isRecord(value: unknown): value is Record<string, unknown> {
  return (
    typeof value === "object" &&
    value !== null &&
    !Array.isArray(value)
  );
}

function isStudent(value: unknown): value is Student {
  return (
    isRecord(value) &&
    typeof value.id === "string" &&
    typeof value.name === "string" &&
    typeof value.email === "string" &&
    typeof value.course === "string"
  );
}

The guard checks the actual properties before treating the value as a Student.

Now validate the array:

validated fetchTS
async function fetchStudents(): Promise<Student[]> {
  const response = await fetch("/api/students");

  if (!response.ok) {
    throw new Error(`Student request failed: ${response.status}`);
  }

  const payload: unknown = await response.json();

  if (!Array.isArray(payload) || !payload.every(isStudent)) {
    throw new Error("Invalid student response");
  }

  return payload;
}

This is safer than blindly asserting the response type.

The type guard validates the fields defined in the example. A production validator may need to check nested objects, optional fields, dates, numeric constraints, and business rules.

8.4 Display API loading, success, and error states

StudentPage.tsxTSX
import { useEffect, useState } from "react";

type StudentState =
  | { status: "loading" }
  | { status: "success"; data: Student[] }
  | { status: "error"; message: string };

function StudentPage() {
  const [state, setState] = useState<StudentState>({
    status: "loading",
  });

  useEffect(() => {
    let ignore = false;

    async function loadStudents() {
      try {
        const data = await fetchStudents();

        if (!ignore) {
          setState({ status: "success", data });
        }
      } catch (error: unknown) {
        if (!ignore) {
          setState({
            status: "error",
            message:
              error instanceof Error
                ? error.message
                : "An unexpected error occurred",
          });
        }
      }
    }

    loadStudents();

    return () => {
      ignore = true;
    };
  }, []);

  if (state.status === "loading") {
    return <p>Loading students...</p>;
  }

  if (state.status === "error") {
    return <p role="alert">{state.message}</p>;
  }

  return (
    <ul>
      {state.data.map((student) => (
        <li key={student.id}>
          {student.name} — {student.course}
        </li>
      ))}
    </ul>
  );
}

This demonstrates typed request states, response data, and error handling.

For production applications, a data-fetching library such as TanStack Query or RTK Query may be a better choice than manually coordinating request state and effects. The types of the returned data should still be grounded in validation or a trustworthy API contract.

8.5 Typing error values correctly

In strict TypeScript, catch variables are commonly typed as unknown.

That is helpful because not every thrown value is guaranteed to be an Error object.

Use a check before accessing .message:

catchTS
catch (error: unknown) {
  if (error instanceof Error) {
    console.error(error.message);
  } else {
    console.error("Unknown error");
  }
}

TechniqueWhat it does
interface StudentDescribes the expected structure at development time

Runtime validation libraryValidates input against a declared schema

Type the API contract, validate untrusted data, and handle request failures separately.

Section 09

Typing Context and Reducers

A typed distribution system for shared state — with an exhaustive audit trail.

Context is useful when information must be shared across several parts of a component tree without passing the same props through every intermediate component.

A reducer is useful when state has multiple actions or related transitions that benefit from being handled in one place.

Imagine an institute portal containing:

  • A dashboard
  • A student list
  • A student editor
  • A student details panel

All those components may need access to the selected student or shared student-management state.

9.1 Define the state and actions

Create studentState.ts:

studentState.tsTS
export interface Student {
  id: string;
  name: string;
  course: string;
}

export interface StudentState {
  students: Student[];
  selectedStudentId: string | null;
}

export type StudentAction =
  | { type: "student/added"; student: Student }
  | { type: "student/selected"; studentId: string }
  | { type: "student/removed"; studentId: string };

The action union ensures every action has a known structure.

9.2 Write a typed reducer

studentReducer.tsTS
import type { StudentAction, StudentState } from "./studentState";

export function studentReducer(
  state: StudentState,
  action: StudentAction
): StudentState {
  switch (action.type) {
    case "student/added":
      return {
        ...state,
        students: [...state.students, action.student],
      };

    case "student/selected":
      return {
        ...state,
        selectedStudentId: action.studentId,
      };

    case "student/removed":
      return {
        students: state.students.filter(
          (student) => student.id !== action.studentId
        ),
        selectedStudentId:
          state.selectedStudentId === action.studentId
            ? null
            : state.selectedStudentId,
      };

    default: {
      const exhaustiveCheck: never = action;
      return exhaustiveCheck;
    }
  }
}

Why use never?

The final branch expects that all possible actions have already been handled.

If you add another action to StudentAction but forget to handle it in the reducer, TypeScript can report the missing case at the exhaustive check.

This pattern helps maintain reducers as applications become more complex.

9.3 Create a typed Context

Create StudentContext.tsx:

StudentContext.tsxTSX
import {
  createContext,
  useContext,
  useReducer,
} from "react";

import type { ReactNode } from "react";

import { studentReducer } from "./studentReducer";

import type {
  StudentState,
  StudentAction,
} from "./studentState";

interface StudentContextValue {
  state: StudentState;
  dispatch: React.Dispatch<StudentAction>;
}

const StudentContext = createContext<StudentContextValue | null>(
  null
);

const initialState: StudentState = {
  students: [],
  selectedStudentId: null,
};

interface StudentProviderProps {
  children: ReactNode;
}

export function StudentProvider({
  children,
}: StudentProviderProps) {
  const [state, dispatch] = useReducer(studentReducer, initialState);

  return (
    <StudentContext value={{ state, dispatch }}>
      {children}
    </StudentContext>
  );
}

export function useStudents() {
  const context = useContext(StudentContext);

  if (context === null) {
    throw new Error(
      "useStudents must be used inside StudentProvider"
    );
  }

  return context;
}

This uses the React 19 context-provider syntax:

React 19TSX
<StudentContext value={{ state, dispatch }}>
  {children}
</StudentContext>

For React 18 and earlier versions, use:

React 18TSX
<StudentContext.Provider value={{ state, dispatch }}>
  {children}
</StudentContext.Provider>

The type for StudentContextValue ensures consumers receive both the state and a dispatch function that accepts only valid student actions.

9.4 Provide the context to the application

App.tsxTSX
import { StudentProvider } from "./StudentContext";
import StudentDashboard from "./StudentDashboard";

function App() {
  return (
    <StudentProvider>
      <StudentDashboard />
    </StudentProvider>
  );
}

export default App;

Now descendants can access the state.

9.5 Use Context in a child component

StudentDashboard.tsxTSX
import { useStudents } from "./StudentContext";

function StudentDashboard() {
  const { state, dispatch } = useStudents();

  function selectStudent(studentId: string) {
    dispatch({
      type: "student/selected",
      studentId,
    });
  }

  return (
    <div className="space-y-3">
      <h2 className="text-xl font-bold">Students</h2>

      {state.students.map((student) => (
        <button
          type="button"
          key={student.id}
          onClick={() => selectStudent(student.id)}
          className="block w-full rounded-lg border p-3 text-left"
        >
          {student.name}
        </button>
      ))}
    </div>
  );
}

The action must include a valid studentId string. Sending a different action structure is caught by TypeScript.

9.6 When should you use a reducer?

useReducer is useful when:

  • Many related actions change one state object.
  • State transitions have multiple conditions.
  • You want to centralize state-update logic.
  • The same reducer logic should be independently testable.
  • A component's state logic is becoming difficult to understand.

For a single boolean such as a modal's open state, useState is often simpler.

9.7 A practical Context warning

Context is a way to distribute a value through the component tree; it is not automatically a complete state-management solution.

When a context value changes, components that consume it can re-render. Consider splitting unrelated context values into separate contexts or using an appropriate state library if your application becomes large.

Also avoid choosing null as the context default and then simply assuming a value exists. The custom useStudents Hook uses a runtime check to handle the case where a component is rendered outside its provider.

Section 10

Strict Type Checking and Avoiding any

The safety net that catches what any would quietly let fall.

TypeScript provides many of its benefits when you enable strict checks and handle uncertain values explicitly.

10.1 What is strict mode?

The strict compiler option enables a group of stricter type-checking options.

In a React Vite TypeScript project, inspect the TypeScript configuration files created by the template. Make sure strict checking is enabled where intended.

A minimal example of the relevant options is:

tsconfig.jsonJSON
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "noEmit": true,
    "jsx": "react-jsx"
  }
}

This is an illustrative configuration fragment, not a complete replacement for a Vite template's tsconfig files. Existing project settings may be split across several config files, so preserve the other required options.

10.2 Why is any dangerous?

Consider:

✕ anyTS
let student: any = {
  name: "Aarav",
  course: "React",
};

student.age.toUpperCase();

TypeScript allows the property access because student is typed as any. The application may fail when it runs because the property does not exist or has the wrong type.

The any type effectively opts out of checking for that value and can cause that loss of type safety to propagate through your code.

10.3 Prefer unknown for uncertain data

If you receive an untrusted value, unknown makes you validate it before using its properties.

unknownTS
const responseData: unknown = await response.json();

You must narrow or validate that value before treating it as a Student.

For example:

narrowTS
function printName(value: unknown) {
  if (
    typeof value === "object" &&
    value !== null &&
    "name" in value &&
    typeof value.name === "string"
  ) {
    console.log(value.name);
  }
}

TypeScript knows that accessing .name is valid after these checks.

10.4 Avoid implicit any

This function does not provide enough type information for the parameter:

✕ implicit anyTS
function greet(name) {
  return `Hello, ${name}`;
}

Under strict settings, TypeScript flags an implicitly any parameter.

Correct it:

✓ explicitTS
function greet(name: string): string {
  return `Hello, ${name}`;
}

Now the function requires a string and returns a string.

10.5 Handle null and undefined explicitly

Consider a selected student:

nullableTS
interface Student {
  id: string;
  name: string;
}

const selectedStudent: Student | null = null;

This is unsafe:

✕ unsafeTS
// selectedStudent.name

TypeScript reports that the selected student could be null.

Check first:

✓ safeTS
if (selectedStudent !== null) {
  console.log(selectedStudent.name);
}

Or use optional chaining when it is appropriate:

optional chainingTS
console.log(selectedStudent?.name);

Optional chaining does not guarantee that the value exists; it returns undefined when the receiver is nullish.

10.6 Avoid unnecessary type assertions

A type assertion tells TypeScript to treat a value as a specified type:

assertionTS
const student = responseData as Student;

It does not perform validation. Use it only when you have a sound reason to trust the value and understand what the compiler can no longer verify.

When data comes from the network, a type guard or runtime schema validation is usually a safer starting point.

10.7 Replace weakly typed code

Avoid:

✕ weakTSX
function StudentCard({ student }: any) {
  return <div>{student.name}</div>;
}

Prefer:

✓ strongTSX
interface Student {
  id: string;
  name: string;
  course: string;
}

interface StudentCardProps {
  student: Student;
}

function StudentCard({ student }: StudentCardProps) {
  return (
    <div>
      <h2>{student.name}</h2>
      <p>{student.course}</p>
    </div>
  );
}

The second version provides editor autocomplete, checks the expected fields, and documents the component contract.

10.8 Practical strict-TypeScript rules

  • Prefer string, number, and boolean for primitive value types.
  • Avoid any when a precise type or unknown is possible.
  • Represent optional and nullable values explicitly.
  • Let TypeScript infer straightforward values when inference is clear.
  • Use unions for known alternatives.
  • Validate data at runtime when it crosses a trust boundary.
  • Keep event handlers, reducers, and public component props typed.
  • Run the type checker regularly.
  • Do not silence an error with as any just to make the build pass.
◆ Remember

Strict mode does not make incorrect code impossible, but it helps expose missing assumptions before they become runtime bugs.

Common Mistakes to Avoid

Fourteen pitfalls every typed React developer runs into.

  1. Using any for component props rather than defining the expected data shape.
  2. Assuming the Student interface validates data returned from a backend.
  3. Typing every component return value unnecessarily instead of using inference.
  4. Forgetting that DOM input values are usually strings.
  5. Treating checkbox .value as the checkbox's checked state.
  6. Using an untyped empty array when the intended item type is not obvious.
  7. Forgetting that DOM refs may be null before a component mounts or after it unmounts.
  8. Using ReactNode when a particular component genuinely requires a single element.
  9. Making every component generic even when there is only one relevant data type.
  10. Creating a context with null and using it without checking that its provider exists.
  11. Forgetting to handle every action in a reducer's discriminated union.
  12. Using as Student as a substitute for validating API responses.
  13. Silencing type errors with as any.
  14. Disabling strict compiler checks because of one difficult error rather than addressing the underlying type issue.
