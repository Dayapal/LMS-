Topic 1

Compound Components

Several related components that share behavior — without a giant prop list.

What are compound components?

Compound components are multiple related components that work together to provide one flexible interface.

Imagine a reusable tabs component in your LMS. You want to display:

  • Course Overview
  • Student List
  • Attendance
  • Reports

Rather than building a different tabs implementation for every page, you create a set of related components that work together.

For example:

CourseTabs.tsxTSX
<Tabs.Root defaultValue="overview">
  <Tabs.List>
    <Tabs.Trigger value="overview">Overview</Tabs.Trigger>
    <Tabs.Trigger value="students">Students</Tabs.Trigger>
    <Tabs.Trigger value="reports">Reports</Tabs.Trigger>
  </Tabs.List>

  <Tabs.Panel value="overview">
    Course overview content
  </Tabs.Panel>

  <Tabs.Panel value="students">
    Student list content
  </Tabs.Panel>

  <Tabs.Panel value="reports">
    Course reports
  </Tabs.Panel>
</Tabs.Root>

The API reads almost like a description of the interface.

The consumer decides which tabs exist and what each tab contains. The root component coordinates shared state, and the child components use that state to cooperate.

Analogy · Interlocking blocks
Compound components are interlocking blocks. The root is the baseplate; the triggers, list, and panels clip onto it in whatever configuration the consumer chooses. The blocks know how to fit together — you decide the shape.

Why use compound components?

Imagine a complex dropdown menu. You could provide dozens of props:

✕ Props-only APITSX
<Dropdown
  showHeader
  showDivider
  showFooter
  hasSearch
  searchable
  selectedItem="React"
/>

As the component grows, its API may become difficult to understand.

Composition offers another approach:

CoursePicker.tsxTSX
<Dropdown.Root>
  <Dropdown.Trigger>Choose a course</Dropdown.Trigger>

  <Dropdown.Content>
    <Dropdown.Search />
    <Dropdown.Item value="react">React</Dropdown.Item>
    <Dropdown.Item value="typescript">TypeScript</Dropdown.Item>
  </Dropdown.Content>
</Dropdown.Root>

This structure allows related components to share behavior without forcing every use case into a single large component.

How do compound components share state?

Context is a common solution.

The root stores the selected tab:

Tabs.tsxTSX
import {
  createContext,
  useContext,
  useState,
  type ReactNode,
} from "react";

interface TabsContextValue {
  value: string;
  setValue: (value: string) => void;
}

const TabsContext = createContext<TabsContextValue | null>(null);

function useTabs() {
  const context = useContext(TabsContext);

  if (!context) {
    throw new Error("Tabs components must be inside Tabs.Root");
  }

  return context;
}

function TabsRoot({
  defaultValue,
  children,
}: {
  defaultValue: string;
  children: ReactNode;
}) {
  const [value, setValue] = useState(defaultValue);

  return (
    <TabsContext.Provider value={{ value, setValue }}>
      {children}
    </TabsContext.Provider>
  );
}

A trigger reads and updates the shared value:

TabsTrigger.tsxTSX
function TabsTrigger({
  value,
  children,
}: {
  value: string;
  children: ReactNode;
}) {
  const tabs = useTabs();

  return (
    <button
      type="button"
      role="tab"
      aria-selected={tabs.value === value}
      onClick={() => tabs.setValue(value)}
      className="rounded-lg px-4 py-2"
    >
      {children}
    </button>
  );
}

A panel uses the same context to determine whether it should be displayed:

TabsPanel.tsxTSX
function TabsPanel({
  value,
  children,
}: {
  value: string;
  children: ReactNode;
}) {
  const tabs = useTabs();

  if (tabs.value !== value) {
    return null;
  }

  return <div role="tabpanel">{children}</div>;
}

You could export these components through a Tabs object:

Tabs.tsxTSX
export const Tabs = {
  Root: TabsRoot,
  Trigger: TabsTrigger,
  Panel: TabsPanel,
};
Tabs — Overview selected Output
Overview Students Reports
Course overview content — components, props, hooks, and a project.

Only the panel matching the active trigger renders. Context coordinates the whole group.

Compound Dropdown — open Output
React
TypeScript

Structure comes from the consumer — not from a dozen boolean props.

This illustrates the core pattern. A complete tabs component should also implement a tab list, correct ARIA relationships, keyboard navigation, focus management, and a clear policy for controlled versus uncontrolled selection. A tested accessibility primitive is usually a better choice for production widgets with complex interaction requirements.

Real-life use cases

Compound components work well for:

  • Tabs
  • Dropdowns
  • Dialogs
  • Accordions
  • Data tables
  • Complex forms
  • Menus
  • Reusable card layouts

They are particularly valuable when consumers need flexibility over the structure of a UI while the components share behavior.

Topic 2

Render Props and Higher-Order Components

Two reusable patterns you will meet in existing React codebases.

These are reusable component patterns that you'll encounter in existing React codebases and libraries.

Modern React often favors custom Hooks and composition for sharing behavior, but understanding both patterns remains useful.

2.1 What are render props?

A render prop is a function passed to a component that determines how some content should be rendered.

Imagine your dashboard needs to share the logic for tracking a mouse position, but different pages want to display that position differently.

One page might display coordinates. Another might draw a marker on a canvas.

Instead of coupling the behavior to one UI, the component receives a function that decides what to display.

MouseTracker.tsxTSX
import { useState, type ReactNode } from "react";

interface MousePosition {
  x: number;
  y: number;
}

function MouseTracker({
  render,
}: {
  render: (position: MousePosition) => ReactNode;
}) {
  const [position, setPosition] = useState<MousePosition>({
    x: 0,
    y: 0,
  });

  return (
    <div
      onMouseMove={(event) => {
        setPosition({
          x: event.clientX,
          y: event.clientY,
        });
      }}
      className="min-h-40 rounded-xl border p-6"
    >
      {render(position)}
    </div>
  );
}

Usage:

Dashboard.tsxTSX
<MouseTracker
  render={({ x, y }) => (
    <p>Mouse position: {x}, {y}</p>
  )}
/>

The tracking logic belongs to MouseTracker, while the caller controls the displayed result.

Analogy · The shared workbench
A render prop is a shared workbench with an interchangeable tool head. The bench (the component) supplies the workspace and the raw materials (state); the caller brings the tool head (the render function) that decides what the output looks like.

2.2 What is a higher-order component?

A higher-order component (HOC) is a function that takes a React component and returns an enhanced component.

Conceptually:

HOC shapeTSX
const EnhancedComponent = withFeature(BaseComponent);

Real-life example: a legacy application may have many components that need a shared loading indicator.

An HOC can provide that behavior without duplicating the loading check.

withLoading.tsxTSX
import type { ComponentType } from "react";

function withLoading<P extends object>(
  WrappedComponent: ComponentType<P>
) {
  return function WithLoading(
    props: P & { isLoading: boolean }
  ) {
    const { isLoading, ...componentProps } = props;

    if (isLoading) {
      return <p role="status">Loading...</p>;
    }

    return (
      <WrappedComponent
        {...(componentProps as P)}
      />
    );
  };
}

The type assertion helps TypeScript understand that the remaining props belong to the wrapped component. As with any assertion, it should be used carefully.

Usage:

StudentList.tsxTSX
interface StudentListProps {
  students: string[];
}

function StudentList({ students }: StudentListProps) {
  return (
    <ul>
      {students.map((student) => (
        <li key={student}>{student}</li>
      ))}
    </ul>
  );
}

const StudentListWithLoading = withLoading(StudentList);

Then use:

UsageTSX
<StudentListWithLoading
  isLoading={false}
  students={["Aarav", "Diya"]}
/>
withLoading — two states Output

isLoading=true

Loading...

isLoading=false

  • Aarav
  • Diya

Same wrapper logic, different wrapped component — loading state does not leak into the child.

2.3 What should you use in modern React?

Consider a custom Hook when the primary goal is to reuse stateful behavior.

For example, instead of a component or HOC that owns loading behavior, a data-fetching Hook or query library can share the request logic while leaving each component free to choose its own presentation.

Use render props when caller-controlled rendering is genuinely useful. Use HOCs when they fit an established codebase or library API. Don't introduce either pattern merely to make simple code appear more advanced.

Topic 3

Controlled and Uncontrolled Component APIs

Who owns the value? React state or the DOM?

3.1 What is a controlled component?

A controlled component receives its current value from React state and notifies its parent when the user changes it.

Imagine the LMS has a course-search field whose value must remain synchronized with the dashboard's search query.

CourseSearch.tsxTSX
import { useState } from "react";

function CourseSearch() {
  const [query, setQuery] = useState("");

  return (
    <input
      value={query}
      onChange={(event) => setQuery(event.currentTarget.value)}
      placeholder="Search courses..."
      className="w-full rounded-lg border p-3"
    />
  );
}

React state controls the displayed value.

This is especially useful when you need to validate, transform, synchronize, or reset the input based on application state.

3.2 What is an uncontrolled component?

An uncontrolled component keeps its current value in the DOM rather than making React state the source of truth for every input change.

You can supply an initial value using defaultValue and read the final value through a ref or during form submission.

QuickStudentSearch.tsxTSX
import { useRef } from "react";

function QuickStudentSearch() {
  const inputRef = useRef<HTMLInputElement | null>(null);

  function handleSearch() {
    const query = inputRef.current?.value ?? "";
    console.log("Search for:", query);
  }

  return (
    <div className="flex gap-2">
      <input
        ref={inputRef}
        defaultValue=""
        placeholder="Search students..."
        className="rounded-lg border p-3"
      />

      <button
        type="button"
        onClick={handleSearch}
        className="rounded-lg bg-indigo-600 px-4 py-2 text-white"
      >
        Search
      </button>
    </div>
  );
}

The browser maintains the input value, and React reads it when the button is clicked.

Uncontrolled inputs can be convenient for simple forms, while controlled inputs are often easier when the UI depends on input state immediately.

Analogy · The mixing console
Controlled inputs are a mixing desk whose faders report back to the studio. Every adjustment is mirrored in React state so the rest of the app can react to it. Uncontrolled inputs are a standalone instrument — the browser holds the value until you ask for it.

3.3 Designing reusable APIs that support both

A reusable component may support a controlled mode or an uncontrolled mode, but it should define the rules clearly.

For example, a custom disclosure component might accept:

Disclosure.tsxTSX
interface DisclosureProps {
  open?: boolean;
  defaultOpen?: boolean;
  onOpenChange?: (open: boolean) => void;
}

The intended contract is:

  • If open is provided, the parent controls the state.
  • If open is omitted, the component maintains internal state initialized from defaultOpen.
  • onOpenChange notifies the parent about a requested change.

Supporting both modes requires careful implementation. Avoid switching between controlled and uncontrolled mode during a single component lifetime, and keep the open value authoritative when controlled.

Disclosure — controlled vs uncontrolled Output

Controlled

<Disclosure open={isOpen} onOpenChange={setIsOpen}>

Parent is the single source of truth.

Uncontrolled

<Disclosure defaultOpen={false}>

Component owns its own internal state.

Real-life example

Use controlled APIs for:

  • Search input synchronized with URL query parameters
  • Form fields with immediate validation
  • Theme selection
  • Tabs whose selection belongs to a parent
  • Components synchronized with shared application state

Uncontrolled APIs may work well for:

  • Simple input collections submitted as a form
  • Integrations with native browser forms
  • Small fields that do not need continuous React-controlled state

Reusable Hooks and Feature Boundaries

Share the logic, keep the ownership clear.

4.1 What is a custom Hook?

A custom Hook extracts reusable React logic into a function whose name begins with use.

Imagine several LMS components need the current online status. You do not want every component to implement its own browser event listeners.

A custom Hook can encapsulate that behavior.

useOnlineStatus.tsTS
import { useSyncExternalStore } from "react";

function subscribe(callback: () => void) {
  window.addEventListener("online", callback);
  window.addEventListener("offline", callback);

  return () => {
    window.removeEventListener("online", callback);
    window.removeEventListener("offline", callback);
  };
}

export function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    () => navigator.onLine,
    () => true
  );
}

This example's server snapshot assumes an online placeholder. For an application that uses server rendering, choose a deterministic initial value and UI strategy that avoids hydration mismatches.

Use it in separate components:

NetworkStatus.tsxTSX
function NetworkStatus() {
  const online = useOnlineStatus();

  return (
    <p>
      {online ? "Connected" : "Offline"}
    </p>
  );
}

Another component can use the same Hook.

The Hook shares logic, not one common state object. Each Hook call has its own Hook state and lifecycle unless it subscribes to a shared external store or another shared source.

Reference: React — Reusing Logic with Custom Hooks.

Analogy · The shared toolbox
A custom Hook is a tool in the shared toolbox. It carries its own state and lifecycle, but it is designed to be reached for by many components. Every workshop that picks it up gets the same reliable behaviour without duplicating the tool.

4.2 What are feature boundaries?

A feature boundary is an organizational boundary around related functionality.

Instead of grouping all components in one enormous directory, organize code around concepts such as students, courses, attendance, or payments.

Example:

src/ ├── app/ │ ├── App.tsx │ └── router.tsx ├── features/ │ ├── students/ │ │ ├── components/ │ │ ├── hooks/ │ │ ├── api/ │ │ └── types.ts │ ├── courses/ │ │ ├── components/ │ │ ├── hooks/ │ │ ├── api/ │ │ └── types.ts │ └── attendance/ │ ├── components/ │ ├── hooks/ │ ├── api/ │ └── types.ts └── shared/ ├── components/ ├── hooks/ └── utils/

A student-specific search Hook can live in features/students/hooks. A generic useOnlineStatus Hook might belong in shared/hooks.

Do not automatically make every feature depend on every other feature. Keep dependencies intentional and easy to understand.

Topic 5

Dependency Injection Through Context

Supply the service; do not hard-code the implementation.

5.1 What is dependency injection?

Dependency injection means supplying a component or function with the services it needs rather than forcing it to create or import every dependency directly.

Imagine you have a StudentRepository that talks to a backend. Your component should not need to know whether that repository uses fetch, Axios, a mock implementation, or a different API base URL.

Context can provide the required dependency to a subtree.

5.2 Define a service contract

StudentApi.tsTS
interface Student {
  id: string;
  name: string;
}

interface StudentApi {
  getStudents(): Promise<Student[]>;
}

This defines what a student API must provide without forcing a specific implementation.

Analogy · Swappable modules
Dependency injection is a swappable module slot. The component knows the shape of the connector, not the brand of the module. Production plugs in the real API; tests plug in a fake. The component never notices the difference.

5.3 Provide the dependency with Context

StudentApiContext.tsxTSX
import {
  createContext,
  useContext,
  type ReactNode,
} from "react";

const StudentApiContext = createContext<StudentApi | null>(null);

export function StudentApiProvider({
  api,
  children,
}: {
  api: StudentApi;
  children: ReactNode;
}) {
  return (
    <StudentApiContext.Provider value={api}>
      {children}
    </StudentApiContext.Provider>
  );
}

export function useStudentApi() {
  const api = useContext(StudentApiContext);

  if (!api) {
    throw new Error(
      "useStudentApi must be used inside StudentApiProvider"
    );
  }

  return api;
}

The provider makes the API service available to descendants.

5.4 Inject different implementations

Production implementation:

productionStudentApi.tsTS
const productionStudentApi: StudentApi = {
  async getStudents() {
    const response = await fetch("/api/students");

    if (!response.ok) {
      throw new Error("Failed to load students");
    }

    // A real project should validate the returned JSON.
    return response.json() as Promise<Student[]>;
  },
};

Test implementation:

fakeStudentApi.tsTS
const fakeStudentApi: StudentApi = {
  async getStudents() {
    return [
      { id: "STU-101", name: "Aarav Patel" },
    ];
  },
};

The application can receive either implementation through the provider.

A component calls useStudentApi() and does not need to know where the service came from.

Same component, two providers Output

Production provider

<StudentApiProvider api={productionStudentApi}>

→ real HTTP request to /api/students

Test provider

<StudentApiProvider api={fakeStudentApi}>

→ returns STU-101 Aarav Patel instantly

▲ Security note

Dependency injection is an architectural technique, not an access-control mechanism. A frontend-provided service cannot enforce server-side authorization.

State Machines and Complex Workflows

Model the states and transitions instead of juggling booleans.

6.1 Why do complex workflows need more than a boolean?

Imagine an LMS checkout flow with several steps:

  • Enter enrollment details
  • Confirm course selection
  • Submit payment
  • Show success
  • Show an error if submission fails

If you use several unrelated booleans, you could accidentally create contradictory states:

✕ BooleansTSX
const [isLoading, setIsLoading] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
const [hasError, setHasError] = useState(false);

What should happen if both isSuccess and hasError become true?

A state machine models the workflow as a set of defined states and permitted transitions.

6.2 Model a checkout workflow

checkout.tsTS
type CheckoutState =
  | { status: "details" }
  | { status: "payment"; orderId: string }
  | { status: "submitting"; orderId: string }
  | { status: "success"; orderId: string }
  | { status: "error"; message: string };

This structure expresses which data belongs to each state.

For instance, a successful checkout must have an orderId. An error state must have an error message.

Analogy · The metro map
A state machine is a metro map. Every state is a station; every event is a track connecting two stations. You can only reach the stops that are actually on a line — there is no accidental shortcut from "details" straight to "success".

6.3 Define the permitted events

checkout.tsTS
type CheckoutEvent =
  | { type: "CONTINUE"; orderId: string }
  | { type: "SUBMIT" }
  | { type: "SUCCESS" }
  | { type: "FAILURE"; message: string }
  | { type: "RETRY" }
  | { type: "EDIT_DETAILS" };

These event types represent actions the workflow may receive.

6.4 Implement transitions

checkoutReducer.tsTS
function checkoutReducer(
  state: CheckoutState,
  event: CheckoutEvent
): CheckoutState {
  switch (state.status) {
    case "details":
      if (event.type === "CONTINUE") {
        return {
          status: "payment",
          orderId: event.orderId,
        };
      }

      return state;

    case "payment":
      if (event.type === "SUBMIT") {
        return {
          status: "submitting",
          orderId: state.orderId,
        };
      }

      if (event.type === "EDIT_DETAILS") {
        return { status: "details" };
      }

      return state;

    case "submitting":
      if (event.type === "SUCCESS") {
        return {
          status: "success",
          orderId: state.orderId,
        };
      }

      if (event.type === "FAILURE") {
        return {
          status: "error",
          message: event.message,
        };
      }

      return state;

    case "error":
      if (event.type === "RETRY") {
        return {
          status: "payment",
          orderId: getCurrentOrderId(),
        };
      }

      return state;

    case "success":
      return state;
  }
}

This demonstrates the idea of defining legal transitions, but getCurrentOrderId() is a placeholder for your actual order-management logic. In a complete implementation, preserve the order ID in the error state or in a separate stable state structure rather than relying on a global lookup.

The important principle is that the state and allowed events are explicitly modeled.

Checkout workflow — reachable states Output
details → CONTINUE → payment → SUBMIT → submitting → SUCCESS → success
submitting → FAILURE → error → RETRY → payment

No transition from success back to submitting exists. Contradictory states like "success and error" are impossible.

6.5 When should you use a state machine?

State machines can be especially useful for:

  • Multi-step forms
  • Checkout and payment flows
  • Authentication workflows
  • Upload processes
  • Booking systems
  • Approval workflows
  • Complex dialogs
  • Operations with retry and cancellation behavior

For simple UI state, useState or useReducer may be enough. A dedicated library such as XState can help when a workflow has many states, guards, delayed transitions, parallel states, or other complex requirements.

Topic 7

Optimistic UI Updates

Show the result immediately, but know how to roll back.

7.1 What is an optimistic update?

An optimistic update makes the UI reflect an action immediately, before the server confirms that it succeeded.

Imagine a student clicks Mark Lesson Complete. Waiting for the server may take 800 milliseconds. The application can immediately show the lesson as completed, then reconcile the UI when the request succeeds or fails.

Optimistic updates improve perceived responsiveness, but they require a correct strategy for handling failures.

7.2 Use React's useOptimistic Hook

React provides useOptimistic to display a temporary optimistic state while an Action is in progress.

Example: a student posts a course comment.

CommentBox.tsxTSX
import { useOptimistic, useState, useTransition } from "react";
import type { FormEvent } from "react";

interface Comment {
  id: string;
  text: string;
}

interface CommentBoxProps {
  comments: Comment[];
  onSave: (comment: Comment) => Promise<void>;
}

function CommentBox({ comments, onSave }: CommentBoxProps) {
  const [optimisticComments, addOptimisticComment] =
    useOptimistic(
      comments,
      (current, comment: Comment) => [...current, comment]
    );

  const [isPending, startTransition] = useTransition();
  const [error, setError] = useState("");

  function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();

    const form = event.currentTarget;
    const formData = new FormData(form);
    const text = String(formData.get("comment") ?? "").trim();

    if (!text) return;

    setError("");

    const newComment: Comment = {
      id: `temp-${crypto.randomUUID()}`,
      text,
    };

    startTransition(async () => {
      addOptimisticComment(newComment);

      try {
        await onSave(newComment);
      } catch {
        setError("Unable to post comment. Please try again.");
      }
    });

    form.reset();
  }

  return (
    <section className="space-y-4">
      <form onSubmit={handleSubmit} className="flex gap-2">
        <label htmlFor="comment" className="sr-only">
          Add a comment
        </label>

        <input
          id="comment"
          name="comment"
          className="min-w-0 flex-1 rounded-lg border p-3"
          placeholder="Write a comment..."
        />

        <button
          type="submit"
          disabled={isPending}
          className="rounded-lg bg-indigo-600 px-4 py-2 text-white disabled:opacity-50"
        >
          {isPending ? "Posting..." : "Post"}
        </button>
      </form>

      {error && <p role="alert">{error}</p>}

      <ul className="space-y-2">
        {optimisticComments.map((comment) => (
          <li key={comment.id} className="rounded-lg border p-3">
            {comment.text}
          </li>
        ))}
      </ul>
    </section>
  );
}

This is an illustrative React 19 pattern. The parent must update the underlying comments prop with the authoritative saved comment after the request succeeds. If saving fails, the temporary optimistic entry is removed when the Action completes.

For a production implementation, consider generating temporary IDs carefully, preventing duplicate submissions as needed, displaying pending state per comment, and reconciling temporary IDs with server-generated IDs.

Analogy · Instant feedback
An optimistic update is a light switch that flips instantly — with a quiet "undo" button. The room brightens immediately (perceived performance), but the wiring behind the wall still confirms the switch is real. If the circuit fails, the light reverts and the user is told.

7.3 Understand the flow

  1. The user submits a comment.
  2. The application adds the comment to the optimistic view.
  3. The request is sent to the server.
  4. If saving succeeds, the parent updates the authoritative comments.
  5. If saving fails, the optimistic view reverts to the current authoritative state and the error message is shown.

useOptimistic does not automatically save data or make the backend transaction succeed. It only helps present temporary state while the Action is pending.

Reference: React useOptimistic.

Internationalization

Design for languages and locales from the start — not as a retrofit.

8.1 What is internationalization?

Internationalization, commonly abbreviated i18n, means designing software so it can support different languages and regional conventions.

Localization means adapting content for a specific locale, such as Hindi for India or English for the United States.

For an LMS, this may include:

  • English and Hindi translations
  • Locale-aware numbers
  • Date formatting
  • Currency formatting
  • Right-to-left language support where relevant
  • Language-specific plural forms
  • Localized routes or page metadata

8.2 Why hard-coded text becomes difficult to maintain

Suppose your dashboard displays:

✕ Hard-codedTSX
<button>Start Learning</button>

If every component contains hard-coded strings, supporting multiple languages can become difficult.

A translation system stores language-specific messages centrally and lets components request the appropriate version.

Analogy · One app, many voices
i18n is one application speaking many languages. The message catalogue is the phrasebook; Intl is the local convention for numbers, dates, and currency. The component doesn't hard-code a phrase — it asks the catalogue.

Topic 9

Designing Scalable Frontend Architecture

Make the relationships between features explicit and easy to change.

9.1 What is frontend architecture?

Frontend architecture is the way an application organizes responsibilities, dependencies, state, reusable UI, data access, and feature boundaries.

Imagine a small training portal with only a dashboard and student list. A few files may be sufficient.

Now imagine it grows to include authentication, payments, book releases, assignments, attendance, multilingual support, and analytics. If everything remains in a single component or a collection of tangled shared modules, changing one feature can break another.

Scalable architecture makes these relationships explicit.

Analogy · The blueprint
Architecture is a blueprint, not a floor plan. The blueprint shows which walls are load-bearing and which doors connect which rooms. A reader can find the entrance, the kitchen, and the exits without walking every corridor.

9.2 Organize around features

A practical organization might look like:

src/ ├── app/ │ ├── App.tsx │ ├── router.tsx │ └── providers.tsx ├── features/ │ ├── auth/ │ │ ├── components/ │ │ ├── api/ │ │ └── hooks/ │ ├── students/ │ │ ├── components/ │ │ ├── api/ │ │ ├── hooks/ │ │ └── types.ts │ ├── courses/ │ ├── books/ │ ├── attendance/ │ └── analytics/ ├── shared/ │ ├── components/ │ ├── hooks/ │ ├── utilities/ │ └── types/ └── styles/

This is one possible structure, not a universal standard.

The goal is to keep closely related code together and make the public boundaries between features easy to understand.

9.3 Separate responsibilities

A maintainable application often separates these concerns:

ResponsibilityExample
PresentationStudentCard.tsx
Feature behavioruseStudentSearch.ts
Data accessstudentsApi.ts
Shared stateContext or a state-management library
RoutingRoute definitions and layouts
Shared design systemButtons, cards, inputs, dialogs
ValidationDomain-specific schema or validation functions
App compositionProviders and route setup

Do not create a separate layer for every trivial function merely to match a diagram. Introduce boundaries that make changes, testing, and ownership easier.

9.4 Keep domain logic out of oversized components

A component may become difficult to maintain if it performs all of these jobs:

  • Fetches student data
  • Validates input
  • Calculates attendance
  • Manages several dialogs
  • Applies permissions to actions
  • Formats currency
  • Displays a table
  • Handles export functionality

Extract cohesive responsibilities into suitable feature modules, services, Hooks, or utilities.

The goal is not to make every component tiny. The goal is to make each component's responsibility clear.

9.5 Avoid circular dependencies

A problematic dependency structure looks like:

Circular dependency
Students → Courses → Attendance → Students

When features depend on one another in both directions, changes become difficult to reason about.

A clearer structure might place shared types or common domain concepts in a lower-level shared module, then define a deliberate direction of dependency.

For example:

Directed dependencies
Shared Types
    ↑       ↑
Students   Courses
    ↑       ↑
  Dashboard

The exact dependency direction depends on your domain, but aim to avoid unnecessary cycles.

Topic 10

React Server Components Concepts

Render on the server; send less JavaScript to the browser.

10.1 What are React Server Components?

React Server Components (RSC) are components designed to render in a server environment.

They allow applications using a compatible React framework or bundler integration to render parts of the component tree on the server. Server Component code can access server-side resources and avoid shipping that component's implementation to the browser.

In the Next.js App Router, pages and layouts are Server Components by default. Client Components are introduced for interactivity and browser-only behavior. See the Next.js Server and Client Components guide.

Analogy · The restaurant kitchen
Server Components are the kitchen; Client Components are the dining room. The kitchen (server) has the knives, the oven, and the private recipe book. The dining room (browser) has the chairs, the music, and the customers. The plate that crosses the pass is serializable — you don't hand a customer a stove.

10.2 Real-life example: Course catalogue

Imagine your LMS has a public course catalogue.

The server can fetch public course information and render the course cards without requiring the browser to fetch the same data after rendering the page.

A simplified Server Component could look like:

app/courses/page.tsxTSX
// app/courses/page.tsx

interface Course {
  id: string;
  title: string;
  description: string;
}

export default async function CoursesPage() {
  const response = await fetch(
    "https://api.example.com/public/courses"
  );

  if (!response.ok) {
    throw new Error("Could not load courses.");
  }

  const courses: Course[] = await response.json();

  return (
    <main className="mx-auto max-w-6xl p-6">
      <h1 className="mb-6 text-3xl font-bold">
        Available Courses
      </h1>

      <div className="grid gap-4 md:grid-cols-2 lg:grid-cols-3">
        {courses.map((course) => (
          <article key={course.id} className="rounded-xl border p-5">
            <h2 className="font-bold">{course.title}</h2>
            <p className="mt-2 text-slate-600">
              {course.description}
            </p>
          </article>
        ))}
      </div>
    </main>
  );
}

This demonstrates the structure of a Server Component in Next.js. The endpoint is illustrative, and a production application should validate external data and handle errors appropriately.

If server-side credentials or private data are involved, access them only through trusted server-side code and check authorization for the current user.

10.3 When do you need a Client Component?

Consider a course card with a favorite button.

FavoriteButton.tsxTSX
"use client";

import { useState } from "react";

export default function FavoriteButton() {
  const [favorite, setFavorite] = useState(false);

  return (
    <button
      type="button"
      aria-pressed={favorite}
      onClick={() => setFavorite((value) => !value)}
    >
      {favorite ? "Favorited" : "Add to favorites"}
    </button>
  );
}

The "use client" directive declares a boundary between the server and client module graphs in a supported framework such as Next.js.

A Client Component is suitable here because the feature requires interactive state and an event handler.

It is important to understand that Client Components can still participate in server pre-rendering on the initial page load in Next.js. "Client Component" does not simply mean that its HTML can only ever be created in the browser.

10.4 Server Components versus Client Components

CapabilityServer ComponentClient Component
Access server-only resources directlyYes, where the server environment and authorization allow itNo direct access to server-only resources
Use state and event handlersNoYes
Use browser APIs such as windowNoYes, in appropriate client execution
Keep server-only module code out of the client bundleYes, for the Server Component implementationNot for client-side module dependencies
Use interactive Hooks such as useStateNoYes
Send serialized props from server to clientCan pass supported serializable valuesReceives them as props

Props passed across a Server-to-Client Component boundary need to satisfy React's serialization requirements. Do not assume that functions, database connections, or arbitrary server objects can be passed as ordinary props.

Also, a Server Component is not automatically a security boundary for every resource it accesses. Server-side authorization is still required.

Topic 11

Server Rendering and Hydration Concepts

HTML first. Interactivity second. The two must agree.

11.1 What is server-side rendering?

Server-side rendering (SSR) means generating the initial HTML for a React UI on the server and sending it to the browser.

Without server-rendered HTML, a client-rendered application may need to load JavaScript and execute it before the main UI appears.

SSR can allow users to see useful HTML sooner and may support content discovery by crawlers. Its benefits depend on the application, rendering setup, caching strategy, and performance characteristics.

11.2 What is hydration?

Hydration is the process where React attaches event handlers and connects React behavior to existing server-rendered HTML.

For example, the server might send:

Server HTMLHTML
<div id="root">
  <button>Count: 0</button>
</div>

The initial HTML can display a button, but it is not yet interactive merely because its markup exists.

The browser loads the client JavaScript and React hydrates the HTML so that the button can respond to interaction.

Analogy · The blueprint and the building
SSR ships the building; hydration turns the lights on. The server delivers the structure (HTML) so people can walk around it. The client wires up the electricity (event handlers). If the client's blueprint disagrees with the server's, the lights flicker — that is a hydration mismatch.

11.3 Why hydration mismatches happen

The server-rendered output and the first client render should agree on the UI structure and initial content.

For example, this component is risky in a server-rendered application:

✕ RiskyTSX
function CurrentTime() {
  return <p>{new Date().toLocaleTimeString()}</p>;
}

The server and browser may evaluate the time at different moments, and their locale settings may differ. Their first rendered outputs can disagree.

Other causes can include:

  • Using window or localStorage during server rendering
  • Generating random values during rendering
  • Incorrect HTML nesting
  • Rendering different branches on the server and initial client pass
  • Nondeterministic data or formatting

11.4 Avoid browser-only values during the initial render

A safer pattern can delay browser-specific logic until the component mounts:

LocalTime.tsxTSX
"use client";

import { useEffect, useState } from "react";

function LocalTime() {
  const [time, setTime] = useState<string | null>(null);

  useEffect(() => {
    setTime(new Date().toLocaleTimeString());
  }, []);

  return <p>{time ?? "Loading time..."}</p>;
}

The server output and initial client render both display the placeholder. After hydration, the effect updates the displayed time.

This avoids the specific initial mismatch in the example, but it also means the local time is not present in the server-rendered HTML. Choose the right rendering and formatting strategy for your use case rather than adding effects everywhere.

11.5 What is hydrateRoot?

For a manually configured SSR application, React DOM provides hydrateRoot to hydrate existing HTML.

main.tsxTSX
import { hydrateRoot } from "react-dom/client";
import App from "./App";

const rootElement = document.getElementById("root");

if (!rootElement) {
  throw new Error("Root element not found.");
}

hydrateRoot(rootElement, <App />);

This is a conceptual client-side hydration example. It assumes the server has already generated compatible HTML for App and that both server and client are configured consistently.

For an ordinary Next.js application, the framework coordinates the rendering and hydration process. You generally should not add your own hydrateRoot call to an App Router page.

Topic 12

Streaming and Suspense in Frameworks

Send the shell first; stream the slow parts as they become ready.

12.1 What is streaming?

Traditional SSR can wait until a complete page is ready before sending the generated HTML.

Streaming can allow parts of the page to be sent as they become ready, so slower sections do not have to block all of the useful content.

Imagine an LMS dashboard that displays the user's name quickly but loads a large analytics report more slowly.

With appropriate streaming support, the server can send the page shell first and stream the slower section when it is ready.

Analogy · The waterfall
Streaming is a waterfall, not a dam. Each drop does not wait for the last to arrive. The shell of the page falls first, then the slower sections come down in their own time. A Suspend boundary is the lip of each drop.

12.2 What is Suspense?

React's Suspense provides a fallback for supported operations that suspend while rendering.

Example:

Dashboard.tsxTSX
import { Suspense } from "react";

function Dashboard() {
  return (
    <main>
      <h1 className="text-2xl font-bold">
        Student Dashboard
      </h1>

      <Suspense fallback={<p>Loading analytics...</p>}>
        <AnalyticsReport />
      </Suspense>
    </main>
  );
}

A boundary is useful only when a descendant uses a supported Suspense-enabled mechanism.

▲ Important

An ordinary fetch() inside useEffect does not automatically cause a surrounding Suspense boundary to show its fallback.

12.3 Streaming with Next.js App Router

In Next.js, Server Components can fetch data, and streaming can progressively reveal UI.

A simplified page might look like this:

app/dashboard/page.tsx

app/dashboard/page.tsxTSX
import { Suspense } from "react";

async function AnalyticsReport() {
  const response = await fetch(
    "https://api.example.com/analytics"
  );

  if (!response.ok) {
    throw new Error("Could not load analytics.");
  }

  const report = await response.json();

  return (
    <section className="rounded-xl border p-5">
      <h2 className="text-xl font-semibold">
        Analytics Report
      </h2>

      <pre className="mt-3 overflow-auto text-sm">
        {JSON.stringify(report, null, 2)}
      </pre>
    </section>
  );
}

export default function DashboardPage() {
  return (
    <main className="space-y-6 p-6">
      <h1 className="text-3xl font-bold">
        Student Dashboard
      </h1>

      <Suspense
        fallback={
          <div className="animate-pulse rounded-xl bg-slate-200 p-8">
            Loading analytics...
          </div>
        }
      >
        <AnalyticsReport />
      </Suspense>
    </main>
  );
}

This demonstrates the intended pattern. The analytics component is asynchronous and can suspend while its data is being retrieved.

In production:

  • Validate the response before rendering.
  • Choose the appropriate caching and revalidation policy.
  • Ensure data access is authorized.
  • Handle failures using the framework's appropriate error boundaries and route error handling.
  • Use a meaningful UI fallback.

The example displays JSON to demonstrate the data flow. A real report should render the specific fields it needs.

For example:

app/dashboard/loading.tsxTSX

A route-level loading boundary and a component-level Suspense boundary serve related but different UI composition needs.

12.5 How streaming helps

Streaming can make it possible for:

  • Useful page content to appear sooner.
  • A slow analytics region to load independently.
  • Different page sections to use different loading placeholders.
  • The interface to progressively reveal content as it becomes available.

However, streaming does not automatically make every operation faster. Poor boundary placement, expensive server work, or inappropriate caching can still hurt the experience.

Topic 13

When to Use a Framework Such as Next.js

Choose by requirements, not by fashion.

13.1 What is Next.js?

Next.js is a React framework for building web applications. It includes routing, server rendering capabilities, React Server Component support in the App Router, loading and error conventions, and other build and deployment features.

It provides an organized way to build larger applications without configuring all the underlying infrastructure from scratch.

Official documentation: Next.js.

13.2 When a plain React + Vite project can be enough

Imagine you are building an internal dashboard used after staff sign in.

Its requirements include:

  • Client-side dashboard interactions
  • API-based data access
  • A protected login flow
  • Charts and tables
  • Internal forms and workflows

A React + Vite SPA may be a good fit, especially if the backend already provides routing, APIs, and authentication.

You do not necessarily need a full-stack React framework for every React project.

Analogy · The fork in the road
Choosing a framework is choosing a fork in the road — not the destination. Vite is the short, direct path for internal apps that consume an existing API. Next.js is the wider highway for public pages, SSR, and server components. Walk the requirements before you pick the road.

13.3 When Next.js may be a better choice

Imagine you are building a public online course marketplace.

Its requirements include:

  • Public course pages
  • Discoverability by search engines
  • Dynamic server-rendered pages
  • Server-side data access
  • Page layouts and nested routes
  • Route loading and error UI
  • A mixture of server-rendered content and interactive components

Next.js may be useful because it provides framework-level routing, Server Components, SSR, static rendering, and streaming patterns.

The right rendering strategy depends on which requirements the application actually has.

Neither option is always better. Consider the team's expertise, hosting constraints, rendering needs, caching behavior, operational complexity, and long-term maintenance.

13.5 A practical decision process

Ask yourself:

Question 1: Does the application need only a client-side UI?

If it is a relatively straightforward SPA that consumes an existing backend API, React + Vite may be enough.

Question 2: Do you need server-side rendering or static rendering for public content?

If the application benefits from these rendering modes, a framework such as Next.js may be worth considering.

Question 3: Do you need server-only data access?

Next.js Server Components and server-side application features can help organize this architecture, but secrets and authorization still require proper server-side enforcement.

Question 4: Do you need a more structured routing and data-loading model?

A framework may supply useful conventions and features. A standalone React project with a router and API layer may still be sufficient.

Question 5: Can your team operate the framework reliably?

Evaluate deployment, observability, caching, runtime behavior, and maintenance. More capability also means more architectural choices to understand.

Scalable Training LMS Architecture

Design a modular LMS that supports different users, reusable UI components, predictable workflows, internationalization, and an appropriate rendering architecture.

Analogy · Ready for the next floor
A scalable architecture is a building designed to grow upward. The foundation (shared types), the columns (features), and the services (APIs) are in place before the next floor is added. Each floor can be built without re-pouring the concrete below.

Project objective

Design a modular LMS that supports different users, reusable UI components, predictable workflows, internationalization, and an appropriate rendering architecture.

Required features

  1. Build compound tabs and an accordion component.
  2. Demonstrate a render-prop component and understand HOCs.
  3. Support controlled and uncontrolled inputs where appropriate.
  4. Extract reusable Hooks for repeated behavior.
  5. Provide a service through Context and inject a fake service in tests.
  6. Model a multi-step enrollment workflow with explicit states and transitions.
  7. Add an optimistic course or lesson update with failure recovery.
  8. Support English and Hindi with locale-aware formatting.
  9. Organize features into clear modules with deliberate dependencies.
  10. Build a Server Component and a Client Component in Next.js.
  11. Understand hydration and avoid mismatches.
  12. Add loading UI and streaming boundaries for slow report data.
  13. Document why the chosen application framework fits the requirements.

Suggested architecture

src/ ├── app/ │ ├── providers.tsx │ └── routes.tsx ├── features/ │ ├── auth/ │ ├── students/ │ ├── courses/ │ ├── books/ │ ├── attendance/ │ └── analytics/ ├── shared/ │ ├── components/ │ ├── hooks/ │ └── utilities/ └── services/ ├── studentApi.ts └── courseApi.ts

For a Next.js App Router project, adapt the structure to the framework's app/ directory conventions rather than copying a Vite router structure literally.

Acceptance criteria

  • Components expose understandable and consistent APIs.
  • Complex workflow states and transitions are explicitly modeled.
  • Shared behavior is extracted into focused Hooks where appropriate.
  • Tests can provide a fake service without relying on the production backend.
  • Optimistic changes recover correctly when a request fails.
  • Translation strings are organized and locale-sensitive formatting is used where appropriate.
  • Feature boundaries are documented.
  • Server-only logic is kept on the server.
  • Hydration issues are prevented or properly diagnosed.
  • Loading boundaries are placed intentionally.
  • The selected framework is justified by actual requirements.

⚠ Pitfalls

Common mistakes to avoid

Fourteen traps to recognise before they cost you a refactor.

  1. Building one enormous component with dozens of unrelated props instead of considering composition.
  2. Using render props or HOCs where a small custom Hook would be simpler.
  3. Supporting controlled and uncontrolled modes without defining their behavior.
  4. Extracting Hooks for every tiny repeated line of code.
  5. Using Context as a universal replacement for all state-management solutions.
  6. Modeling complex workflows with unrelated boolean flags.
  7. Showing optimistic success without handling server failures.
  8. Hard-coding translated strings throughout the UI.
  9. Organizing every file by file type without considering feature dependencies.
  10. Mixing server-only dependencies into the client bundle.
  11. Assuming Server Components and SSR mean the same thing.
  12. Assuming every fetch automatically triggers a Suspense fallback.
  13. Using streaming without designing meaningful loading UI.
  14. Choosing a framework solely because it is popular rather than because its capabilities fit the requirements.

Final Goal · Phase 14

Choose the simplest pattern that solves the problem

Design and build a React application in which components are composable, business workflows are predictable, shared dependencies are testable, language support is organized, and the rendering architecture fits the product.

The key principle: Advanced architecture is not about using every pattern. It is about choosing the simplest pattern that solves the actual problem and remains maintainable as the application grows.
