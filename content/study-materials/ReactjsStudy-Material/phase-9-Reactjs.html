Section 01

Component Lifecycle Through Modern Hooks

What a component goes through — from appearing to updating to disappearing.

1.1 What is a component lifecycle?

A component lifecycle describes the stages a component goes through while your application runs.

Think of a student joining an institute.

  • Mounting: The student joins the institute.
  • Updating: The student's details or course changes.
  • Unmounting: The student leaves the institute.

A React component has similar stages.

Mounting

A component appears in the React UI tree for the first time.

For example, a user opens a dashboard, and the dashboard component appears.

Updating

A component renders again because its props, state, or relevant context changed.

For example, a user clicks a button and the dashboard displays an updated notification count.

Unmounting

A component is removed from the UI tree.

For example, a user closes a chat panel and React removes the chat panel component.

1.2 How did class components handle lifecycle events?

Older React applications often use class lifecycle methods such as:

  • componentDidMount
  • componentDidUpdate
  • componentWillUnmount

Example:

Clock.jsxJSX
import { Component } from "react";

class Clock extends Component {
  componentDidMount() {
    console.log("Clock appeared");
  }

  componentDidUpdate() {
    console.log("Clock updated");
  }

  componentWillUnmount() {
    console.log("Clock removed");
  }

  render() {
    return <h1>Clock component</h1>;
  }
}

This code is still useful to understand when reading older React projects. However, modern React applications generally favor function components with Hooks.

1.3 How do lifecycle tasks work with useEffect?

The useEffect Hook allows a component to synchronize with an external system, such as a timer, browser event, subscription, or network connection.

Real-life example: imagine a student dashboard displays a live clock. The component needs to start a timer when it appears and stop the timer when it disappears.

LiveClock.jsxJSX
import { useEffect, useState } from "react";

function LiveClock() {
  const [time, setTime] = useState(() => new Date());

  useEffect(() => {
    const timerId = setInterval(() => {
      setTime(new Date());
    }, 1000);

    return () => {
      clearInterval(timerId);
    };
  }, []);

  return (
    <div className="rounded-xl bg-white p-5 shadow">
      <h2 className="text-lg font-semibold">Current Time</h2>
      <p className="mt-2 text-2xl">
        {time.toLocaleTimeString()}
      </p>
    </div>
  );
}

export default LiveClock;

Understand the code step by step

Step 1: Create the state

stateJSX
const [time, setTime] = useState(() => new Date());

React stores the current time. The initializer function is used when the component initializes its state.

Step 2: Start the timer

effectJSX
useEffect(() => {
  const timerId = setInterval(() => {
    setTime(new Date());
  }, 1000);

  return () => {
    clearInterval(timerId);
  };
}, []);

The effect sets up a timer that updates the state every second.

Step 3: Clean up the timer

cleanupJSX
return () => {
  clearInterval(timerId);
};

The function returned by the effect is its cleanup function. React calls this cleanup when the effect needs to stop synchronizing, including when the component unmounts.

Because the dependency array is empty, the effect does not need to re-synchronize when props or state change. In development Strict Mode, React may perform an extra setup-and-cleanup cycle to help uncover bugs.

Step 4: Display the time

displayJSX
<p>{time.toLocaleTimeString()}</p>

Each state update causes another render, and the screen displays the latest value.

1.4 Understanding effect dependencies

Suppose a counsellor dashboard displays the profile for the currently selected student.

StudentProfile.jsxJSX
import { useEffect, useState } from "react";

function StudentProfile({ studentId }) {
  const [student, setStudent] = useState(null);

  useEffect(() => {
    let ignore = false;

    async function loadStudent() {
      setStudent(null);

      const response = await fetch(`/api/students/${studentId}`);

      if (!response.ok) {
        throw new Error("Could not load student");
      }

      const data = await response.json();

      if (!ignore) {
        setStudent(data);
      }
    }

    loadStudent().catch((error) => {
      if (!ignore) {
        console.error(error);
      }
    });

    return () => {
      ignore = true;
    };
  }, [studentId]);

  if (!student) {
    return <p>Loading student profile...</p>;
  }

  return <h2>{student.name}</h2>;
}

The important line is:

depsJSX
}, [studentId]);

The effect re-runs when studentId changes. If the user opens a different student's profile, React starts loading the appropriate record.

The cleanup prevents an old request's result from updating this component after the effect has been replaced or cleaned up. For production networking code, also consider AbortController, user-friendly error handling, and a data-fetching library.

Lifecycle mapping: approximate, not exact

Class lifecycleTypical Hook pattern
componentDidMountAn effect with setup and an appropriate dependency list
componentDidUpdateAn effect that re-synchronizes when dependencies change
componentWillUnmountAn effect's cleanup function
Derived display valuesUsually calculate during rendering instead of adding an effect

These are conceptual mappings, not exact replacements in every situation.

1.5 When should you use useEffect?

Use it when React must synchronize with something outside its rendering process, such as:

  • A timer or event listener
  • A WebSocket connection
  • An external browser API
  • An imperative third-party widget
  • A request flow that you intentionally manage in an effect

Do not add an effect just to calculate a value that can be derived from props or state.

For example, avoid storing fullName separately when it can be calculated directly from firstName and lastName:

derivedJSX
const fullName = `${firstName} ${lastName}`;
◆ Remember

Rendering calculates UI. Effects synchronize with external systems.

Official guide: https://react.dev/learn/synchronizing-with-effects

Section 02

Reconciliation and Render Behavior

What "rendering" really means, and how React decides what to commit.

2.1 What does rendering mean in React?

When people say “React rendered the component,” they do not necessarily mean that React changed the browser DOM.

A render means React calls the component to calculate what its UI should look like.

React then compares the new output with the previous result and commits any required DOM changes.

Think of a restaurant.

A chef may prepare a new version of a dish, but the waiter only replaces what has actually changed on the customer's table.

React behaves similarly: it calculates a new UI and applies the necessary changes.

2.2 The render-and-commit process

React's update process can be understood in three steps.

Step 1: Trigger

A render is triggered by an initial render, a state update, or another relevant update in the component tree.

Step 2: Render

React calls components to calculate the next UI.

Step 3: Commit

React applies necessary changes to the DOM.

Consider this example:

StudentCounter.jsxJSX
import { useState } from "react";

function StudentCounter() {
  const [count, setCount] = useState(0);

  console.log("StudentCounter rendered");

  return (
    <div className="space-y-3">
      <h2>Enrolled Students: {count}</h2>

      <button
        type="button"
        onClick={() => setCount((value) => value + 1)}
        className="rounded-lg bg-indigo-600 px-4 py-2 text-white"
      >
        Add Student
      </button>
    </div>
  );
}

Every time you click the button, React re-renders StudentCounter.

However, React only needs to update the displayed count in the DOM. It does not rebuild the entire page from scratch.

2.3 What is reconciliation?

Reconciliation is the process React uses to determine how the previous UI tree relates to the new UI tree.

Imagine a dashboard showing 100 student records. When one student's name changes, React can compare the updated UI with the previous output and commit the necessary changes instead of manually rebuilding the whole DOM yourself.

React uses information including element types, their positions in the tree, and keys to determine which components and elements correspond between renders.

A simplified example:

Before:

beforeJSX
<div>
  <h1>Student Dashboard</h1>
  <p>Students: 10</p>
</div>

After:

afterJSX
<div>
  <h1>Student Dashboard</h1>
  <p>Students: 11</p>
</div>

The structure remains largely the same. Only the displayed count needs updating.

You should not depend on React's private reconciliation implementation details. Instead, write components with stable identities, correct keys, and pure rendering logic.

2.4 Why does a child component sometimes render again?

Parent.jsxJSX
function Parent() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>
        Count: {count}
      </button>

      <StudentDetails />
    </div>
  );
}

function StudentDetails() {
  console.log("StudentDetails rendered");

  return <p>Student details</p>;
}

When Parent updates, React will ordinarily render StudentDetails again because it is part of the updated subtree and has not been memoized.

This is not automatically a performance problem. Rendering relatively simple components is often inexpensive.

If a child performs costly work or renders a very large tree, profiling can help you decide whether an optimization is useful.

2.5 Rendering must be pure

A React component should calculate the same JSX when given the same props, state, and context. Rendering should not unexpectedly change outside state or start external work.

Avoid this:

✕ ImpureJSX
function BadCounter() {
  let count = 0;
  count += 1;

  return <p>{count}</p>;
}

The local variable is recreated whenever the function runs. It is not persistent React state.

Use useState for values that should persist across renders:

Counter.jsxJSX
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((value) => value + 1)}>
      Count: {count}
    </button>
  );
}

Also avoid mutating props or existing state objects during rendering.

✕ MutatingJSX
// Avoid mutating an existing state array.
students.push(newStudent);

Instead, create the updated array:

✓ ImmutableJSX
setStudents((previous) => [...previous, newStudent]);

Real-life example: Student dashboard filtering

When a user chooses “Active Students,” React calculates the list to display from the existing records and selected filter.

filteringJSX
const visibleStudents = students.filter((student) => {
  return filter === "all" || student.status === filter;
});

This is derived UI data. It generally doesn't need its own state variable or an effect to keep it synchronized.

◆ Remember

Render calculates the desired UI; reconciliation determines how it corresponds to the previous UI; commit applies actual DOM changes.

Official guide: https://react.dev/learn/render-and-commit

Section 03

State Preservation and Reset with Keys

Keys are identity — not just a list warning.

3.1 Why does React preserve state?

Suppose a student types a message and then opens another student's chat. Should the old message remain in the input?

Usually, no. The draft belongs to the earlier conversation.

React preserves state when it identifies a component as the same component in the same position in the UI tree. It resets state when that identity changes—for example, when the component type changes or when a different key is used.

3.2 Example: A form that retains its input

StudentEditor.jsxJSX
import { useState } from "react";

function StudentEditor({ student }) {
  const [name, setName] = useState(student.name);

  return (
    <div className="space-y-2">
      <h2 className="font-bold">{student.name}</h2>

      <input
        value={name}
        onChange={(event) => setName(event.target.value)}
        className="rounded border p-2"
      />
    </div>
  );
}

The state initializer runs when this component initializes its state. It does not automatically replace name every time student.name changes.

If React keeps the same component identity while a different student is passed in, the input may still contain the earlier student's draft.

3.3 Use a key to reset state when the student changes

StudentPage.jsxJSX
function StudentPage({ student }) {
  return (
    <StudentEditor
      key={student.id}
      student={student}
    />
  );
}

Now React recognizes a different key when the selected student's ID changes. The previous StudentEditor instance is removed and a new one is mounted, giving it fresh state.

Real-life situations include:

  • Switching between chat recipients
  • Opening a different student's edit form
  • Switching between product configuration screens
  • Starting a new checkout flow
  • Resetting a multi-step form when the underlying record changes

3.4 How list keys help React

Suppose you render a list:

listJSX
{students.map((student) => (
  <StudentCard
    key={student.id}
    student={student}
  />
))}

The key gives each record a stable identity within that list.

Avoid using array indexes as keys for lists that can be reordered, inserted into, or deleted from:

✕ RiskyJSX
// Risky if this list can change order.
{students.map((student, index) => (
  <StudentCard key={index} student={student} />
))}

If the second student is deleted, React may associate the remaining rows with identities that no longer match the intended student records.

Prefer a stable record ID from your data.

3.5 Key rules to remember

  • A key is used by React to identify elements among siblings.
  • Keys are not passed as ordinary props. Pass student.id separately if the component needs it.
  • The same key in a different list or parent does not establish a global identity.
  • Changing a key can intentionally reset component state.
  • Do not generate random keys on every render. Doing so can repeatedly remount components.
◆ Remember

Keys are not only list warnings; keys are part of component identity.

Official guide: https://react.dev/learn/preserving-and-resetting-state

Section 04

State Batching and Update Queues

Why three setter calls don't always add three.

4.1 What is batching?

React often groups multiple state updates that occur within the same event or update cycle into a batch, reducing unnecessary work.

Imagine a shopping cart. When a user purchases an item, the application might update the cart count, total price, and order status. It is better to process those updates coherently than to display every intermediate state as a separate screen update.

4.2 Why three calls do not always add three

Consider:

Counter.jsxJSX
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  function increaseThreeTimes() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  return (
    <div className="space-y-3">
      <p>Count: {count}</p>
      <button onClick={increaseThreeTimes}>
        Add 3
      </button>
    </div>
  );
}

You might expect the count to increase by three, but it increases by one.

Why?

During that event handler, count represents the state snapshot from the current render. If count is 0, all three calls calculate 1.

Conceptually, React receives:

conceptualJSX
setCount(1);
setCount(1);
setCount(1);

The final result is 1, not 3.

4.3 The functional updater solution

When the next state depends on the previous state, use a functional updater:

updaterJSX
function increaseThreeTimes() {
  setCount((previous) => previous + 1);
  setCount((previous) => previous + 1);
  setCount((previous) => previous + 1);
}

React processes the queued updater functions in order.

Starting from 0:

  1. First updater produces 1.
  2. Second updater receives 1 and produces 2.
  3. Third updater receives 2 and produces 3.

The displayed value becomes 3.

4.4 A real-life example: tracking asynchronous orders

Suppose users can click “Place Order” several times before requests finish.

OrderTracker.jsxJSX
import { useState } from "react";

function OrderTracker() {
  const [pending, setPending] = useState(0);
  const [completed, setCompleted] = useState(0);

  async function placeOrder() {
    setPending((value) => value + 1);

    try {
      await new Promise((resolve) => setTimeout(resolve, 1500));
      setCompleted((value) => value + 1);
    } finally {
      setPending((value) => value - 1);
    }
  }

  return (
    <div className="space-y-3 rounded-xl border p-5">
      <p>Pending orders: {pending}</p>
      <p>Completed orders: {completed}</p>

      <button
        onClick={placeOrder}
        className="rounded-lg bg-indigo-600 px-4 py-2 text-white"
      >
        Place Order
      </button>
    </div>
  );
}

The functional updates prevent multiple concurrent operations from overwriting each other's state based on an old snapshot.

The example simulates the operation with a timer. A real application should catch request failures and choose whether failed orders count separately. Its UI should represent the actual business state, not only a simulated delay.

4.5 Batching does not mean state changes immediately

This code reads the state snapshot from the current render:

snapshotJSX
setCount((value) => value + 1);
console.log(count);

The log does not instantly print the new state. setCount schedules an update, and count remains the value that belongs to this render.

If you need to observe the value after React commits an update, a development effect can help:

effectJSX
useEffect(() => {
  console.log("Count after render:", count);
}, [count]);

Don't use this pattern just to calculate another piece of state that could have been derived directly.

Interview concept: Automatic batching

Modern React can batch updates in more situations than older React versions, including many updates from promises and timers. The exact integration depends on how your application is mounted and the APIs being used.

◆ Remember

State variables are snapshots, setters request updates, and functional updater functions help correctly queue state changes that depend on earlier values.

Official guide: https://react.dev/learn/queueing-a-series-of-state-updates

Section 05

useMemo and useCallback

Two different caches — one for values, one for functions.

Both hooks can help avoid repeated work, but they cache different things.

  • useMemo caches a calculated value.
  • useCallback caches a function definition between renders, as long as its dependencies remain unchanged.

They are performance tools, not requirements for every variable or function.

5.1 What is useMemo?

Imagine an institute has 20,000 student records. The dashboard lets an administrator search and filter those students.

Filtering a small list is cheap. Filtering, grouping, or sorting a very large dataset may be expensive enough that repeated calculations matter.

useMemo can cache the result of a calculation while its dependencies remain unchanged.

StudentSearch.jsxJSX
import { useMemo, useState } from "react";

function StudentSearch({ students }) {
  const [query, setQuery] = useState("");
  const [status, setStatus] = useState("all");

  const filteredStudents = useMemo(() => {
    console.log("Calculating student list");

    return students.filter((student) => {
      const matchesName = student.name
        .toLowerCase()
        .includes(query.toLowerCase());

      const matchesStatus =
        status === "all" || student.status === status;

      return matchesName && matchesStatus;
    });
  }, [students, query, status]);

  return (
    <div className="space-y-4">
      <input
        value={query}
        onChange={(event) => setQuery(event.target.value)}
        placeholder="Search students..."
        className="w-full rounded-lg border p-3"
      />

      <select
        value={status}
        onChange={(event) => setStatus(event.target.value)}
        className="rounded-lg border p-2"
      >
        <option value="all">All statuses</option>
        <option value="active">Active</option>
        <option value="inactive">Inactive</option>
      </select>

      <p>Found {filteredStudents.length} students</p>

      <ul>
        {filteredStudents.map((student) => (
          <li key={student.id}>{student.name}</li>
        ))}
      </ul>
    </div>
  );
}

What does the dependency array mean?

depsJSX
[students, query, status]

React compares these dependencies with the dependencies from the previous render.

If all dependencies are unchanged according to React's comparison, it can reuse the memoized result. If one changes, React recalculates the filtered list.

If a parent recreates the students array on every render, its reference will change and the memo will recalculate. Optimize the actual cause of excessive work rather than adding memoization everywhere.

When should you use useMemo?

Potentially useful for:

  • Expensive filtering or sorting
  • Calculating a complex chart dataset
  • Processing large client-side datasets
  • Providing a stable calculated value to an optimized child
  • Preventing repeated expensive transformations during unrelated renders

Usually unnecessary for:

trivialJSX
const total = price * quantity;

This simple calculation rarely requires memoization.

5.2 What is useCallback?

Suppose a memoized student row receives an event handler from its parent. If the parent creates a new handler function on every render, that function's reference changes even if the behavior is the same.

inline handlerJSX
const handleSelect = (studentId) => {
  console.log("Selected:", studentId);
};

Each time the component renders, this function expression creates a new function object.

useCallback lets React reuse the function definition between renders when its dependencies have not changed.

useCallbackJSX
import { useCallback, useState } from "react";

function StudentManager() {
  const [selectedStudent, setSelectedStudent] = useState(null);

  const handleSelect = useCallback((studentId) => {
    setSelectedStudent(studentId);
  }, []);

  return (
    <StudentList onSelect={handleSelect} />
  );
}

function StudentList({ onSelect }) {
  return (
    <div>
      <button onClick={() => onSelect("STU-101")}>
        Select Student 101
      </button>
    </div>
  );
}

The empty dependency array is appropriate here because the callback does not read any reactive values from the component. It receives the ID as an argument.

If the callback uses a reactive variable from the component, include the required dependencies.

For example:

with depsJSX
const handleSelect = useCallback((studentId) => {
  setSelectedStudent(studentId);
  console.log("Current filter:", filter);
}, [filter]);

When filter changes, React creates a new callback containing the updated value.

5.3 Difference between the two hooks

FeatureuseMemouseCallback
CachesA calculated resultA function definition
Typical purposeAvoid repeating expensive calculationsPreserve function identity
ReturnsThe memoized valueThe memoized function
Good exampleFiltering thousands of recordsPassing a callback to a memoized row

Conceptually:

conceptualJSX
const result = useMemo(() => expensiveCalculation(data), [data]);

const handleClick = useCallback(() => {
  doSomething(id);
}, [id]);

5.4 Common mistakes

Mistake 1: Using memoization for everything.

A cache has complexity and maintenance costs. For trivial calculations, normal code is often better.

Mistake 2: Omitting dependencies.

If a callback or calculation reads reactive values, incorrect dependency lists can cause stale values and bugs.

Mistake 3: Assuming useMemo guarantees permanent storage.

React treats memoization as an optimization. Your application should remain correct if React recalculates a memoized value.

◆ Remember

First write clear, correct code. Then profile and optimize work that actually causes performance problems.

  • https://react.dev/reference/react/useCallback

Section 06

React.memo

Skip rendering when props haven't changed.

6.1 What is React.memo?

React.memo creates a component that React can skip rendering when its props are unchanged according to a shallow comparison by default.

Imagine a teacher dashboard with 200 student cards. Selecting one student changes the selected ID in the parent. You may want the unchanged student cards to avoid unnecessary rendering work.

React.memo can help when the component's rendering is expensive and its props are stable.

6.2 Example: Memoizing a student card

StudentDashboard.jsxJSX
import { memo, useState } from "react";

const StudentCard = memo(function StudentCard({
  student,
  onSelect,
}) {
  console.log("Rendering:", student.name);

  return (
    <button
      type="button"
      onClick={() => onSelect(student.id)}
      className="w-full rounded-xl border p-4 text-left hover:bg-slate-50"
    >
      <h3 className="font-semibold">{student.name}</h3>
      <p className="text-sm text-slate-500">
        {student.course}
      </p>
    </button>
  );
});

function StudentDashboard({ students }) {
  const [selectedId, setSelectedId] = useState(null);

  return (
    <div className="space-y-3">
      <p>Selected student: {selectedId ?? "None"}</p>

      {students.map((student) => (
        <StudentCard
          key={student.id}
          student={student}
          onSelect={setSelectedId}
        />
      ))}
    </div>
  );
}

Why might this help?

The state update in the parent causes the parent to render again. If the student objects and onSelect function remain the same references, React can skip rendering the memoized card for unchanged props.

The state setter from useState has a stable identity, so it is suitable to pass here.

6.3 Why can React.memo still re-render?

A memoized component can still render for reasons other than changed props.

For example:

  • Its own state changes.
  • A context it consumes changes.
  • A prop value changes.
  • A prop is a new object or function reference each render.

This can defeat memoization:

✕ New ref each renderJSX
<StudentCard
  student={student}
  onSelect={(id) => setSelectedId(id)}
/>

The inline callback has a new reference on each parent render.

You could pass the stable setter directly, as in the previous example, or use useCallback if the handler needs additional logic and profiling shows it matters.

Likewise, creating an inline object repeatedly may prevent memoization:

✕ New object each renderJSX
<StudentCard
  student={{ id: student.id, name: student.name }}
  onSelect={setSelectedId}
/>

Here a fresh object is created on every render.

6.4 Is React.memo always faster?

No.

Memoizing a component has its own costs, including comparing props and increasing code complexity. A cheap component may be just as fast—or simpler—without memoization.

◆ Practical rule

Consider React.memo for expensive components that often receive the same props. Use the React Profiler to understand whether it improves the actual application.

Official reference: https://react.dev/reference/react/memo

Section 07

useTransition and useDeferredValue

Keeping interfaces responsive when some updates are expensive.

These hooks help keep interfaces responsive when some updates cause expensive rendering work.

Think about a product page containing a text input and a grid of thousands of products. The user's keystrokes should remain responsive even if calculating and rendering the result grid is expensive.

7.1 What is useTransition?

useTransition allows you to mark certain state updates as non-urgent transitions. React can prioritize urgent interactions over this rendering work.

It returns:

shapeJSX
const [isPending, startTransition] = useTransition();
  • isPending indicates that a transition is still in progress.
  • startTransition marks state updates inside its callback as transition updates.

Real-life example: Changing dashboard tabs

AnalyticsTabs.jsxJSX
import { useState, useTransition } from "react";

function AnalyticsTabs() {
  const [tab, setTab] = useState("overview");
  const [isPending, startTransition] = useTransition();

  function selectTab(nextTab) {
    startTransition(() => {
      setTab(nextTab);
    });
  }

  return (
    <div className="space-y-4">
      <div className="flex gap-3">
        <button onClick={() => selectTab("overview")}>
          Overview
        </button>

        <button onClick={() => selectTab("reports")}>
          Reports
        </button>

        <button onClick={() => selectTab("students")}>
          Students
        </button>
      </div>

      {isPending && (
        <p aria-live="polite">Updating dashboard...</p>
      )}

      <section className={isPending ? "opacity-70" : ""}>
        {tab === "overview" && <Overview />}
        {tab === "reports" && <Reports />}
        {tab === "students" && <Students />}
      </section>
    </div>
  );
}

function Overview() {
  return <h2>Overview dashboard</h2>;
}

function Reports() {
  return <h2>Reports dashboard</h2>;
}

function Students() {
  return <h2>Students dashboard</h2>;
}

The example demonstrates the pattern. The transition is most useful if rendering the selected view creates meaningful work. For three tiny components, it may not provide a visible benefit.

Important limitation

Do not use transition updates to control the value of a text input. The input's value should update urgently so that typing stays responsive.

useTransition changes rendering priority; it does not automatically make network requests faster.

7.2 What is useDeferredValue?

useDeferredValue creates a deferred version of a value that may update later than the latest value, allowing a part of the UI to catch up in the background.

Think of typing in a search box:

  • The input should always display the latest character immediately.
  • A costly result list can update with a deferred query.
ProductSearch.jsxJSX
import { useDeferredValue, useState } from "react";

function ProductSearch({ products }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);

  const results = products.filter((product) =>
    product.name
      .toLowerCase()
      .includes(deferredQuery.toLowerCase())
  );

  const isStale = query !== deferredQuery;

  return (
    <div className="space-y-4">
      <input
        value={query}
        onChange={(event) => setQuery(event.target.value)}
        placeholder="Search products..."
        className="w-full rounded-lg border p-3"
      />

      <div
        aria-live="polite"
        className={isStale ? "opacity-60" : ""}
      >
        <p>Matching products: {results.length}</p>

        <ul>
          {results.slice(0, 30).map((product) => (
            <li key={product.id}>{product.name}</li>
          ))}
        </ul>
      </div>
    </div>
  );
}

The input uses query, which updates immediately. The result calculation uses deferredQuery, which can lag behind during intensive rendering.

For a small array, this may be unnecessary. It becomes more relevant when result rendering is costly.

useId

Connecting labels and descriptions without ID collisions.

8.1 What is useId?

useId generates a unique ID associated with a particular component instance. It is especially useful for accessibility relationships, such as connecting a form label to an input or an input to its help text.

Imagine a registration form with email, password, and confirmation fields. Each input needs a label and may have its own error message. IDs must not accidentally collide when the same reusable field component appears more than once.

8.2 Example: Reusable input field

SignupForm.jsxJSX
import { useId } from "react";

function EmailField() {
  const id = useId();

  return (
    <div className="space-y-2">
      <label htmlFor={id} className="block font-medium">
        Email address
      </label>

      <input
        id={id}
        type="email"
        className="w-full rounded-lg border p-3"
        aria-describedby={`${id}-help`}
      />

      <p id={`${id}-help`} className="text-sm text-slate-500">
        Use the email address associated with your account.
      </p>
    </div>
  );
}

export default function SignupForm() {
  return (
    <form className="space-y-4">
      <EmailField />
      <EmailField />
    </form>
  );
}

Each EmailField gets an ID associated with its own component instance, so the label and description can refer to the correct input.

In a real signup form, you normally would not show duplicate email fields. The example renders two copies to demonstrate ID uniqueness.

8.3 When should you use it?

Use useId to connect:

  • A label and form input
  • A validation message and an input
  • A description and a control
  • An accessible disclosure or other related elements

8.4 What should you not use it for?

Do not use useId to generate keys for list items.

Instead, use the stable ID from the underlying data:

list keysJSX
{students.map((student) => (
  <StudentCard key={student.id} student={student} />
))}

Also do not use useId as a cache key or general-purpose data identifier.

◆ Remember

useSyncExternalStore

Subscribing React to state that lives outside React.

9.1 What is an external store?

Most React components receive data through props, state, and context.

An external store is a state source that lives outside React's normal state mechanism. Examples can include:

  • A custom subscription-based store
  • A third-party state management library
  • A browser API that changes over time
  • A shared data source maintained independently of React components

Real-life example: imagine a dashboard widget displaying the browser's online/offline status. The browser itself owns that status. React needs to subscribe to changes and re-render when it changes.

useSyncExternalStore provides a way to subscribe to an external source and read its current snapshot.

9.2 Example: Browser online status

NetworkStatus.jsxJSX
import { useSyncExternalStore } from "react";

function subscribe(callback) {
  window.addEventListener("online", callback);
  window.addEventListener("offline", callback);

  return () => {
    window.removeEventListener("online", callback);
    window.removeEventListener("offline", callback);
  };
}

function getSnapshot() {
  return navigator.onLine;
}

function getServerSnapshot() {
  return true;
}

function NetworkStatus() {
  const isOnline = useSyncExternalStore(
    subscribe,
    getSnapshot,
    getServerSnapshot
  );

  return (
    <p
      className={
        isOnline
          ? "text-emerald-700"
          : "text-red-700"
      }
    >
      {isOnline ? "You are online" : "You are offline"}
    </p>
  );
}

export default NetworkStatus;

How it works

subscribe

subscribeJSX
function subscribe(callback) {
  window.addEventListener("online", callback);
  window.addEventListener("offline", callback);

  return () => {
    window.removeEventListener("online", callback);
    window.removeEventListener("offline", callback);
  };
}

React subscribes using this function and uses the returned function to unsubscribe.

getSnapshot

getSnapshotJSX
function getSnapshot() {
  return navigator.onLine;
}

This reads the current browser status.

getServerSnapshot

getServerSnapshotJSX
function getServerSnapshot() {
  return true;
}

This provides a server-side snapshot for rendering environments that support server rendering. The value is illustrative and assumes the application chooses an online placeholder. If the snapshot cannot reliably match the server-rendered output during hydration, choose an appropriate deterministic fallback and design the UI to handle correction on the client.

For a client-only Vite application, you can omit getServerSnapshot.

9.3 Important rules when using this Hook

  • Keep snapshots stable when the underlying data has not changed.
  • Subscribe and unsubscribe correctly.
  • Do not return a new object from getSnapshot on every call if the store has not changed.
  • Prefer a maintained state library when it already handles subscriptions and concurrent React integration correctly.
  • Do not reach for useSyncExternalStore when ordinary useState or context is sufficient.

For example, this is a risky snapshot function if the store has not changed:

✕ Unstable snapshotJSX
function getSnapshot() {
  return { online: navigator.onLine };
}

It creates a new object every time. Prefer a stable snapshot or use the appropriate immutable snapshot mechanism for your store.

useImperativeHandle and forwardRef Compatibility

Exposing a narrow imperative API when a ref is the right tool.

10.1 First, understand a ref

A ref gives a component a way to hold a value that is not itself used to render the UI. A common example is obtaining access to an input DOM element so that the application can focus it.

Real-life situation: a user clicks “Search Students,” and the search input should receive focus automatically.

SearchStudents.jsxJSX
import { useRef } from "react";

function SearchStudents() {
  const inputRef = useRef(null);

  function focusInput() {
    inputRef.current?.focus();
  }

  return (
    <div className="flex gap-2">
      <input
        ref={inputRef}
        placeholder="Search students..."
        className="rounded-lg border p-2"
      />

      <button
        type="button"
        onClick={focusInput}
        className="rounded-lg bg-indigo-600 px-4 py-2 text-white"
      >
        Focus Search
      </button>
    </div>
  );
}

React assigns the DOM element to inputRef.current after it is mounted and clears the DOM ref when it is removed.

10.2 What is useImperativeHandle?

Usually, a parent tells a child what to render through props. A ref offers an alternative for a narrow set of cases where the parent needs an imperative action.

useImperativeHandle lets a component expose a chosen object of methods through a ref rather than exposing its entire internal DOM structure.

Imagine a custom text editor. Its parent needs methods like focus() and clear(), but it does not need to know the internal structure of the editor.

10.3 React 19 example: pass ref as a prop

React 19 allows function components to receive ref as a prop. New React 19 code generally does not need forwardRef.

StudentSearch.jsxJSX
import { useImperativeHandle, useRef } from "react";

function SearchInput({ ref }) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() {
      inputRef.current?.focus();
    },

    clear() {
      if (inputRef.current) {
        inputRef.current.value = "";
      }
    },
  }), []);

  return (
    <input
      ref={inputRef}
      placeholder="Search students..."
      className="rounded-lg border p-3"
    />
  );
}

export default function StudentSearch() {
  const searchRef = useRef(null);

  return (
    <div className="space-y-3">
      <SearchInput ref={searchRef} />

      <div className="flex gap-2">
        <button
          onClick={() => searchRef.current?.focus()}
          className="rounded bg-indigo-600 px-3 py-2 text-white"
        >
          Focus
        </button>

        <button
          onClick={() => searchRef.current?.clear()}
          className="rounded border px-3 py-2"
        >
          Clear
        </button>
      </div>
    </div>
  );
}

The parent receives an object containing the two explicit methods rather than a direct reference to the internal input.

▲ Important

This is an imperative API. Directly clearing the DOM value is appropriate only for an uncontrolled input. If the input is controlled with a React value prop, clearing it imperatively is not sufficient; the component should update the relevant React state instead.

10.4 What about forwardRef?

For React 18 and older function-component patterns, forwardRef allows a ref to be passed through a component to a child.

forwardRefJSX
import { forwardRef } from "react";

const SearchInput = forwardRef(function SearchInput(props, ref) {
  return (
    <input
      ref={ref}
      {...props}
      className="rounded-lg border p-3"
    />
  );
});

In React 18, this enables a parent to obtain the input DOM element by using a ref on SearchInput.

In React 19, forwardRef is no longer necessary for new function components because ref can be received as a prop. The API is still relevant when maintaining applications and components written for older React versions.

When should you use imperative handles?

Use them sparingly for actions that are genuinely imperative, such as:

  • Focusing an input
  • Selecting text
  • Starting or stopping a custom media widget
  • Triggering a narrow operation on an embedded third-party editor

Do not turn a component into a huge object of methods when ordinary props and state can describe the same behavior more clearly.

  • https://react.dev/reference/react/forwardRef

Portals

Rendering into a different DOM location — while keeping React tree.

11.1 What is a React portal?

A portal allows React to render elements into a different location in the DOM while keeping those elements in the same React component tree.

Real-life example: an admin dashboard opens a confirmation dialog inside a deeply nested card. If the dialog stays inside a parent container with clipping or stacking restrictions, it might appear behind other elements or be cut off.

A portal can render the dialog's DOM into another container, often a dedicated element near the end of the document body.

11.2 Add a portal target

In the Vite project's index.html:

index.htmlHTML
<div id="root"></div>
<div id="modal-root"></div>

The second element provides a target for portal content.

11.3 Create a modal using a portal

ConfirmationModal.jsxJSX
import { createPortal } from "react-dom";

function ConfirmationModal({ onClose, onConfirm }) {
  const modalRoot = document.getElementById("modal-root");

  if (!modalRoot) {
    return null;
  }

  return createPortal(
    <div className="fixed inset-0 z-50 grid place-items-center bg-black/50 p-4">
      <section
        role="dialog"
        aria-modal="true"
        aria-labelledby="delete-title"
        className="w-full max-w-md rounded-xl bg-white p-6 shadow-xl"
      >
        <h2 id="delete-title" className="text-xl font-bold">
          Delete student?
        </h2>

        <p className="mt-3 text-slate-600">
          This action cannot be undone.
        </p>

        <div className="mt-6 flex justify-end gap-3">
          <button
            type="button"
            onClick={onClose}
            className="rounded-lg border px-4 py-2"
          >
            Cancel
          </button>

          <button
            type="button"
            onClick={onConfirm}
            className="rounded-lg bg-red-600 px-4 py-2 text-white"
          >
            Delete
          </button>
        </div>
      </section>
    </div>,
    modalRoot
  );
}

Usage:

DeleteStudentButton.jsxJSX
import { useState } from "react";

function DeleteStudentButton() {
  const [showModal, setShowModal] = useState(false);

  function confirmDelete() {
    // Call your real delete workflow here.
    setShowModal(false);
  }

  return (
    <>
      <button
        type="button"
        onClick={() => setShowModal(true)}
        className="rounded-lg bg-red-600 px-4 py-2 text-white"
      >
        Delete Student
      </button>

      {showModal && (
        <ConfirmationModal
          onClose={() => setShowModal(false)}
          onConfirm={confirmDelete}
        />
      )}
    </>
  );
}

This illustrates where a portal can be useful. A production modal needs more than visual positioning: it should move focus into the dialog, keep keyboard focus appropriately contained, handle Escape where suitable, return focus to the opener, and prevent inappropriate interaction with the background.

Use a tested accessible dialog primitive when possible.

11.4 What makes portals special?

A portal changes the physical DOM placement, but not the logical React parent-child relationship.

Consequently:

  • React context still works inside the portal.
  • Events bubble through the React tree rather than only through the physical DOM tree.
  • The portal still participates in React's state and component lifecycle.
  • Portals are useful for modals, tooltips, menus, and overlays.

Error Boundaries

Catching render failures and isolating them to one section.

12.1 What is an Error Boundary?

An Error Boundary is a React component that catches certain errors thrown while rendering its descendant components, displaying a fallback UI instead of letting that rendering failure break the rest of the interface.

Imagine an analytics dashboard containing:

  • A student statistics panel
  • A fee collection chart
  • An attendance panel
  • A placement report

If the placement report crashes, it is often better to show an error message inside that panel while allowing other sections to remain useful.

12.2 Create an Error Boundary

The standard built-in React Error Boundary pattern still uses a class component.

ErrorBoundary.jsxJSX
import { Component } from "react";

class ErrorBoundary extends Component {
  constructor(props) {
    super(props);

    this.state = {
      hasError: false,
    };
  }

  static getDerivedStateFromError(error) {
    return {
      hasError: true,
    };
  }

  componentDidCatch(error, info) {
    // Send error details to your monitoring service.
    console.error("UI rendering error:", error, info);
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="rounded-xl border border-red-200 bg-red-50 p-5 text-red-900">
          <h2 className="font-bold">
            This section could not load.
          </h2>

          <p className="mt-2 text-sm">
            Try again or return to the dashboard.
          </p>
        </div>
      );
    }

    return this.props.children;
  }
}

export default ErrorBoundary;

12.3 Use the Error Boundary around a component

Dashboard.jsxJSX
function Dashboard() {
  return (
    <main className="grid gap-5 lg:grid-cols-2">
      <StudentStatistics />

      <ErrorBoundary>
        <PlacementReport />
      </ErrorBoundary>
    </main>
  );
}

If PlacementReport or a descendant throws during rendering and no closer boundary catches the error, React can show the fallback for that section.

12.4 What does an Error Boundary catch?

Error Boundaries are designed for errors thrown during rendering of descendant components and the related React rendering/lifecycle work covered by the boundary.

Do not assume an Error Boundary catches every possible application error.

They do not automatically catch:

  • Errors from ordinary event-handler code
  • Errors from arbitrary asynchronous callbacks such as a timer
  • Errors that occur in server-side rendering
  • Errors thrown by the boundary itself

For example, this request needs its own error handling:

saveStudentJSX
async function saveStudent() {
  try {
    await fetch("/api/students", {
      method: "POST",
    });
  } catch (error) {
    console.error("Failed to save student:", error);
  }
}

Error Boundaries and try...catch solve different problems and are often used together.

12.5 Choosing a boundary's location

Consider boundaries around UI sections where a local failure can be isolated.

Useful places include:

  • A large dashboard panel
  • A route or page
  • A complex editor
  • A third-party visualization
  • An independent area of an application

An overly broad boundary may replace an entire application when only one panel failed. Too many tiny boundaries can clutter the design. Choose a boundary level that matches how much of the UI can reasonably recover independently.

Real-world production behavior

Instead of simply displaying an error, a production boundary might:

  • Log sanitized diagnostic data to a monitoring service
  • Offer a retry mechanism where appropriate
  • Show a friendly fallback
  • Preserve unrelated parts of the interface
◆ Remember

Error Boundaries catch certain rendering failures; normal application code still needs its own error handling for events and network requests.

Section 13

Suspense Fundamentals

Coordinated loading UI — but only for supported operations.

13.1 What is Suspense?

Suspense allows you to display a fallback UI while a descendant is waiting on a supported Suspense-enabled operation.

Imagine opening the Reports page in an admin dashboard. The report component's code has not yet loaded. Rather than showing a blank area, the application can display a loading placeholder until the real UI becomes available.

ReportsPage.jsxJSX
import { Suspense } from "react";

function ReportsPage() {
  return (
    <Suspense fallback={<p>Loading reports...</p>}>
      <Reports />
    </Suspense>
  );
}

When a descendant suspends during rendering, React can show the nearest Suspense boundary's fallback.

13.2 A crucial distinction: Suspense is not a universal loading detector

This common misconception causes confusion:

✕ Not detectedJSX
useEffect(() => {
  fetch("/api/students");
}, []);

Adding this effect does not automatically make the nearest Suspense boundary display its fallback.

Suspense does not detect arbitrary data loading that occurs in an effect or event handler.

Suspense can be used with supported mechanisms such as lazy, Suspense-enabled frameworks, or supported Promise-reading patterns. How data fetching integrates with Suspense depends on your framework or data library.

13.3 Suspense with a lazy component

Dashboard.jsxJSX
import { lazy, Suspense } from "react";

const Reports = lazy(() => import("./Reports.jsx"));

function Dashboard() {
  return (
    <main>
      <h1 className="text-2xl font-bold">
        Dashboard
      </h1>

      <Suspense
        fallback={
          <div className="mt-5 animate-pulse rounded-xl bg-slate-200 p-8">
            Loading reports...
          </div>
        }
      >
        <Reports />
      </Suspense>
    </main>
  );
}

export default Dashboard;

When React first attempts to render Reports, its component code may still be loading. Suspense provides the loading UI.

When the module becomes available, React can render the actual reports UI.

13.4 Nested Suspense boundaries

Imagine a dashboard has a profile summary and a heavy analytics chart.

You might choose to let the profile load independently from the chart.

Dashboard.jsxJSX
import { Suspense } from "react";
import ProfileSummary from "./ProfileSummary";
import AnalyticsChart from "./AnalyticsChart";

function Dashboard() {
  return (
    <div className="space-y-6">
      <ProfileSummary />

      <Suspense fallback={<p>Loading analytics chart...</p>}>
        <AnalyticsChart />
      </Suspense>
    </div>
  );
}

This boundary isolates the chart's fallback behavior from content that does not suspend within it.

A boundary higher up in the tree can handle a broader section. Good boundaries help the application reveal useful content at the right time rather than replacing more UI than necessary.

13.5 Error handling for Suspense

Suspense and Error Boundaries address different conditions:

  • Suspense: A supported child operation is not ready yet.
  • Error Boundary: A descendant throws a render-related error covered by the boundary.

Lazy-loaded modules can fail to load. A robust application should handle that failure with an appropriate Error Boundary, alongside its Suspense fallback.

◆ Remember

Suspense is a rendering coordination feature. It is not the same thing as a spinner component or a general-purpose isLoading state.

Official reference: https://react.dev/reference/react/Suspense

Section 14

Lazy Loading and Code Splitting

Loading only the code a user actually needs — when they need it.

14.1 What is lazy loading?

Lazy loading means delaying the loading or initialization of something until it is needed.

For a React application, code splitting can divide your JavaScript into smaller chunks so a user does not necessarily download the code for every screen at the start.

Think of an institute portal with separate pages for student management, financial reports, analytics, and settings.

A user who opens the student page may not need to download every report component immediately.

14.2 Eager versus lazy loading

A regular import is typically statically included in the dependency graph:

eagerJSX
import Reports from "./Reports.jsx";

A lazy import can defer loading that module until React first attempts to render the component:

lazyJSX
import { lazy } from "react";

const Reports = lazy(() => import("./Reports.jsx"));

When configured with a supported build tool such as Vite, this dynamic import can become a separate chunk.

14.3 Full example: Lazily load an analytics page

Reports.jsx:

Reports.jsxJSX
export default function Reports() {
  return (
    <section className="rounded-xl border p-6">
      <h2 className="text-xl font-bold">
        Analytics Reports
      </h2>

      <p className="mt-3 text-slate-600">
        Your advanced analytics view is ready.
      </p>
    </section>
  );
}

App.jsx:

App.jsxJSX
import { lazy, Suspense, useState } from "react";

const Reports = lazy(() => import("./Reports.jsx"));

export default function App() {
  const [showReports, setShowReports] = useState(false);

  return (
    <main className="space-y-5 p-6">
      <h1 className="text-2xl font-bold">
        Institute Dashboard
      </h1>

      <button
        type="button"
        onClick={() => setShowReports((value) => !value)}
        className="rounded-lg bg-indigo-600 px-4 py-2 text-white"
      >
        {showReports ? "Hide Reports" : "Open Reports"}
      </button>

      {showReports && (
        <Suspense fallback={<p>Loading analytics reports...</p>}>
          <Reports />
        </Suspense>
      )}
    </main>
  );
}

What is happening?

  1. The application starts without needing to render the Reports component.
  2. The user opens the reports section.
  3. React tries to render the lazy component.
  4. If its code has not loaded, the Suspense fallback is displayed.
  5. When the module is ready, the real component appears.

This can reduce the initial JavaScript needed by the application, especially when some screens are large or rarely visited.

14.4 Where should you use lazy loading?

Good candidates include:

  • Large analytics reports
  • An admin-only editor
  • Less frequently visited route pages
  • Heavy charting or visualization features
  • An advanced rich-text editor
  • Large feature-specific components

Small components that are needed immediately are usually not worth splitting out individually.

14.5 Does lazy loading always improve performance?

Not necessarily.

Splitting too much can create many network requests, and users may experience a delay when opening a lazy section. Code splitting works best when it reduces unnecessary initial downloads while keeping navigation responsive.

Consider where to place Suspense boundaries, use loading placeholders, and measure the resulting bundle rather than assuming more chunks are always better.

A common real-world pattern is to lazy-load entire route pages rather than every small button, heading, and card.

Official reference: https://react.dev/reference/react/lazy

Section 15

React Compiler Concepts and When Manual Memoization Is Needed

Automatic optimization — and the judgment that still matters.

15.1 What is React Compiler?

React Compiler is a build-time tool that can automatically optimize component rendering by applying memoization-like optimizations to supported code.

Previously, developers often needed to identify rendering bottlenecks and manually introduce tools such as:

  • useMemo
  • useCallback
  • React.memo

React Compiler aims to reduce that manual work by recognizing opportunities to reuse calculations and avoid unnecessary re-rendering.

It does not replace React fundamentals, correct state management, profiling, or good architecture.

Official guide: https://react.dev/learn/react-compiler

15.2 Why was manual memoization common?

Imagine a parent component renders a large student list. Every time a filter changes, some values and callbacks may be recreated.

Manual memoization might help:

manual memoJSX
const visibleStudents = useMemo(() => {
  return students.filter((student) => student.active);
}, [students]);

const handleStudentClick = useCallback((studentId) => {
  setSelectedId(studentId);
}, []);

const StudentRow = memo(function StudentRow({ student, onSelect }) {
  return (
    <button onClick={() => onSelect(student.id)}>
      {student.name}
    </button>
  );
});

These APIs let a developer explicitly cache a result, a callback, or a component's rendering behavior.

The drawback is that manual memoization introduces extra code and dependency-management requirements. It can be unnecessary or even confusing if used without a measurable reason.

15.3 How does React Compiler change the picture?

When React Compiler is installed and correctly configured, it can automatically optimize supported components and hooks. In suitable cases, this can reduce the need to manually memoize every value, callback, or component.

However, it is not a magic speed-up switch.

  • The compiler must be properly set up for your project and build.
  • Your code should follow React's rules and be compatible with the compiler.
  • The compiler cannot eliminate all expensive algorithms, network delays, or poorly designed state flows.
  • External systems and business logic still require sound architecture.
  • You still need to measure whether the application meets its performance goals.

Follow the current official installation guide for your build tool and React version instead of copying compiler configuration from an older tutorial.

15.4 Should you stop learning useMemo, useCallback, and React.memo?

No.

Understand these tools because existing applications may use them, a compiler may not cover every situation, and some library APIs may have particular identity or caching requirements.

But you should not begin every React component by adding manual memoization.

A practical sequence is:

  1. Build correct components with clear data flow.
  2. Avoid unnecessary duplicated state and expensive work.
  3. Test the screen and measure its performance.
  4. Enable and validate React Compiler when it is appropriate for your project.
  5. Add manual memoization when profiling, architectural requirements, or integration constraints justify it.

15.5 When might manual memoization still be appropriate?

Consider manual memoization when:

  • You have identified an expensive calculation that should not repeat unnecessarily.
  • A memoized child needs stable prop references, and the compiler is not providing the necessary optimization.
  • You are developing or maintaining a library with specific referential-stability expectations.
  • Your setup does not use React Compiler, or parts of your code are not compiled.
  • Profiling reveals that a manual optimization meaningfully improves performance.

Always preserve correctness. A component must not depend on React retaining a memo forever; memoization is a performance optimization, not the source of truth for application state.

Common Advanced React Mistakes

Fifteen pitfalls every advanced React developer runs into.

  1. Using useEffect for values that could be derived during rendering.
  2. Assuming every component render creates a DOM update.
  3. Using array indexes as keys for lists that change.
  4. Expecting state updates to change the current render's state snapshot immediately.
  5. Using useMemo and useCallback for trivial calculations without a clear reason.
  6. Believing React.memo prevents every possible re-render.
  7. Using useTransition to control a text input.
  8. Using useId for list keys or business record identifiers.
  9. Subscribing to an external store without cleaning up correctly.
  10. Exposing a large imperative API when ordinary props and state would be simpler.
  11. Assuming that createPortal automatically provides accessible modal behavior.
  12. Expecting an Error Boundary to catch every event-handler or asynchronous error.
  13. Assuming Suspense detects every fetch made with useEffect.
  14. Lazy-loading every small component and harming the loading experience.
  15. Believing React Compiler removes the need for profiling or correct architecture.
